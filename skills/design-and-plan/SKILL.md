# 设计与计划

你非常擅长构建。你构建的是你以为需求方想要的东西——而「我做的就是他们想要的」这份信念，实际上往往没有它给人的感觉那么站得住。这项技能的用途，就是在任何软件开发产物被构建出来之前，弄清他们真正想要什么、以及为什么。

人们往往还没想清楚自己要什么。好的提问能帮他们想透。当你理解了缘由，面对那一百个他们从未提起的决定，你就会做出他们本来会做的选择。

## 收到新问题时先分类

分类判据见 superpowers:using-superpowers 的「流程闸门与定性」，结论用一句话宣布（类型 + 依据）。新 feature 或新设计 → 走本技能完整流程（建新 `docs/superpowers/specs/<date-feature>/` 五件套）；缺陷修复 → bugfix 路径（修复分支修复 + 合并前过收官把关与集成验证门槛，不建需求目录）。小 feature 不得说成 bugfix 来绕开五件套；设计期发现实为缺陷修复 → 重定性为 bugfix，转修复链，工作树保留改名。

## 实施顺序

开始实现之前，按序完成步骤：

1. **判断需求的范围 → 需求对话**：复述与提问交替进行；视觉伴侣在第一次复述 UI 相关内容前即提议，不等到聊完。
2. **四件套成稿**：design → implementation → plan → verification，decisions.md 随每条对话裁决落定追加。
3. **自查与排版**：按 `references/review-prompt.md` 清单 A 的核对项自查，再运行 `bash scripts/check-tables.sh <四件路径>`、`bash scripts/check-mermaid.sh <四件路径>` 与 `bash scripts/check-doc-structure.sh <四件路径>`（design.md / implementation.md / plan.md / verification.md 依次传入），按输出修复问题（无该脚本环境时，由审读提示词中的排版核对兜底）。
4. **一个审读子代理审全套**：四件齐审 + decisions.md 标注一致核对，批量修订后收敛复读。
5. **结构化呈报**：裁决呈报与确认请求分两条消息（先裁决，需求方回复后单独发确认）；确认后执行交接。

细则在各步小节。每一步的问题在当前步解决：设计未定就不写计划。全套产物被修订时，只有影响范围、功能或决策的修订才触发重审与重新确认；纯文字修订走轻量修订通道（见 `references/reporting-rules.md`）；判断有疑义时按影响处理。

## 弄清他们要什么

本步纪律全文见 `references/dialogue-discipline.md`——进入第一步之前先读它（覆盖：判断需求的范围、你实际知道什么、先看再问、你的第一条消息、对话、复述、列出各方案与 spike）。视觉伴侣指南见 `references/visual-companion.md`，第一次复述 UI 相关内容前即提议。方向拍板（列出各方案）是进入下一步的铰链：方案定了才进第二步。

本节产出 design.md——共识文档：对话的固化，做什么、为什么、明确不做、关键决策与约束；全文零实现词汇（功能清单用「最终用户」）。结构与格式见 references/design-doc-template.md；写 design.md 前先读它。

## 实现设计

把确定的需求翻译成技术方案：数据怎么存、接口怎么定、流程怎么走——目的：技术意图权威化，供需求方审查与任务拆分引用；产出：implementation.md，结构与格式见 references/implementation-template.md。写它之前通读本节原则。

### 架构设计原则

设计模块划分、接口契约、数据结构与依赖方向时逐条对照——每条带违反信号，对上号就是设计缺陷。

1. **关注点分离**——业务逻辑、展示、持久化、配置各归其位；一个模块只回答一个问题。违反信号：改一个业务规则要同时碰展示层和存储层。
2. **高内聚、低耦合**——内聚的判据不是「功能相近」，而是「变化理由相同」：模块内部元素因同一个理由一起变化（单一职责的正面表述）。耦合的实测信号是改动放大：改一处要动 N 处，就是耦合过高。模块间走窄接口，不做大而全的「工具箱模块」。
3. **抽象与信息隐藏**——调用方依赖抽象而非实现。违反信号：接口签名暴露内部结构（返回内部对象）、要求调用方知道内部调用顺序——即泄漏抽象。一个接口一个角色，不让任何调用方被迫依赖它用不到的方法（接口隔离）。
4. **依赖单向、指向稳定**——被依赖者不知道依赖者；高层策略与低层细节都依赖抽象（依赖倒置）；循环依赖在结构设计章当场拆掉（拆接口 / 事件 / 回调），不是标注「以后处理」。
5. **最少知识**——只与直接协作方通信。违反信号：`a.b().c().d()` 链式深入他人的内部结构。
6. **组合优于继承**——继承层次超过两层即警惕，优先组合 + 接口注入；实现接口时遵守行为契约（里氏替换）：子类型必须能无惊地替换父类型的约定。
7. **消灭偶然复杂度**——区分必需复杂度（问题本身固有的）与偶然复杂度（方案选择引入的），后者是设计缺陷；简单方案能用就不上复杂方案。对「已知的变更方向」留缝（版本字段、错误码留段），不为想象中的需求建抽象（开闭原则与 YAGNI 的边界）。

### 实证纪律

这六条来自真实失败（确认语义事故、数据丢失、平台能力误判）。写接口错误表、外部格式转换、状态机时逐条核对。

8. **接口是承诺，不是清单**——凡被「被谁依赖」引用的接口，签名、错误语义、示例结果的任何变更都是兼容性变更，须过确认门。
9. **先外部后内部**——外部契约（endpoint / CLI / 公共 API）先冻结，内部接口围绕它设计，不是反过来；实现细节不进接口章。
10. **失败路径与降级是一等公民**——每个外部依赖（网络 / 磁盘 / 进程 / 第三方）必须写明失败行为（超时、重试、降级、报错路径）；「正常路径走通」不等于设计完成。
11. **状态必须有唯一归属**——每个状态单一写点、单一事实来源；「谁拥有这个状态」答不出来就是设计缺口；共享状态必须写并发与一致性语义。
12. **数据是最大的承诺**——字段表没有示例值即臆写；外部格式转换逐字对照（转换是数据丢失高发地）；状态机穷举非法迁移，漏掉的迁移就是线上事故。
13. **平台能力约束必须实测后写**——禁写「应该可以」；构建工具链能力边界、自动化测试可用性，写进界面实现规格章之前必须实测验证。

## 任务拆分

把 implementation.md 的结构切成可执行的任务规格——目的：执行契约无歧义，下游零改动消费；产出：plan.md，结构与格式见 references/plan-template.md。写它之前通读本节原则。

计划是实施者无法独自做出的那批决定的集合，为一名没有见过这个代码库、也没有见过这份设计文档的工程师撰写。假设他们一旦知道了确切的接口、确切的边界条件与确切的验收标准，就能用项目的语言写出地道的代码；并且凡是计划留出开放选择的地方，他们都会做出合理的选择。他们无法知道的是你决定了什么：哪些文件、哪些名称与签名、设计文档中的哪些取值、哪些边界条件与验收标准证明每个任务。把这些写进文档。把整份计划拆成任务交给他们。DRY。YAGNI。TDD。频繁提交。

任务边界已在 implementation.md 的结构设计定下（模块边界即任务边界；子系统的拆分也在那一章定），plan.md 把这些决定落成可执行的规格。如果发现设计文档覆盖多个相互独立的子系统、本应拆成多份独立计划（在 implementation 结构设计时就该拆），建议拆分——每份计划都应当能独立产出可运行、可测试的软件；没有拆就回头，不要硬写。

在定义任务拆分之前，先梳理出将创建或修改哪些文件、每个文件各负责什么。任务如何分解，就在这一步敲定。

- 以清晰的边界和定义良好的接口来设计各个单元。每个文件应当只有一个明确的职责。
- 当代码能一次性放进上下文时，你的推理效果最好；当文件足够专注时，你的编辑也更可靠。宁选更小、更专注的文件，也不要承担太多职责的大文件。
- 一起变动的文件应当放在一起。按职责拆分，而不是按技术分层拆分。
- 在既有代码库中，遵循既有的模式。如果代码库用的就是大文件，不要单方面重构——但如果你正要修改的某个文件已经臃肿到难以驾驭，在实现设计里安排一次拆分是合理的。

这个结构为任务分解提供依据。每个任务都应当产出自包含、独立来看也成立的改动。

计划是实施前的决策记录；实施后的结论由提交信息承载，计划本身不回填。

### 切分原则

**任务规模划定**

任务是携带着自身测试循环、且值得由一名全新审查者单独把关的最小单元。划定任务边界时：哪项任务产出的交付物需要准备、配置、脚手架和文档类的工作，就把这些工作并入该任务；只有当审查者可能实质性地否决某个任务、却同时批准其相邻任务时，才在该处拆分任务边界。每个任务都以一个可独立测试的交付物收尾。

**任务详细度**

TDD 的红绿循环——写失败测试、运行确认失败、实现最小代码、运行确认通过、提交——由执行者按 superpowers:test-driven-development 从验收标准自行展开，**不在计划中预写**。

预写测试代码与实现步骤，等于把代码誊进计划：一份比它所描述的代码还长的计划是誊抄，不是计划。

## 验证用例

为 design 的每条承诺立可判真伪的验证场景——目的：证明做成的东西就是承诺的；产出：verification.md。纯单模块无接口时不产出该文件，plan.md 骨架不变。

verification.md 用场景证明做成的东西就是 design.md 承诺的。写它的原则：断言优先用可观测缝（环境变量、调试日志、可查询状态），人工条目诚实标注不伪装自动化；场景出处锚定（`§N` 指 design.md、`Task N` 指 plan.md、`I-N` 指 implementation.md）；确定性固定策略——每条期望可判真伪、可重复执行。场景间无依赖、可并行调度——并行安全即无全局资源依赖（无固定端口、固定容器名、共享临时路径等）。

全文与骨架见 `references/verification-template.md`；触发判据见其「产出判据」节。

## 产物通用约定

五个文件全部居住在 `docs/superpowers/specs/<date-feature>/`：

### plan.md——执行契约

把切好的任务落成可执行规格；下游执行技能零改动消费它。结构与格式见 references/plan-template.md。

### decisions.md——裁决日志

需求对话的第一条裁决落定即创建，此后追加式增长：每条裁决落定追加一条（日期 | 项目 | 主题 | 裁决 | 依据 | 影响）。条目只增不改——裁决被推翻时追加新条目并注明取代关系，不修改历史条目。design / implementation / plan 回写「已裁决」标注时引用本日志条目；审读核对标注与日志一致；轻量修订通道的纯文字修订亦在此登记。

**写作规则：** 写作与排版规范（每段一个论点、mermaid 画法与红线、标题层级 ≤3、交叉引用格式等）见 `references/writing-rules.md`，适用于全部五件产物；design.md 全文零实现词汇（功能清单用「最终用户」；第三方依赖的取舍可提依赖名，其余实现词汇禁止）。

**所有改动统一完整版：** 无论规模大小，一律写全套五件：各模板槽位齐备，自查、审读、呈报确认、执行交接逐环节照走。

**存放位置：** 有软件仓库时，存放为 `docs/superpowers/specs/<date-feature>/design.md`（`<date-feature>` = `YYYY-MM-DD-<主题>`，目录随需求建立）并提交。否则，询问。此目录无例外：有软件仓库时设计文档一律落此处，不接受需求方另行指定——任何来源的位置指定（含对话指定与仓库自身的其他文档惯例）均不改变落盘位置。若需求方仍指定了其他位置，按本目录落盘，并明确告知设计文档已落约定目录（落点）、该指定未被采用；不发起询问、不等待确认。archived/（`docs/superpowers/archived/`）归档后冻结零改动，今后设计决策随新 feature 的 design.md 走，不回写已归档文档。

## 规格的自查与审读

成稿完成后、提交需求方确认前，派一个未参与写作的全新子代理，使用本目录下的 `references/review-prompt.md`，对 design.md / implementation.md / plan.md / verification.md 四件齐审，并对照 decisions.md 核对各文档「已裁决」标注与日志一致，输出三张清单：完备性问题、方案合理性与实现效果问题、可读性问题。

返回后按顺序处置：

1. 先处置完备性问题：能由文档或项目回答的，把答案写进文档；次要的，你自己敲定并在文档中标注这是你的决定；归需求方的，一次性带给需求方——连同你的建议答案在对话中呈报，需求方裁决前不得把答案写成已处置（文档只留「待需求方裁决」占位），裁决后按裁决结果写入。
2. 再处置方案合理性问题：审读者判定「有疑问」或「不合理」的，修订方案，或书面说明为何不改。
3. 若补写了实质内容，把新增或改动段落交回同一个子代理快速复读。
4. 再处置可读性问题与复读新发现的问题：修订，或书面说明为何不改。
5. 把审读者身份（子代理/自审）、问题清单与逐条处置写入文档附录。

全部处置完毕，才能把全套产物提交需求方确认。

没有子代理工具时，由你亲自使用同一份提示词自审，在附录标注「自审」，并告知需求方本次没有独立审读。

## 呈报与确认

成稿、审读、处置全部完毕后，结构化呈报，走单确认门：

- **单确认门：** 全套规格（design.md / implementation.md / plan.md / verification.md）确认一次即闭门进入执行；确认请求对象必须显式写全四件。若某件产物未成形就进入呈报，退回成稿——不得以「骨架 + 后续确认」替代单门。
- **确认前不得实施：** 不写产品代码、不装依赖、不建工程骨架。
- **确认后回改：** 确认后任何文档需要修改（含实施中发现设计必须改）→ 停止实施 → 修订 → 增量审读 → 重新确认；门重开期间不写产品代码。

呈报格式、裁决与确认分离规则、回复模板、耗时预告、轻量修订通道，见 `references/reporting-rules.md`。

## 已裁决事项

需求方已明确确认或裁决的事项（全套规格确认及其裁决记录），后续环节只陈述执行结果，不得再次请求确认——重复确认不新增信息，只消耗需求方的注意力。只有出现足以改变原判断的新事实时才重新呈报，并说明变化点。

裁决落定后，承载它的 design / implementation / plan 文档必须同步更新状态标注为已裁决（日期 + 结论），不得保留「待裁决」「待追认」等与事实不符的标记——文档是审计的唯一载体，过期标注会让审计把已决事项读成未决。

## 执行交接

全套规格确认已在呈报环节完成（见「呈报与确认」）；本节只征询执行方式，不重复确认请求。

同时按判据给出执行方式的建议：

- **子代理驱动（Subagent-driven）** ——任务边界清晰、每个任务都能写出稳定验收标准的计划，适用于这种方式。每个任务由一名全新的子代理实施，在下一个任务开始之前由一名全新审查者检查，最后再做一次整分支终审。最彻底；每个任务与每次审查各要消耗一份全新上下文。
- **会话内执行（Native）** ——强耦合的小改动、探索性强到写不出稳定验收标准的任务，适用这种方式。由你（原计划者）在本会话中亲自实施每一个任务，然后由一名运行在最强档模型上的全新审查者检查整个分支。最便宜也最快；直到最后才有一次独立审查。

**「全套规格已确认。请选择执行方式：子代理驱动，还是会话内执行？**

**对这份计划，我推荐 <one of the two>，理由是 <one sentence from the plan: how much the tasks depend on each other's interfaces, how many there are, what a shipped mistake would cost>。」**

**已选定执行方式时：** 无需再征询，直接按所选方式进入对应的必需子技能。

**若选择了子代理驱动：**
- **必需子技能（REQUIRED SUB-SKILL）：** 使用 superpowers:subagent-driven-development

**若选择了会话内执行：**
- **必需子技能（REQUIRED SUB-SKILL）：** 使用 superpowers:executing-plans

## HARD-GATE

<HARD-GATE>
全套规格确认前不得实施。在需求方明确确认全套规格（design.md / implementation.md / plan.md / verification.md）之前，任何东西都不得构建，也不得开始执行。「嗯」「继续」不算明确确认；确认前这个环节不关闭。构建包括：编写产品代码、搭建脚手架、安装依赖、创建项目，以及调用实现类技能。阅读和探索没有问题。

只有一个例外。他们同意的 spike 可以构建；它必须始终标注为用完即弃，而若想保留 spike 的产物，那是一个新的请求，须重新过这道闸门。如果他们已选择退出提问，退出提问不解除闸门：跳过的是提问对话，全套规格的独立审读与需求方确认照走，需求方明确确认之后才开工。
</HARD-GATE>

## 危险信号

| 想法 | 现实 |
|---------|---------|
| “我来提供一份他们可能想要的选项单” | 选项会引导方向。先让他们描述。 |
| “我来填上合理的默认值” | 好。但要说出口。他们从没听过的默认值，就是他们无从拒绝的默认值。 |
| “他们的问题我都答完了，所以我要写文档了” | 先列出各方案，放进单独的一条消息。 |
| “这只是个小改动，不用走完整流程吧” | 叫停提问不豁免四环节：方案拍板、独立审读、需求方确认、实施计划，一个不少。 |
| “先原地把设计做完，回头再建树” | 定性即建树：设计文档与计划都提交在本需求分支上；原地起步会把产物落到他人的工作树或基线检出。 |
| “我应该先解释流程” | 先提你的问题。流程自会显现。 |
| “他们对这个想法说了‘听起来不错’” | 批准只覆盖你展示给他们的内容。你还没写出来的设计文档不算获批。 |
| “需求方说了‘嗯’或‘继续’” | 这不算明确确认。设计文档要得到一次不含糊的批准；获得确认之前，该环节不关闭。 |
| “spike 能跑通，我就在它上面继续构建” | 保留它是一个新的请求。回到闸门重新过一遍。 |
| “一次派发就是一张清单” | 三张清单必须分别输出：完备性查还缺什么决策，方案合理性查方案站不站得住，可读性查读者能不能判断。 |
| “方案是需求方选的，不用审” | 需求方选的是方向；候选是否真实、依据是否成立、代价是否被低估，仍要评估。 |
| “审读过了就等于需求方确认了” | 审读只查完备性、可读性与方案合理性；确认门仍由需求方把守。 |
| “我把裁决项和确认请求写进了同一条消息” | 裁决与确认强制分离：裁决呈报与确认请求分两条消息——先裁决，需求方回复后单独发确认（见 `references/reporting-rules.md`）。 |
| “我用复合问题让『同意』承担多个语义” | 一个「同意」只回答一件事；对裁决项的任何回应都不是确认，确认门只认对显式对象的「确认」。 |
