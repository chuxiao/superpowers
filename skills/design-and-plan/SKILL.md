# 设计与计划

你非常擅长构建。你构建的是你以为需求方想要的东西——而「我做的就是他们想要的」这份信念，实际上往往没有它给人的感觉那么站得住。这项技能的用途，就是在任何软件开发产物被构建出来之前，弄清他们真正想要什么、以及为什么。

人们往往还没想清楚自己要什么。好的提问能帮他们想透。当你理解了缘由，面对那一百个他们从未提起的决定，你就会做出他们本来会做的选择。

## 首先：你实际知道什么？

收到新问题时先分类：分类判据见 superpowers:using-superpowers 的「流程闸门与定性」，结论用一句话宣布（类型 + 依据）。新 feature 或新设计 → 走本技能完整流程（建新 `docs/superpowers/specs/<date-feature>/` 五件套）；缺陷修复 → bugfix 路径（修复分支修复 + 合并前过收官把关与集成验证门槛，不建需求目录）。小 feature 不得说成 bugfix 来绕开五件套；设计期发现实为缺陷修复 → 重定性为 bugfix，转修复链，工作树保留改名。

回复之前，先问自己：对于他们想要什么、以及为什么，我到底知道些什么？

- **相关信息都在需求描述里**（“把图标改成矢车菊蓝”）。这是一个快速、清晰的任务。需求完备时，跳过的是对话，不是流程：直接进入「列出各方案」与四件套成稿，方案拍板、成稿、审读、呈报确认、执行交接逐环节照走，然后构建，并说明你做了什么。
- **关键信息缺失。** 开启对话。

## 实施顺序

开始实现之前，你必须按顺序完成：

1. **需求对话**：复述与提问交替进行（见「对话」「复述」）；视觉伴侣在第一次复述 UI 相关内容前即提议，不等到聊完。
2. **四件套成稿**：design.md / implementation.md / plan.md / verification.md 全部成形（见「四件套成稿」）；decisions.md 随每条对话裁决落定追加。
3. **自查**：把统一审读的核对项前置为作者自查（见「计划与任务原则」的自审清单）。
4. **排版脚本**：运行 `bash scripts/check-tables.sh <四件路径>`、`bash scripts/check-mermaid.sh <四件路径>` 与 `bash scripts/check-doc-structure.sh <四件路径>`（design.md / implementation.md / plan.md / verification.md 依次传入），按输出修复表格列错位、mermaid 红线违规与结构槽位缺损（无该脚本环境时，由审读提示词中的排版核对兜底）。
5. **一个审读子代理审全套**：四件齐审 + decisions.md 标注一致核对（见「独立审读」）。
6. **批量修订**：按审读返回的三张清单批量裁决，之后整章重写（Write 替代几十个零散 Edit）。
7. **收敛复读**：补写了实质内容的段落交回同一个子代理复读，只核对修订是否忠实落实（见「独立审读」）。
8. **结构化呈报**：裁决项独立成段，全套规格确认请求独立成段（见「呈报与确认」）。
9. **确认后执行交接**：需求方确认全套规格后，按判据给出执行方式建议（见「执行交接」）。

每一步的问题在当前步解决：设计未定就不写计划。全套产物被修订时，只有影响范围、功能或决策的修订才触发重审与重新确认；纯文字修订走轻量修订通道（见 `references/reporting-rules.md`）；判断有疑义时按影响处理。

有一件事不算实现：他们点头同意的 spike（快速试制，见 `references/dialogue-discipline.md` 的「用 spike 摸底」）。

## 四件套成稿

对话收敛后，把理解落成五个文件，全部居住在 `docs/superpowers/specs/<date-feature>/`：

**design.md——设计文档。** 全部后续产物的依据：做什么、为什么、明确不做、关键决策与约束；文首形态声明 + 条件章（界面规格、数据字典）。完整模板、逐章内容要求与措辞纪律见 `references/design-doc-template.md`；写 design.md 前先读它。

**implementation.md——实现设计。** 数据与接口的唯一权威定义；plan.md 只引用它的章节号，不复制签名。写它之前先读 `references/implementation-rules.md`——实现设计的流程与规则（架构设计原则 / 实证纪律 / 成文纪律）；结构与格式见 `references/implementation-template.md`。

**plan.md——实施工作单。** 唯一执行依据；下游执行技能零改动消费它。计划与任务原则见下方「计划与任务原则」节；结构与格式见 `references/plan-template.md`。

**verification.md——验证方案。** 需求级验证方案：分层自动化策略、可观测缝清单、场景数据条目。计划存在跨任务组装点或触及外部接口时产出（触发判据见 `references/plan-template.md`「验证方案文件」段）；模板见 `references/verification-template.md`。纯单模块无接口时不产出该文件，plan.md 骨架不变。

**decisions.md——裁决日志。** 追加式：每条对话裁决落定即追加一条（日期 | 项目 | 主题 | 裁决 | 依据 | 影响）。design / implementation / plan 回写「已裁决」标注时引用本日志条目；审读核对文档标注与日志一致。

**写作规则：** 写作与排版规范（每段一个论点、mermaid 画法与红线、标题层级 ≤3、交叉引用格式等）见 `references/writing-rules.md`，适用于全部五件产物；design.md 全文零实现词汇（功能清单用「最终用户」；第三方依赖的取舍可提依赖名，其余实现词汇禁止）。

**所有改动统一完整版：** 无论规模大小，一律写全套五件：各模板槽位齐备，自查、审读、呈报确认、执行交接逐环节照走。

**存放位置：** 有软件仓库时，存放为 `docs/superpowers/specs/<date-feature>/design.md`（`<date-feature>` = `YYYY-MM-DD-<主题>`，目录随需求建立）并提交。否则，询问。此目录无例外：有软件仓库时设计文档一律落此处，不接受需求方另行指定——任何来源的位置指定（含对话指定与仓库自身的其他文档惯例）均不改变落盘位置。若需求方仍指定了其他位置，按本目录落盘，并明确告知设计文档已落约定目录（落点）、该指定未被采用；不发起询问、不等待确认。archived/（`docs/superpowers/archived/`）归档后冻结零改动，今后设计决策随新 feature 的 design.md 走，不回写已归档文档。

## 计划与任务原则

计划是实施前的决策记录；实施后的结论由提交信息承载，计划本身不回填。写 plan.md 前，任务如何分解、每个任务写到什么程度，按本节原则执行。

### 范围检查

设计文档覆盖多个相互独立的子系统时，应拆成多份独立的计划——每个子系统一份；每份计划都应当能独立产出可运行、可测试的软件。

### 任务规模划定

任务是携带着自身测试循环、且值得由一名全新审查者单独把关的最小单元。划定任务边界时：哪项任务产出的交付物需要准备、配置、脚手架和文档类的工作，就把这些工作并入该任务；只有当审查者可能实质性地否决某个任务、却同时批准其相邻任务时，才在该处拆分任务边界。每个任务都以一个可独立测试的交付物收尾。

### 任务详细度

任务写到「边界条件 + 验收标准」为止。TDD 的红绿循环——写失败测试、运行确认失败、实现最小代码、运行确认通过、提交——由执行者按 superpowers:test-driven-development 从验收标准自行展开，**不在计划中预写**。

预写测试代码与实现步骤，等于把代码誊进计划：一份比它所描述的代码还长的计划是誊抄，不是计划。

### 一个任务包含什么

当实施者依据一个任务只能写出一种合理的实现时，这个任务就算写到位了。这就是全部的要求：无歧义，而非完备。

- **Files / Interfaces：** 决策的落点——路径、章节号与名字，逐字写；签名留在 implementation.md，不复制。
- **边界条件：** 触发条件与失败行为，写成可判真伪的命题。禁止「适当处理」「必要时」「等等」这类不可判真的措辞；重要行为给 ❌/✅ 对照（❌「超长输出会被妥善处理」/ ✅「超过 30000 字符截断至 30000 并追加截断说明」）。任务触及既有代码时，边界条件写明「不得改变的既有行为」清单——它是执行者写特征测试的锁定来源；锁定范围的知识在你（计划者）手里，不写，执行者只能自己推断。
- **验收标准：** 测试要证明什么，不是测试代码本身。只有当验收标准推不出测试的写法（算法不由行为决定）时，才附一段测试思路说明。
- **对另一个任务的引用：** 被引用任务的 Interfaces 块写明要用什么；计划不重复那个任务的代码。

计划是实施者无法独自做出的那批决定的集合。什么都不决定的行（"TBD"、"处理边界情况"、"加上恰当的校验"、没有任何任务加以定义的接口或数据）是缺口；预写的测试代码与函数体（凡是验收标准与签名已能确定的）是誊抄。这两种失败自审都要抓出来。

**自审：** 写完整份 plan.md 后，用新视角重读设计文档并对照检查计划——13 项清单（设计文档覆盖、单元五问、类型一致性、边界条件承接、比例、行为可判真伪与锚定、骨架完整与写作要求、实现效果、接口可测性、验证方案专项、形态声明与裁剪推导核对、任务依赖图与实施顺序核对、跨文件引用一致性核对）全文见 `references/plan-self-review.md`——自审之前先读它。发现问题就原地修；发现设计文档的某条需求没有对应任务，就补上那个任务。自查越严，首轮审读越薄，总时间越短；核对项全文以 `references/review-prompt.md` 清单 A 的核对项段为准。

## 独立审读

自查与排版脚本通过后、提交需求方确认前，派一个未参与写作的全新子代理，使用本目录下的 `references/review-prompt.md`，对 design.md / implementation.md / plan.md / verification.md 四件齐审，并对照 decisions.md 核对各文档「已裁决」标注与日志一致，输出三张清单：完备性问题、方案合理性与实现效果问题、可读性问题。

返回后按顺序处置：

1. 先处置完备性问题：能由文档或项目回答的，把答案写进文档；次要的，你自己敲定并在文档中标注这是你的决定；归需求方的，一次性带给需求方——连同你的建议答案在对话中呈报，需求方裁决前不得把答案写成已处置（文档只留「待需求方裁决」占位），裁决后按裁决结果写入。
2. 再处置方案合理性问题：审读者判定「有疑问」或「不合理」的，修订方案，或书面说明为何不改。
3. 若补写了实质内容，把新增或改动段落交回同一个子代理快速复读。
4. 再处置可读性问题与复读新发现的问题：修订，或书面说明为何不改。
5. 把审读者身份（子代理/自审）、问题清单与逐条处置写入文档附录。

全部处置完毕，才能把全套产物提交需求方确认。

没有子代理工具时，由你亲自使用同一份提示词自审，在附录标注「自审」，并告知需求方本次没有独立审读。

## 呈报与确认

成稿、审读、处置全部完毕后，结构化呈报，走单确认门：

- **单确认门：** 全套规格（design.md / implementation.md / plan.md / verification.md）确认一次即闭门进入执行；确认请求对象必须显式写全四件。若某件产物未成形就进入呈报，退回成稿——不得以「骨架 + 后续确认」替代单门。
- **确认前不得实施：** 不写产品代码、不装依赖、不建工程骨架。
- **确认后回改：** 确认后任何文档需要修改（含实施中发现设计必须改）→ 停止实施 → 修订 → 增量审读 → 重新确认；门重开期间不写产品代码。

呈报格式、裁决与确认分离规则、回复模板、耗时预告、轻量修订通道，见 `references/reporting-rules.md`。

## 已裁决事项

需求方已明确确认或裁决的事项（全套规格确认及其裁决记录），后续环节只陈述执行结果，不得再次请求确认——重复确认不新增信息，只消耗需求方的注意力。只有出现足以改变原判断的新事实时才重新呈报，并说明变化点。

裁决落定后，承载它的 design / implementation / plan 文档必须同步更新状态标注为已裁决（日期 + 结论），不得保留「待裁决」「待追认」等与事实不符的标记——文档是审计的唯一载体，过期标注会让审计把已决事项读成未决。

## 执行交接

全套规格确认已在呈报环节完成（见「呈报与确认」）；本节只征询执行方式，不重复确认请求。

同时按判据给出执行方式的建议：

- **子代理驱动（Subagent-driven）** ——任务边界清晰、每个任务都能写出稳定验收标准的计划，适用于这种方式。每个任务由一名全新的子代理实施，在下一个任务开始之前由一名全新审查者检查，最后再做一次整分支终审。最彻底；每个任务与每次审查各要消耗一份全新上下文。
- **会话内执行（Native）** ——强耦合的小改动、探索性强到写不出稳定验收标准的任务，适用这种方式。由你（原计划者）在本会话中亲自实施每一个任务，然后由一名运行在最强档模型上的全新审查者检查整个分支。最便宜也最快；直到最后才有一次独立审查。

**「全套规格已确认。请选择执行方式：子代理驱动，还是会话内执行？**

**对这份计划，我推荐 <one of the two>，理由是 <one sentence from the plan: how much the tasks depend on each other's interfaces, how many there are, what a shipped mistake would cost>。」**

**已选定执行方式时：** 无需再征询，直接按所选方式进入对应的必需子技能。

**若选择了子代理驱动：**
- **必需子技能（REQUIRED SUB-SKILL）：** 使用 superpowers:subagent-driven-development

**若选择了会话内执行：**
- **必需子技能（REQUIRED SUB-SKILL）：** 使用 superpowers:executing-plans

## HARD-GATE

<HARD-GATE>
全套规格确认前不得实施。在需求方明确确认全套规格（design.md / implementation.md / plan.md / verification.md）之前，任何东西都不得构建，也不得开始执行。「嗯」「继续」不算明确确认；确认前这个环节不关闭。构建包括：编写产品代码、搭建脚手架、安装依赖、创建项目，以及调用实现类技能。阅读和探索没有问题。

只有一个例外。他们同意的 spike 可以构建；它必须始终标注为用完即弃，而若想保留 spike 的产物，那是一个新的请求，须重新过这道闸门。如果他们已选择退出提问，退出提问不解除闸门：跳过的是提问对话，全套规格的独立审读与需求方确认照走，需求方明确确认之后才开工。
</HARD-GATE>

## 危险信号

| 想法 | 现实 |
|---------|---------|
| “我来提供一份他们可能想要的选项单” | 选项会引导方向。先让他们描述。 |
| “我来填上合理的默认值” | 好。但要说出口。他们从没听过的默认值，就是他们无从拒绝的默认值。 |
| “他们的问题我都答完了，所以我要写文档了” | 先列出各方案，放进单独的一条消息。 |
| “这只是个小改动，不用走完整流程吧” | 叫停提问不豁免四环节：方案拍板、独立审读、需求方确认、实施计划，一个不少。 |
| “先原地把设计做完，回头再建树” | 定性即建树：设计文档与计划都提交在本需求分支上；原地起步会把产物落到他人的工作树或基线检出。 |
| “我应该先解释流程” | 先提你的问题。流程自会显现。 |
| “他们对这个想法说了‘听起来不错’” | 批准只覆盖你展示给他们的内容。你还没写出来的设计文档不算获批。 |
| “需求方说了‘嗯’或‘继续’” | 这不算明确确认。设计文档要得到一次不含糊的批准；获得确认之前，该环节不关闭。 |
| “spike 能跑通，我就在它上面继续构建” | 保留它是一个新的请求。回到闸门重新过一遍。 |
| “一次派发就是一张清单” | 三张清单必须分别输出：完备性查还缺什么决策，方案合理性查方案站不站得住，可读性查读者能不能判断。 |
| “方案是需求方选的，不用审” | 需求方选的是方向；候选是否真实、依据是否成立、代价是否被低估，仍要评估。 |
| “审读过了就等于需求方确认了” | 审读只查完备性、可读性与方案合理性；确认门仍由需求方把守。 |
| “我把裁决项和确认请求写进了同一条消息” | 裁决与确认强制分离：裁决项独立成段，确认请求独立成段（见 `references/reporting-rules.md`）。 |
| “我用复合问题让『同意』承担多个语义” | 一个「同意」只回答一件事；对裁决项的任何回应都不是确认，确认门只认对显式对象的「确认」。 |
