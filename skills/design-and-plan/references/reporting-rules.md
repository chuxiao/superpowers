# 呈报与确认纪律

> 读者：设计撰写者（呈报前逐条对照）与执行技能（解读确认语义时）。本文件是硬规则载体：逐条执行，无酌情空间。流程与门在 SKILL.md「呈报与确认」；呈报格式、分离规则、回复模板、耗时预告、轻量修订通道的规则全文在这里。
>
> 共十条：第 1–9 条与方案呈报纪律九条一一对应；第 10 条处理判定不产出的条件产物，使单门不被字面卡死。

## 1. 单确认门

全套规格文档（design.md / implementation.md / plan.md / verification.md）确认一次即闭门进入执行；确认请求对象必须显式写全四件。**确认前不得实施**（不写产品代码、不装依赖、不建工程骨架）。若某件产物未成形就进入呈报，退回成稿——不得以「骨架 + 后续确认」替代单门；经判据判定不产出的条件产物按第 10 条标注成形。

## 2. 裁决与确认分离（分离规则）

**裁决呈报与确认请求是两条独立消息：先发裁决呈报（只含裁决项），待需求方回复裁决后，再单独发确认请求（只含确认请求）。**

- 裁决消息只含裁决项（第 3 条格式），不含确认请求；需求方回复裁决后，确认请求才发出——裁决的回应与确认请求在时间上不毗邻，彻底杜绝混淆。
- ❌ 一条消息里先列裁决项、再接确认请求（即使分段隔开）——两个语义同屏，确认被稀释。
- ✅ 消息一：【待裁决】N 项 + 裁决回复格式；需求方回复后，消息二：【确认请求】对象：… + 确认回复格式。

## 3. 裁决呈报格式

每项固定三段：**现状 / 建议 / 影响**。裁决项可一次列多项，但只回答裁决——裁决的回应不产生确认语义（见第 5 条）。实际形态见「结构化呈报示例」。

## 4. 回复模板

裁决消息末尾给出裁决回复格式（逐字）；确认消息末尾给出确认回复格式（逐字）：

```
裁决回复格式：
- 裁决：1–N 按建议，或逐项说明你的决定
```

```
确认回复格式：
- 确认：确认 / 不确认 + 对象（全套规格文档）
```

## 5. 解读规则（写给执行技能的自己）

**需求方对裁决项的任何回应（含「同意」「按建议」）不得被解读为对任何文档的确认；确认门只在需求方对显式对象回复确认时关闭。**

- 「嗯」「继续」「同意」「按建议」「听起来不错」都不关闭门；门只认对显式写全对象的「确认」。HARD-GATE 在门关闭前持续生效。

## 6. 呈报审查负担缓解

确认请求段附两样，把需求方从通读全套中解放出来：

- **决策速览表：** 决策 / 结论 / 出处章节（出处写 design.md、implementation.md 的章节号）。
- **建议重点抽查点：** ≤3 处，按审读高危项挑。

## 7. 确认后回改

确认后任何文档需要修改（含实施中发现设计必须改）→ 停止实施 → 修订 → 增量审读 → 重新确认；门重开期间不写产品代码。已实施部分的处理：返工还是回滚由需求方决定；已合入 main 的用新提交修正，不改写历史。

## 8. 耗时预告

呈报附下一阶段预计耗时：对话轮数 + 机器时间量级 + 需人工参与点数量（落点见「结构化呈报示例」末行括注）。

## 9. 轻量修订通道

**纯文字修订（不改行为/范围/决策的引用修正、措辞）允许直接改 + 在 decisions.md 或附录登记，门不重开；影响行为/范围/决策的任何改动必须重走确认。**

- ❌ 修订 §3 错误表中错误码的取值——改行为，必须重走确认。
- ✅ 修正 §2 指向 design.md §4 的章节号笔误、调整措辞——登记后直接生效，门不重开。
- 拿不准属于哪类时按影响处理：走重确认。

## 10. 条件产出的标注即成形

确认对象四件中，经集成面判据判定不产出的一件（如纯单模块项目不产出 verification.md），在确认请求中显式标注「不适用（依据：无集成面推导）」即视为成形，不阻塞单门；标注须引用其不产出的推导依据（verification.md 的推导链权威见 verification-template.md「产出判据」段：改动面清单 → 无组装点、无外部接口、无运行边界）。

- 与第 1 条合读：「显式写全四件」仍成立——四件的名字全部出现在确认请求中，其中判定不产出的一件以标注成形，其余件必须真实成形。本条是第 1 条「未成形退回成稿」的唯一例外，且仅覆盖经判据判定不产出的那一件。
- ✅ `【确认请求】对象：design.md / implementation.md / plan.md / verification.md——verification.md 不适用（依据：无集成面推导，见 plan.md 推导链）。`
- ❌ 直接只列三件、不提 verification.md——第 1 条「显式写全四件」被字面违反，单门对象不完整。

## 结构化呈报示例

第 2、3、4、8 条的实际形态：消息一呈报裁决，需求方回复后消息二呈报确认。示例仅示范两段结构；确认对象按第 1 条写全四件；决策速览表与抽查点的完整形态见第 6 条（随消息二）：

消息一（裁决呈报）：
```markdown
【待裁决】2 项：
1. 配置损坏行为——现状：未定义；建议：弹说明窗（含路径与解决建议）后退出，
   不静默进首跑；影响：进程装配一处。
2. 临时目录机制——现状：无；建议：环境变量 CC_MODEL_CONFIG_DIR；
   影响：首跑验证场景可隔离。
回复格式：
- 裁决：1–2 按建议，或逐项说明
```

需求方回复裁决后，消息二（确认请求）：
```markdown
【确认请求】对象：全套规格（design.md、implementation.md、plan.md、verification.md；本项目无集成面，verification.md 不适用——依据见其推导）。
请明确回复「确认」或「不确认 + 修改点」。
- 决策速览与重点抽查点见第 6 条形态（随本消息附上）。
确认回复格式：
- 确认：确认 / 不确认 + 对象
（预计耗时：确认后实施阶段约 N 轮机器时间 + M 次人工观察点）
```

## decisions.md 条目格式

decisions.md 是裁决日志，落 `docs/superpowers/specs/<date-feature>/decisions.md`，追加式、单一落点。每条对话裁决落定即追加一条，条目格式：

```markdown
### 2026-11-05 | <项目> | 配置损坏的进程行为
裁决：弹说明窗（含路径与解决建议）后退出，绝不静默进入首跑
依据：避免无提示丢失全部模型档案（对话裁决）
影响：Main/AppDelegate 装配；需补验证场景
```

三条规则：

1. **追加式：** 每个对话裁决落定即追加一条；既有条目不回改——日志是审计载体。
2. **回写引用本日志：** design / implementation / plan 回写「已裁决（日期 + 结论）」标注时，引用本日志对应条目；轻量修订通道（第 9 条）的登记也落在本日志或文档附录。
3. **审读核对标注一致：** 统一审读对照本日志核对各文档「已裁决」标注——文档标注与日志不一致即问题。
