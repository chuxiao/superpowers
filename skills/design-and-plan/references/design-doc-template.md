# 设计文档模板

> 读者假设：懂软件工程，不熟悉产生本文档的对话；不需要了解项目内部实现。
>
> 本文档回答：做什么、不做什么、为什么这样取舍、成本量级与主要风险。实现细节留给实现设计与计划（implementation.md / plan.md）。

## 章节骨架

产出文档标题 `# <项目> 设计文档`，文首为上方读者声明引块，另固定一行 `实施前决策记录 + 日期：YYYY-MM-DD`；其后按序成文：

0 形态声明 / 五章（1 背景与目标 / 2 功能清单 / 3 明确不做 / 4 关键决策记录〔含「留给构建者的部分」〕/ 5 关键约束与可行性风险）/ 条件章：界面规格〔形态含 UI 必设〕、数据字典〔涉及持久化或外部格式必设〕/ 文末：独立审读处置记录附录

- 条件章设与不设由 §0 裁剪推导决定；不设时整章省略，五章章号不变——章号是引用锚。
- 「留给构建者的部分」是第 4 章的小节，不独立成章。

## 0. 形态声明

文首固定写两行：

```
产物形态：纯 API / Web 应用 / 桌面 App / 移动 App / CLI / 库或 SDK / 混合
章节裁剪推导：条件章哪些适用、不适用的原因——无推导不合法
```

- 产物形态从枚举中选，混合形态写明组成。
- 章节裁剪推导逐条件章写：适用 / 不适用，各附原因。示例（纯 API 形态）：「界面规格：不设——无 UI；用户可见面为响应 / 输出，其契约完整性由 implementation.md 的接口设计章保障」。

## 五章

### 1. 背景与目标

- 解决什么问题：写出具体场景与失效方式，不写「提升体验」这类无法判断的结论。
- 给谁用：写明最终用户是谁。
- 成功判断标准：写成可观察的行为，例如「需求方只读本文档就能确认范围」，不写「文档清晰易懂」。

### 2. 功能清单

逐项写功能卡片，六字段顺序固定；每张卡片合起来必须能回答「输入什么 → 最终用户看到什么」：

1. **定位：** 功能名 + 一句话职责。
2. **触发与输入：** 触发方式逐个列出（链路接力 / 单独调用 / 显式触发等），输入清单。
3. **执行要点：** 分点写，每点一个可判真伪的命题——禁止把多步流程写成一整段。
4. **出口表：** 功能有多个出口（≥2 种结局）时，三列表格——出口 / 条件 / 去向；单一出口一行文字即可。
5. **流程图：** 执行含决策分支、裁决循环或多出口时配 mermaid 图，先图后文（画法见 `references/writing-rules.md`）；一张图一个主题，节点文本遵守 flowcharts 的预算规则。
6. **本次不做：** 范围与指向（§3 第 N 条）。

用「最终用户」指被设计产品的使用者；「需求方」只指提出需求、做确认的人。

### 3. 明确不做

- 逐项列出不做的事，每项附因果理由：因为 X，所以不做 Y。
- 不接受裸的「暂不做」「后续再说」。
- 本清单在确认后冻结；实施中不得回写。范围要变，回到设计确认门重新确认。

### 4. 关键决策记录

第 4 章开头放决策速览表，一行一个决策，供只查结论的读者使用；正文逐个决策展开：

| 决策 | 一句话结论 | 拍板状态 | 影响功能项 |
|------|-----------|---------|-----------|

每个决策写四段：

1. 候选方案：真正考虑过的两三种做法。
2. 选了哪个。
3. 依据：为什么选它，为什么排除其他。
4. 代价或风险，以及成本量级与主要成本来源。

写完自检方案合理性：候选方案是否真实、是否漏掉明显更简单的做法、取舍依据是否成立、代价与风险是否被低估、方案能否解决第 1 章的问题。审读者会按这五点评估。

**留给构建者的部分**——这一节属于第 4 章，不单独成章；它记录的是委托决定，不是约束或风险。

- 逐项写：交给执行者决定什么、边界在哪、为什么交给执行者。

### 5. 关键约束与可行性风险

- 只列影响「做不做」的事实：依赖缺失、平台限制、时间或成本上限、兼容性要求。
- 不展开实现；不承接委托给执行者的决定。

## 条件章：界面规格

**条件：产物形态含 UI 时必设**；不设须在 §0 裁剪推导中写明对应保障。

每个界面一节：**冻结的效果图**（相对路径引用 `mockups/` 下落盘文件）+ 两级标注：

- **约束级**：布局结构、字段清单、状态清单（空态/错误态/特殊态逐个列出）——必须实现；
- **示意级**：间距、配色、字号——留给实现。

**视觉稿定稿冻结机制**：需求方每确认一块视觉稿，立即将 HTML/截图落盘到 `specs/<date-feature>/mockups/` 并随仓库提交（截图可用 `chrome --headless --screenshot` 等无头方式生成）；design.md 只允许引用已冻结文件，禁止引用会话临时目录——杜绝「无锚引用」。

纯 API 等无 UI 形态不设本章，但须在裁剪推导中写明「响应/输出即用户可见面」的对应保障（如错误码全集归入 implementation.md 的接口设计章）。

## 条件章：数据字典

**条件：产物涉及持久化或外部格式时必设**；不设须在 §0 裁剪推导中写明理由。

- 记录**产品级**数据形态（用户可感知、可手改的）：实体、字段、语义、外部格式、权限、手改语义。
- 与 implementation.md「数据与状态设计」的分工：design 管「是什么」（行为承诺），implementation 管「怎么存」（物理实现）。示例：design 数据字典写「模型 = 显示名 + 接入点 + 密钥 + 档位映射，配置文件用户可手改」；implementation 数据设计写「config.json 的完整 schema、0600 权限、读写原子性」。

## 五章之外

必须包含以下固定块，不计入五章，也不计入条件章；内容章只允许五章与两个条件章（按 §0 裁剪推导取舍），不得新增清单之外的章：

- **文首**：读者假设与术语表。
- **文首**：`实施前决策记录 + 日期：YYYY-MM-DD`。
- **文末**：独立审读处置记录附录，写明审读者身份（子代理/自审）、问题清单与逐条处置。初稿可写「待审读」，确认前必须填完。

## 写作要求

写作与排版规范见 `references/writing-rules.md`（适用于全部五件产物）。本文件专属：

1. 禁止无锚引用——凡「已确认 / 已验证」必须能指到仓库内文件或对话裁决记录（decisions.md），否则删掉断言，或先落盘再引用。

全文零实现词汇：不出现文件名、函数名、模块路径、目录结构。第三方依赖的取舍决策可提依赖名；其余实现词汇一律禁止。冻结效果图的 `mockups/` 相对路径引用不在此限（见「条件章：界面规格」）。
