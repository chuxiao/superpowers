# 计划模板

> 读者假设：需求方（审查全套规格）、工程师（读实现设计）、执行子代理（读本工作单）；懂软件工程，不熟悉产生本项目的对话。
>
> 本文档回答：改哪些文件、每个功能单元怎么改、边界在哪、有什么实施风险。取舍论证与结构依据见 implementation.md；本文件是唯一执行依据。计划只适用于软件开发类工作（含代码与项目文档）。

**计划是实施者无法独自做出的那批决定的集合**，为一名没有见过这个代码库、也没有见过这份设计文档的工程师撰写。假设他们一旦知道了确切的接口、确切的边界条件与确切的验收标准，就能用项目的语言写出地道的代码；并且凡是计划留出开放选择的地方，他们都会做出合理的选择。他们无法知道的是你决定了什么：哪些文件、哪些名称与签名、设计文档中的哪些取值、哪些边界条件与验收标准证明每个任务。把这些写进文档。把整份计划拆成任务交给他们。DRY。YAGNI。TDD。频繁提交。

本文档骨架固定：文首（指针行 + 元数据）→ 任务依赖图与实施顺序 → 任务规格 → 执行交接 → 独立审读处置记录附录。

## 文首

文档开头固定写一行指针 + 元数据：

- **指针行（逐字）：** `实现设计见同目录 implementation.md；本文件是唯一执行依据。`
- **目标：** 一两句话，说明这个能力给需求方带来什么——拿到产出后能看到什么、能做什么。不是技术摘要。
- **架构：** 两三句话说明采用的方案。
- **技术栈：** 关键技术或库。
- **设计文档（Spec）：** 设计文档路径。计划以设计文档为立论依据。
- **实施前决策记录 + 日期：** `YYYY-MM-DD`。

## 任务依赖图与实施顺序

文首固定写（元数据之后、首个任务之前）：

- **任务依赖图：** mermaid 图标出任务间依赖关系与关键路径，先图后文（画法见 `references/writing-rules.md`）。
- **实施顺序声明：** 依图显式声明实施顺序；**多个任务 Modify 同一文件时顺序不可调换**——不可调换的相邻任务逐对点名，说明为什么不可调换。

## 任务结构

每个任务用 `### Task N: <单元名>` 标题，写职责句加四段：Files、Interfaces、边界条件、验收标准；编码多路径流程的任务在 Interfaces 与边界条件之间加流程图。

````markdown
### Task N: [组件名称]

**职责：** 一句话——本任务交付什么、被哪些任务依赖。

**Files:**
- Create: `exact/path/to/file.py`
- Modify: `exact/path/to/existing.py:123-145`
- Test: `tests/exact/path/to/test.py`

**Interfaces:**
- Consumes: implementation.md §I-3（SettingsWriter）——只引用章节号与名字，不复制签名
- Produces: 本任务新增物的名字与所在章节号，如 implementation.md §I-4（ConfigLoader）——供下游引用与审读核对

**边界条件：**
- [触发条件 → 期望行为，写成可判真伪的命题。含失败路径：失败如何表现、返回什么、报什么错。]
- [设计文档暗示、却最容易被测试遗漏的输入类写在这里，每条配一条钉住它的验收标准。]

**验收标准：**
- [该任务的测试必须证明的行为清单，每条可判真伪；与边界条件逐条对应。]
````

任务写到「边界条件 + 验收标准」为止。TDD 的红绿循环由执行者按验收标准自行展开，不在计划中预写。

- 任务编码多路径流程（出口 ≥2、裁决分支或修复循环）时，在 Interfaces 与边界条件之间加 **流程图：** 小节配 mermaid，先图后文（画法见 `references/writing-rules.md`）；纯数据或文档改动任务不加。
- 边界条件条目超过 6 条时按主题加粗体小标分组（如「执行语义」「失败路径与重跑」「禁止项」「逐字契约」），命题原文不重写。
- 逐字契约句——要求在产物中逐字落地的节名、格式行、移交句——原样引用，不改写。

## 验证方案文件

需求级验证方案不是 plan.md 的内嵌章，而是独立文件 `docs/superpowers/specs/<date-feature>/verification.md`，与 design.md、plan.md 同目录；plan.md 只留一句指针：`验证方案见同目录 verification.md。`

- 计划存在跨任务组装点或触及外部接口 → 同目录另产出 verification.md；章节骨架、内容要求与质量判据见 `references/verification-template.md`。
- 纯单模块无接口的计划不产出该文件，plan.md 骨架不变。
- 判定无集成面而不产出验证方案时，把推导依据写进计划：改动面清单 → 无组装点、无外部接口、无运行边界的推导链；不写依据的无方案不合法。

## 写作要求

写作与排版规范见 `references/writing-rules.md`（适用于全部五件产物）；本文件专属：不出现接口签名与调用示例，只引用章节号与名字（§I-N）。

## 执行交接

文档末尾固定写执行交接块：

- 全套规格（design.md / implementation.md / plan.md / verification.md）的确认已在呈报环节完成；本块只征询执行方式，不重复确认请求。
- 建议执行方式：子代理驱动或会话内执行，附一句理由。
- 必需子技能：子代理驱动用 `superpowers:subagent-driven-development`；会话内执行用 `superpowers:executing-plans`。
- 实施开始后发现设计必须改：停止实施，回到设计确认门；返工还是回滚由需求方决定；已合入 main 的部分用新提交修正，不改写历史。

## 独立审读处置记录附录

文档最末固定附上，位于执行交接块之后。写明审读者身份（子代理/自审）、问题清单与逐条处置；初稿可写「待审读」，确认前必须填完。
