# 计划自审清单

写完整份 plan.md 之后、提交统一审读之前，用新视角重读设计文档并对照检查计划。这份清单由你自己来跑——不要派发子代理去做。

## 自审

**1. 设计文档覆盖：** 略读设计文档中的每个小节、每条需求，特别是功能清单与「明确不做」清单。你能指出实现它的是哪个任务吗？把缺口列出来。

**2. 单元五问：** 每个任务自检五问——输入是什么、输出是什么（→ Interfaces）、边界在哪（→ 边界条件）、失败时行为是什么（→ 边界条件的失败路径条目）、拿什么证明（→ 验收标准）。五问齐备，任务即完整。

**3. 类型一致性：** 你在后面任务中用到的类型、接口名和数据名，与你在前面任务中定义、并在 implementation.md 立节的一致吗？同一个接口在 Task 3 里叫 `clearLayers()`，到 Task 7 却叫 `clearFullLayers()`，这就是个 bug。

**4. 边界条件承接原「审查重点」的职能：** 对设计文档暗示的每一类输入或失败模式，是否有一个任务的边界条件与验收标准覆盖到了它？其中最容易坑到使用者的几类，补进最贴切任务的边界条件，并各配一条验收标准。全部覆盖了就不需要补——但这个检查必须真的做过。

**5. 比例：** 把计划的长度与设计文档的长度作比较。一份比它所实现的设计文档长出好几倍的计划，是程序的誊抄，而不是计划。如果测试代码或函数体出现在计划里，把它们换成边界条件与验收标准的措辞。

**6. 行为可判真伪与锚定：** 计划中的每条行为描述都能判真伪吗？引用既有代码或既有测试、描述其行为的地方，能在代码或测试中指到对应吗？指不到即臆写——去读代码，不要凭记忆写。

**7. 骨架完整与写作要求：** 文首指针行、任务依赖图与实施顺序声明、元数据、任务规格、执行交接、审读处置附录是否齐全？七条写作要求是否满足？计划是否只做实施前决策记录，没有混入实施后的内容？

**8. 实现效果：** 按任务顺序做完，设计文档功能清单的每条「输入 → 最终用户看到什么」是否真的会出现？把任务串起来看依赖、接口契约与集成点；每个任务都通过、组合起来却不工作的缺口，在这里抓。

**9. 接口可测性：** 对每个 Consumes / Produces 引用推演它的第一条测试调用——被引用的 implementation.md 章节能支撑这个调用吗？只断言可见行为能否覆盖该任务的验收标准？推演不出来、或必须重型 mock 才能调，就是可测性缺口：回 implementation.md 的接口设计改接口。可测性缺口在计划期修最便宜；这道检查没有人工兜底（确认门审的是忠实性，不是可测性），统一审读会再做一遍，但你是第一道。

**10. 验证方案专项：** 计划产出 verification.md 时逐项核对——四性逐查（出处锚定、双向映射、粒度判据、可操作性判据）、内容要求六项逐查（确定性固定策略、保真度声明、副作用隔离、场景自包含、既有登记册查重、失败证据采集）、出处抽查、双向映射核对。

**11. 形态声明与裁剪推导核对：** design.md 的形态声明与章节裁剪推导是否成立？任务拆分与裁剪结果一致吗——裁掉的条件章没有残留任务，保留的承诺（如纯 API 的错误码契约）有任务覆盖。

**12. 任务依赖图与实施顺序核对：** 依赖图与任务实际的 Consumes / Produces 一致吗？实施顺序声明覆盖了全部 Modify 同一文件的相邻任务对吗？关键路径上的任务能并行吗？

**13. 跨文件引用一致性核对：** 本文件引用的 implementation.md 章节号（§I-N）在 implementation.md 中真实存在吗？Produces 声明的章节号与 implementation.md 的实际章节对应吗？对 design.md 的 §N 引用有效吗？

发现问题就原地修。无需重新审查——修完就继续前进。发现设计文档的某条需求没有对应任务，就补上那个任务。
