# 实现设计模板

> 读者假设：审查者（需求方 / 审读子代理）与计划撰写者；懂软件工程，不熟悉产生本文档的对话。
>
> 本文档回答：数据怎么存、接口是什么约定、关键流程怎么走、规模多大、风险在哪。章节结构与写法见本模板；写它之前先读 `references/implementation-rules.md`。

## 章节骨架

产出文档标题 `# <项目> 实现设计`，文首为上方读者声明引块；其后九节固定、按序成文，5、6 为条件章（设与不设由 §0 裁剪推导决定，默认裁剪见文末速查表）：

0 形态声明 / 1 结构设计 / 2 数据与状态设计 / 3 接口设计（含接口六段式与外部接口补充段）/ 4 流程设计 / 5 界面实现规格〔条件：有 UI〕/ 6 运行与部署形态〔条件：需运行的产物〕/ 7 规模评估 / 8 设计依据 / 约束 / 风险清单

- 条件章不设时整章省略，其余章号保持原号——章号是引用锚。
- 「接口六段式」「外部接口补充段」「示例接口」三节是第 3 章的格式规范，产出文档不单独立章。

## 0. 形态声明

文首固定写两行（与 design.md §0 同源）：

```
产物形态：纯 API / Web 应用 / 桌面 App / 移动 App / CLI / 库或 SDK / 混合
章节裁剪推导：条件章哪些适用、不适用的原因——无推导不合法
```

- 逐条件章写适用 / 不适用，各附原因；文末「章节裁剪速查表」给默认推导，仍须写明本项目适用的具体原因。

示例（桌面 App 形态）：

```markdown
## 0. 形态声明
产物形态：桌面 App（macOS 菜单栏应用）
章节裁剪推导：
- §5 界面实现规格：适用——有 UI；
- §6 运行与部署：适用——需分发 bundle；
- 数据与状态设计：适用——本地配置文件 + 外部格式（settings.json）；
- （若为纯 API 项目此处写：「§5 不设——无 UI；用户可见面为 HTTP 响应，
  其契约完整性由 §3 外部接口段保障」）
```

## 1. 结构设计

在定义任务拆分之前，先梳理出将创建或修改哪些文件、每个文件各负责什么。任务如何分解，就在这一步敲定。

- 以清晰的边界和定义良好的接口来设计各个单元。每个文件应当只有一个明确的职责。
- 当代码能一次性放进上下文时，你的推理效果最好；当文件足够专注时，你的编辑也更可靠。宁选更小、更专注的文件，也不要承担太多职责的大文件。
- 一起变动的文件应当放在一起。按职责拆分，而不是按技术分层拆分。
- 在既有代码库中，遵循既有的模式。如果代码库用的就是大文件，不要单方面重构——但如果你正要修改的某个文件已经臃肿到难以驾驭，在实现设计里安排一次拆分是合理的。

这个结构为任务分解提供依据。每个任务都应当产出自包含、独立来看也成立的改动。

- **模块划分：** mermaid 模块划分图（画法见 `references/writing-rules.md`）+ 各模块一句话职责 + 依赖方向与分层。
- **任务拆分依据：** 为什么这样切任务——每个任务边界对应哪个模块边界或交付物；为 plan.md 的任务依赖图与实施顺序声明供依据（图在 plan.md，依据在这里）。

## 2. 数据与状态设计

- **持久化实体：** 每个实体一节（编号见第 3 章编号约定），一张字段表：字段 / 类型 / 语义 / 约束 / 来源 / 示例值。
- **存储语义：** 存储位置、权限、并发与原子性语义。
- **外部格式：** 需读写外部系统拥有的文件时，转换规则 + 输入输出示例逐字对照。
- **状态机（如有）：** 状态、事件、迁移表。
- 与 design.md 数据字典的分工：design 管「是什么」（产品级行为承诺），本章管「怎么存」（物理实现）。

## 3. 接口设计

按「先外部后内部」组织。接口 = 跨越边界的约定：

- **外部接口（对外承诺）：** HTTP endpoint / 公共库 API / CLI 参数与退出码 / 事件消息——逐字严格；在六段式之上加「外部接口补充段」。
- **内部接口（模块间）：** 六段式。

**编号约定：** 第 2 章每个持久化实体与第 3 章每个接口各立一节，标题 `### I-N <名字>（一句话定位）`，N 按文中出现顺序全文连续编号。plan.md 的 Interfaces 块以 `implementation.md §I-N（名字）` 引用——只引章节号与名字，不复制签名；verification.md 的场景出处以 `I-N` 引用。编号唯一，引用与被引节名一致。

### 接口六段式（每接口固定六段）

1. **职责**：一句话，解决什么问题；
2. **签名**：精确（给执行者）；
3. **参数表**：参数 / 类型 / 含义 / 约束与非法值；
4. **错误表**：条件 → 错误 → 调用方应对；
5. **示例**：一次调用 + 对应行为（结果逐字）；
6. **被谁依赖**：哪些流程 / 模块经由它。

六个段名为逐字契约：plan-template 与统一审读（review-prompt.md）按这六个段名核对接口完整性，不得改写段名。

### 外部接口补充段（对外承诺级）

7. **契约**：请求 / 响应全文示例、错误码全集、版本与兼容承诺（纯 API 项目本节为文档主体）。

### 示例接口

六段式的实际形态（取自真实项目；示例不涉及对外版本承诺，故第 7 段略）：

```markdown
### I-3 SettingsWriter.replaceAnthropicEnv（外部配置替换引擎）
**职责：** 把 Claude Code 全局配置的 env 块整体替换为目标键组，非模型键与
其他顶层内容原样保留——切换/覆盖/编辑应用三条链路的唯一写入点。
**签名：** `func replaceAnthropicEnv(with env: [String: String]) throws`
**参数表：**
| 参数 | 类型 | 含义 | 约束/非法值 |
|------|------|------|------------|
| env | [String: String] | 目标键值组 | 键应为 ANTHROPIC_* 前缀（调用方保证）；值任意字符串 |
**错误表：**
| 条件 | 错误 | 调用方应对 |
|------|------|------------|
| 文件非合法 JSON | 抛错 | 发失败通知；原文件字节不变 |
| 写入失败（磁盘等） | 抛错 | 同上；临时文件+替换保证不破坏原文件 |
**示例：** env 现为 `{"DISABLE_AUTOUPDATER":"1","ANTHROPIC_BASE_URL":"a"}`，
调用 `replaceAnthropicEnv(with: ["ANTHROPIC_BASE_URL":"b","ANTHROPIC_MODEL":"m"])`
后 env 为 `{"DISABLE_AUTOUPDATER":"1","ANTHROPIC_BASE_URL":"b","ANTHROPIC_MODEL":"m"}`。
**被谁依赖：** ModelSwitcher.switchTo / applyEnv、ImportCoordinator、
FirstRunCoordinator、PreferencesViewModel.saveForm
```

## 4. 流程设计

- **关键链路：** 每条关键链路一张 mermaid sequenceDiagram：参与者、消息次序、数据流（画法见 `references/writing-rules.md`）。
- **接口锚定：** 每条链路标注涉及的接口章节号（`I-N`）。

## 5. 界面实现规格（条件：有 UI）

- 视图结构、状态管理方案与归属、与 design.md 界面规格章的映射。
- 平台能力约束实测结论（如：构建工具链能力边界、自动化测试可用性）。

## 6. 运行与部署形态（条件：需运行的产物）

- 进程模型 / 部署目标 / 环境要求 / 分发方式 / 最低系统版本。

## 7. 规模评估

- **指标随形态选：** 代码量分布（模块 × 预估行数）/ QPS·并发·延迟预算（服务）/ 页面数·包体（Web）/ 内存·体积（App）/ API 面大小（库）。
- **复杂度热点与对策：** 逐个热点写对策与代价。

## 8. 设计依据 / 约束 / 风险清单

- 与 design.md 决策的承接关系：引用 design.md 章节与 decisions.md 对应条目。
- 实施层新增取舍按「候选 / 选择 / 依据 / 代价」四段写。

## 章节裁剪速查表

模板参考，不计章；给出的是默认推导，§0 仍须逐章写明本项目适用的具体原因。

| 章 | 纯 API | Web | 桌面/移动 App | CLI | 库/SDK |
|----|--------|-----|--------------|-----|--------|
| 5 界面实现规格 | 不设 | 设 | 设 | 不设 | 不设 |
| 6 运行与部署 | 设（进程/并发/扩缩容） | 设（托管/环境） | 设（bundle/分发/系统版本） | 设（安装方式） | 不设（推导：被嵌入） |
| 2 数据与状态 | DB/缓存/payload | DB + 前端状态归属 | 本地存储/文件格式 | 配置与输出格式 | 不设或极简（推导） |
| 3 接口设计 | **对外 API 即主体** | 前后端契约 + 路由 | 内部接口 + 系统边界 | 参数与退出码即主体 | **公共 API 即主体** |
| 7 规模评估 | QPS/并发/延迟/容量 | 页面数/包体/首屏 | 代码量/内存/体积 | 代码量/二进制大小 | API 面大小 |

## 写作要求

写作与排版规范见 `references/writing-rules.md`（适用于全部五件产物）。本文件专属：

1. 交叉引用写「见 §N（内容摘要）」，不写裸引用；引用 plan.md 任务写 `Task N`；被 plan.md 与 verification.md 引用时以 `I-N` 为锚。
2. 签名与示例精确到执行者可逐字使用：签名可直接落地；示例给一次调用 + 对应行为（结果逐字）。
3. 外部接口逐字严格：endpoint、参数名、错误码、退出码，出现一处歧义即缺陷。
4. 禁止无锚引用——凡「已确认 / 已验证 / 已裁决」必须能指到仓库内文件或 decisions.md 条目，否则删掉断言，或先落盘再引用。
