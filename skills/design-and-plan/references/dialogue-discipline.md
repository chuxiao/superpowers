# 对话纪律

需求对话阶段的指导组：第一条消息怎么发、对话怎么进行、复述怎么交替。由 SKILL.md 的「你的第一条消息」「对话」「复述」三节指向；进入需求对话、发出第一条消息或撰写复述段之前读它。
本文件是第一步「弄清他们要什么」的纪律全文；SKILL.md 第一步只留引用。

## 判断需求的范围

收到需求先判断三件事再开口：

- **量级**——这是一个 feature、一个完整产品、还是一个课题？超出一次开发流程能承载的，引导拆成子项目，商定顺序，从第一个可执行的子项目开始。
- **可行性**——超出模型与工具能力边界的（「帮我写个 windows」），诚实说明，并给出最近的可行版本。
- **模糊度**——需求荒谬地宽泛不是拒绝的理由，是把它放回现实的起点：用开放问题澄清「你要的到底是什么」，让需求方自己把范围收窄。不嘲笑、不照单全收、也不代替需求方收窄。

## 你实际知道什么？

回复之前，先问自己：对于他们想要什么、以及为什么，我到底知道些什么？

- **相关信息都在需求描述里**（“把图标改成矢车菊蓝”）。这是一个快速、清晰的任务。需求完备时，跳过的是对话，不是流程：直接进入「列出各方案」与四件套成稿，方案拍板、成稿、审读、呈报确认、执行交接逐环节照走，然后构建，并说明你做了什么。
- **关键信息缺失。** 开启对话。

## 先看再问

如果是在既有项目里做，或对方已给了你上下文（设计文档、计划、交接说明、他们指给你的文件、早先的对话），先深入钻研，再发出第一条消息。阅读他们所指的内容以及与之相连的代码或材料，一直读到你能解释相关部分如今如何运作、这次改动会触及什么为止。绝不问项目或他们的上下文已经能回答的问题。

## 你的第一条消息

用以下方式之一推进工作：

- **他们已经说了想要什么**（设计文档、计划、一份详细的请求）：整条消息以 200 词左右为目标。用自己的话复述他们的请求，让他们能看出你是否抓住了它的轮廓：就他们已说出的范围而言，他们想要什么、给谁用、以及为什么。补充你发现的与之相关的内容：相关部分如今如何运作、这次改动会触及什么。如果你发现了他们可能没考虑过、且会改变他们所要求的内容或改变必须如何构建的东西——比如一个约束、一处冲突、或一条成本更低的路径——就直说。如何构建稍后再谈（见「列出各方案」）；先弄清他们想要什么。结尾用一行话欢迎对方纠正，然后提一个关于他们想要什么的问题，让它落在对方描述中最悬而未决、而其答案最能改变最终做成之物的那个点上。设计文档往往不完整，所以在以它为基础构建之前，先确认其中的内容。
- **他们还没说：** 只提一个开放问题，沿用他们自己的用词，指向对方描述里悬而未决的最大事项。说明你为什么问：这个答案会怎样改变你要构建的东西。比如面对“给我的面包店做一个网站”：“如果网站主要是给那些在犹豫要不要顺便进店的人看的，我会把营业时间和今天展示柜里有什么放在最前面；在线接单是另一种网站。你希望访客进入页面后做什么？”

消息如何结尾，取决于他们的消息是否要求了头脑风暴：

- **他们要求了**（点名要求、调用该技能、或要求一场设计讨论）：以你的问题结尾。他们想要这场对话。
- **他们没要求：** 他们可能根本不想要对话。在问题之后，轻描淡写地补一句，提议改成直接开工，比如“或者你想让我直接开干，说一声就行”。如果他们接受了，跳过提问对话，直接进入「列出各方案」与四件套成稿：方案拍板、成稿、审读、呈报确认、执行交接逐环节照走，然后去做他们要求的事。

整条消息就是这些。

## 对话

每条消息都以一个问题结尾：单个句子，后面不挂一串示例答案。用平实的语言，难度只比需求方当前的理解水平略高一点。配合他们的词汇；绝不使用流程行话。你绝不需要向需求方引用这项技能的原文。

清晰简洁。先说要紧的。避免行话。当你汇报发现时，给他们最重要的发现项，并主动提出可以提供其余部分。

**让他们描述。** 开放问题优先。他们自己的话承载着你的选项承载不了的意图。只在他们卡住时才提供一份简短的选项单。当他们说“你猜吧”或“你怎么看？”时，就提出一个具体的提议。

**如何制作。** 每个项目都建立在关于媒介、工具、材料和资源的选择之上：一个应用的平台、编程语言和库。尽早弄清这些选择中哪些他们想亲自做、哪些交给你，以及他们已经拥有哪些可用的东西。有强烈见解或相关技能的人会想把选择谈透。指望你的人需要合理的默认值，而且要由你用平实的话说出来。已有现成作品时，就在它已经在用的东西之上构建。你做出的任何选择都作为你的决定写进设计，绝不写成他们同意过的东西。

**要覆盖的领域。** 这是待覆盖的话题，不是剧本。绝不把这些当作问题逐条念出来：

- 这是一种什么东西，它的特别之处是什么
- 为什么是现在，以及在他们的眼中成功是什么样子
- 目标、非目标、反目标（即使技术上可行也会让这件事算作失败的东西）
- 先例：他们在别处见过什么，喜欢过什么、讨厌过什么
- 现状：现在已经有什么，他们尝试过什么
- 他们在意的细节

**让每个问题都具体**——针对他们的项目以及他们已经告诉你的内容。像一位敏锐的同事那样做苏格拉底式提问：把每个问题建立在他们上一条回答或你的某个发现之上，让它帮他们想清某个后果、或某个他们可能漏掉的情形（“投票在会议前就截止，而这个月有两名成员加入。中途加入的人还有投票权吗？”）。当理由还不明显时，说明你想弄清什么、或答案会改变什么。一个他们可以纠正的提议，加上你的理由，常常胜过一个提问。

**提出侦察。** 一旦有了些了解，且再深入看看会有帮助时，就提出去看：更深入地看他们的代码库或项目、他们自己的文件和数据、或者网络。说明你会找什么。去不去由他们决定。

**列出各方案。** 一旦你理解了他们想要什么，并且在把任何东西写成文字之前，把各种构建方式放进单独的一条消息。想出几个真正可行的备选并剔除弱的；凡与他们的缘由相悖、或被现有作品排除的，都在剔除之列。呈现剩下的两三个，每一个都基于项目实际的运作方式，并说明各自的取舍。推荐其中一个并说明理由，然后问他们想走哪条路。当确实只有一种合理做法时，直说，并解释其他做法为何不合适。这一步针对如何构建；至于他们想要什么，先让他们描述。

**展示，而非讲述。** 每当“看”比“读”更有帮助时，提供「视觉伴侣」——一个用来展示视觉稿的浏览器标签页（见 `references/visual-companion.md`）；第一次复述 UI 相关内容前即提议，不等到聊完：

- 他们会看的东西：一个屏幕、一个页面、一个弹窗、一份报表
- 一种布局或排布：页面的、面板的、流程的
- 一个流程或一串步骤
- 彼此看起来会不一样的选项
- 看图比读文更容易理解的结构：一张架构图、一条时间线、一张关系图

一旦他们接受，就用它来展示可供反馈的视觉稿、并排的选项、以及他们能点击的一次性原型。他们接受后，在启动服务器之前，先阅读 `references/visual-companion.md`。

**用 spike 摸底。** agent 式的工作是瀑布式的，只是非常非常快。一次快速的、用完即弃的构建，往往是弄清他们想要什么、或某样东西是否行得通的最省成本的方式。有帮助时就提出做一个。当他们只想做个 spike 时，不要碍事。spike 不带测试或只带最少的测试，不追求无懈可击，并且跳过计划、实现和审查流程。把 spike 教给你的东西带回对话。

**几个相互独立的项目。** 如果这实际上是几个相互独立的项目，就直说，商定顺序，然后一次只对其中一个项目进行头脑风暴。

## 复述

边进行边复述。一旦你对某个部分的理解足以描述它（比如说，它的用途和服务的对象，或某个部件如何运作），就用大约 200-300 词把那个部分复述回去，然后回到关于下一部分的问题。复述与提问在整个对话中交替进行；最后一段涵盖剩下的所有内容。

只有他们说过的话才作为他们的内容记入。你补上的任何东西都作为你的提议记入，并附上理由。每一段结束时，问哪里不对、哪里有缺。

在发出一段复述之前，先检查它：它描述的是他们会看的东西吗，比如一个页面、一个屏幕、一份报表或一个弹窗？如果是，而且他们还没看到过视觉伴侣的提议，就先发提议（单独一条消息，见 `references/visual-companion.md`），把这一段留到下一条消息。第一次复述 UI 相关内容前即提议，不等到聊完。一旦他们接受，就把视觉稿放在描述旁边。
