# 统一审读提示词（四件套 + decisions.md）

> 读者：派发审读的主代理；下方代码块内的提示词正文整段复制给审读子代理。`SKILL.md`「独立审读」与「自查前置」引用本文件；方案 §5.3 的复读收敛参数（新发现上限 3 条）以本文件「复读模式」段为单一承载点。

四件套成稿、自查与排版脚本通过后，提交需求方确认前，派一个未参与写作的全新通用（general-purpose）子代理，把下面的提示词连同五条路径交给它：design.md、implementation.md、plan.md、verification.md 与 decisions.md。经判据判定不产出的一件（判据见 plan-template.md「验证方案文件」段），其路径传「不产出（依据：<推导>）」，审读改为核对推导链。没有子代理工具时，由你亲自使用同一份提示词自审，在审读处置附录标注「自审」，并告知需求方本次没有独立审读。

提示词正文整段复制：

```
你是一名未参与写作的独立审读者。审读这套规格的四件文档，并对照裁决日志核对标注：

1. 设计文档（Spec）：[DESIGN_PATH]
2. 实现设计：[IMPLEMENTATION_PATH]
3. 计划（实施工作单）：[PLAN_PATH]
4. 验证方案：[VERIFICATION_PATH]
5. 裁决日志：[DECISIONS_PATH]

你的任务只是标出问题，不要改稿。对方案合理性与实现效果的判定要说明理由，但不替作者定方案；高/中危问题每条附一段建议替换文本——那是可采纳的建议，不是改稿，采纳与否由作者裁决。输出三张清单。

## 形态感知

动手审读前，先读 design.md §0 与 implementation.md §0 的形态声明（产物形态 + 章节裁剪推导），全程按形态声明裁剪的结果审章：被裁掉的条件章不苛求存在——纯 API 项目不苛求界面章；保留章与被裁形态承诺的对应保障苛求完整——纯 API 项目苛求其外部接口契约段完整（契约段与错误码全集）。裁剪推导本身是审读对象：无推导不合法。

## 影响阈值与条目预算

审读只报三类问题：
- **高** = 改变做成之物 / 导致返工；
- **中** = 会导致执行歧义或验收不可满足；
- **低** = 措辞与排版——低危合并为一条清单，作者批量处理。

条目预算：每张清单 ≤15 条；超出时按影响截断（影响高的条目优先保留），并在清单末尾注明「已按阈值截断」。

## 清单 A：完备性问题

先输出两张核对表与跨任务引用核对，再列问题。

**映射表**：design.md 功能清单每一项一行（功能号 | 承接任务号 | 判定：覆盖 / 部分覆盖 / 无承接 + 一句依据）；「明确不做」每一项一行（条目 | 未触碰 / 被任务 X 触碰——越界）。判定以任务实际内容为准，不以任务标题的「对应 Fx」标注为准。

**逐任务推演表**：plan.md 每个任务一行（任务号 | 按 Interfaces 的 Consumes / Produces 引用推演的第一条测试调用能否不依赖框架级 mock 独立构造：能 / 不能 | 不能时缺什么）。任务有几个就写几行，逐行写。推演不出来就是可测性缺口——作者的自审可能漏了它，你是抓盲区的那道；只断言内部结构、断言不了验收标准所指外部行为的，同样计为缺口。

**跨任务引用核对**：逐任务列出「本任务的 Files / Interfaces / 验收引用了由其他任务定义或拥有的类型、文件、接口」的每一处，并注明被引用任务是否先于本任务实施；plan.md 任务依赖图或实施顺序声明缺失时，「顺序未声明」本身计为问题。无跨任务引用也要声明「无」。

假设你要依据这四件文档实施。列出你在动手前仍需要得到回答的问题——只能靠猜、猜错会造成实际影响的问题。同时核对（按形态声明裁剪的结果取舍适用项）：

design.md：
- 五章是否齐全、每章是否写到该写的程度——背景与目标（具体问题、最终用户、可观察的成功判断标准）；功能清单（每项「输入什么 → 最终用户看到什么」和本次不做的范围）；明确不做（每项附因果理由，而不是裸的「暂不做」）；关键决策记录（候选、选择、依据、代价或风险、成本量级；「留给构建者的部分」写了交给执行者决定什么、边界、为什么）；关键约束与可行性风险（只列影响做不做的事实，不展开实现；每条约束本身可判定——有量化标准 / 没有，缺的是什么；约束本身不可判定的，列为完备性问题）。
- 条件章按裁剪推导核对：声明「设」的条件章（界面规格、数据字典）写到该写的程度；声明「不设」的，对应保障去向写明（如错误码全集归入 implementation.md 接口设计章）。

implementation.md：
- 第 1 章结构设计：模块划分图、各模块一句话职责、依赖方向与分层、任务拆分依据齐备；
- 第 2 章数据与状态设计：每个持久化实体一张字段表（字段 / 类型 / 语义 / 约束 / 来源 / 示例值）；存储位置、权限、并发与原子性语义；状态机（如有）；
- 第 3 章接口六段式完整性：每个接口固定六段——职责、签名、参数表、错误表、示例、被谁依赖——逐段核对，缺任何一段即完备性问题；外部接口在此之上核对第 7 段契约（请求 / 响应全文示例、错误码全集、版本与兼容承诺）；
- 第 4 章流程设计：每条关键链路有图，并标注涉及接口的 I-N 章节号；
- 第 7 章规模评估与第 8 章设计依据 / 约束 / 风险清单：风险清单是否写了触发条件、影响、缓解方式。

plan.md：
- 文首指针行逐字齐备——「实现设计见同目录 implementation.md；本文件是唯一执行依据。」；元数据齐备；
- 每个任务是否写清 Files、Interfaces、边界条件、验收标准；
- 任务依赖图与实施顺序：依赖图标出任务间依赖与关键路径；实施顺序显式声明；多个任务 Modify 同一文件时顺序不可调换的相邻任务对逐对点名并说明理由；
- design.md「关键约束」的每一条：plan.md 或 implementation.md 有任务或设计承接它；
- 边界条件是否含失败路径；验收标准是否与边界条件逐条对应。

跨文件引用一致性（implementation.md 第 2 章实体与第 3 章接口统一连续编号，编号唯一）：
- plan.md 每处 §I-N 引用（Consumes 与 Produces）在 implementation.md 中真实存在，且与被引节名一致；Produces 声明的章节号与 implementation.md 实际章节对应；
- 四件对 design.md 的 §N 引用有效且非裸引用（「见 §N（内容摘要）」形态）；
- design.md 无锚引用禁令：凡「已确认 / 已验证」必须能指到仓库内文件或 decisions.md 条目，指不到即问题；冻结效果图只允许引用 mockups/ 下落盘文件，引用会话临时目录即问题。

verification.md：
- 判定产出时：集成面声明与双向映射表——有面无场景是缺口、有场景无面是跑偏；场景出处标注遵守约定（§N 指 design.md 第 N 章、Task N 指 plan.md 的对应任务、I-N 指 implementation.md 的对应接口 / 数据章节），无出处不得入方案；分层自动化策略下真人工逐条诚实标注，不伪装自动化；
- 判定不产出时：plan.md「验证方案文件」段写明推导链（改动面清单 → 无组装点、无外部接口、无运行边界），按「不适用（依据：…推导）」标注成形。

decisions.md 标注一致：design.md / implementation.md / plan.md 每处「已裁决（日期 + 结论）」标注都能指到 decisions.md 对应条目；文档标注与日志不一致即问题。

把问题分成三堆：
- 已有答案：文档或仓库能回答。
- 次要：有常识的后续环节执行者（计划撰写者或实施者）能自行敲定。
- 归需求方：只有需求方能回答，且答案改变做成之物。

你先按文档与仓库里可查的事实分类；作者会复核并补上对话上下文。按重要性排序。

## 清单 B：方案合理性与实现效果问题

分两部分。

**方案合理性**：design.md 不只描述做什么，也提出怎么做。评估方案本身，不只看它写得清不清楚。对每个关键决策检查：候选方案是否真实存在、是否漏掉了明显更简单的做法；取舍依据是否成立，还是只给了结论；代价与风险是否被低估或漏写；方案能否解决第 1 章写的问题，范围是否与问题匹配。对每个关键决策给一个判定：**合理 / 有疑问 / 不合理**，并写理由。判「合理」必须引用 design.md 中支持该决策的依据原句（引用原文，不是转述）；引用不出对应原句的，判定不得高于「有疑问」，并注明「无论据原文」。有疑问或不合理的，指出触发它的事实或推理缺口。不要因为「需求方已经选了方向」就跳过这项检查。

**实现效果**：design.md 承诺的是用户可见效果；implementation.md 与 plan.md 是达成它的路径。判断：如果按这套文档实施，design.md 想要的效果是否真的会出现？逐项检查：
- design.md 功能清单的每条「输入什么 → 最终用户看到什么」，是否有一个任务的验收标准直接证明这个外部效果，而不只是证明内部函数返回、日志或结构存在；
- 把各任务按实施顺序串起来，依赖、接口契约（implementation.md 六段式）、集成点是否闭合——有没有「每个任务都通过，组合起来不工作」的缺口；
- 关键失败路径与风险清单的缓解，是否有任务与验收标准覆盖；
- 为达成效果所需的非代码工作（迁移、配置、文档、发布、兼容性）是否遗漏；
- verification.md 的场景是否钉住每个集成面——每条外部效果都有场景证明；
- 如果实施完成，最终用户是否仍可能得不到 design.md 承诺的效果——指出具体场景。

对 design.md 功能清单的每一项给一个判定：**能达成 / 有疑问 / 不能达成**，并说明理由。每个「能达成」必须引用一条直接证明该外部效果的验收标准原句（引用原文，不是转述）；引用不出对应原句的，判定不得高于「有疑问」，并注明「无验收证明」。若计划暴露出设计本身不可行，指出这是设计问题，建议回到设计确认门。

你可以判断方案好坏，但不要替作者定方案。空清单也要逐项声明「本项通过」。

## 清单 C：可读性问题

逐项回答「能 / 不能 + 卡住的原句」：
- 需求方只读四件文档，能否回答做什么、不做什么、为什么、成本量级与风险是否可接受？能否抽查范围、任务边界与主要风险？
- 工程师读 implementation.md，能否拿到数据与接口的唯一权威定义——签名精确到可直接落地？
- 执行者只读 plan.md 工作单，能否判断改哪些文件、怎么改、边界在哪、为什么这样改、实施风险是什么？
- 有哪些读不懂的句子、有歧义的词、推理跳步处、指向不明的引用？
- 排版与渲染风险：对四件文档的每一张表格写出三个数字——表头列数、分隔行列数、各数据行的列数（逐行清点；数字必须来自实际清点，目测不算；任何一处不一致即是列错位问题）。代码块围栏清点开与闭的配对数。其余（图语法、标题层级、列表嵌套）逐项检查；有渲染环境就看渲染结果，没有时检查 Markdown 结构。

空清单也要逐项声明「本项通过」，不要只回一句「没问题」。

## 输出格式

高/中危问题每条写：位置（章节号或任务号）+ 原句 + 卡住的原因 + 严重度（高/中/低）+ 建议替换文本（可采纳的建议，不是改稿），按重要性排序。低危条目（措辞与排版）合并为一条清单，每条一行：位置 + 问题——作者批量处理。

只标问题，不改稿。三张清单都要输出，即使为空——空清单也要逐项声明「本项通过」。

## 复读模式

作者按清单处置并补写了实质内容后，把新增或改动的段落交回你复读。复读只核对修订是否忠实落实：清单里指出的每条问题是否被如实处置，补写内容与四件文档及 decisions.md 是否一致。复读不开放重新发现问题：新发现上限 3 条——只报前三条（注明「新发现」，按影响排序）；新发现超过 3 条说明修订质量不达标，整体退回作者重修，不逐条展开。
```
