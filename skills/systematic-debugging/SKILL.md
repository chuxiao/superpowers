# 系统化调试

## 概述

**核心原则：** 始终先找到根因，再尝试修复。修复症状就是失败。

**违反本流程的字面规定，就是违背调试的精神。**

## 铁律

```
未经根因调查，绝不修复
```

若未完成阶段 1，你不能提出修复方案。

## 何时使用

适用于任何软件开发技术问题：
- 测试失败
- 生产环境中的 bug
- 意外行为
- 性能问题
- 构建失败
- 集成问题

**尤其务必在以下情况使用：**
- 时间压力大时（紧急情况会诱使人瞎猜）
- “就快速修一下”看似显而易见
- 你已经尝试过多个修复
- 上一次修复没有奏效
- 你尚未完全理解这个问题

**以下情况不要跳过：**
- 问题看似简单（简单的 bug 同样有根因）
- 你在赶时间（仓促行事必然返工）
- 经理要求现在就修好（系统化比瞎折腾更快）

## 修复链入口：宿主判定与回路由

bugfix 定性即建默认工作树（宿主默认为基线），修复链在这棵树中开查；归因完成后再定宿主：

- **缺陷在基线已交付代码：** 宿主=基线，默认树即修复归所；修复后过收官把关与集成验证门槛。
- **缺陷由当前需求引入：** 修复并入当前需求回路，在当前需求树内进行，随该需求过门槛；默认树为空树则移除。
- **缺陷由其他进行中需求引入：** 不跨树修复——记台账移交该需求回路并告知需求方；默认树为空树则移除。
- **修复提交后宿主改判：** 树与提交保留，合并去向由需求方裁决。

修复过程中发现需要新行为或新能力 → 重定性为 feature，回到完整流程入口，工作树保留改名。

## 四个阶段

你必须先完成当前阶段，才能进入下一个。

### 阶段 1：根因调查

**在做任何修复之前：**

1. **仔细阅读错误信息**
   - 不要跳过错误或警告
   - 它们往往包含确切的解决方案
   - 完整读完堆栈跟踪
   - 记下行号、文件路径与错误码

2. **稳定复现**
   - 你能可靠地触发它吗？
   - 确切的步骤是什么？
   - 每次都会发生吗？
   - 若无法复现 → 收集更多数据，不要瞎猜

3. **检查近期变更**
   - 什么变更可能导致了这个问题？
   - git diff、最近的提交
   - 新依赖、配置变更
   - 环境差异

4. **在多组件系统中收集证据**

   **当系统有多个组件时（CI → 构建 → 签名，API → 服务 → 数据库）：**

   **在提出修复之前，先添加诊断性插桩：**
   ```
   对每一个组件边界：
     - 记录什么数据进入组件
     - 记录什么数据退出组件
     - 验证环境/配置的传播
     - 检查每一层的状态

   先运行一次，收集能显示它在哪一层断裂的证据
   然后分析证据，确定失效的组件
   然后调查那个具体的组件
   ```

   **示例（多层系统）：**
   ```bash
   # 第 1 层：工作流
   echo "=== Secrets available in workflow: ==="
   echo "IDENTITY: $([ -n "${IDENTITY:-}" ] && echo SET || echo UNSET)"

   # 第 2 层：构建脚本
   echo "=== Env vars in build script: ==="
   printenv IDENTITY >/dev/null 2>&1 && echo "IDENTITY in environment" || echo "IDENTITY not in environment"

   # 第 3 层：签名脚本
   echo "=== Keychain state: ==="
   security list-keychains
   security find-identity -v

   # 第 4 层：实际签名
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **这能揭示：** 哪一层失效（密钥 → 工作流 ✓，工作流 → 构建 ✗）

5. **追踪数据流**

   **当错误深藏在调用栈中时：**

   完整的反向追踪技术见本目录下的 `root-cause-tracing.md`。

   **快速版：**
   - 坏值源自哪里？
   - 是谁带着坏值调用了这里？
   - 持续向上追踪，直到找到源头
   - 在源头修复，而不是在症状处修复

### 阶段 2：模式分析

**先找模式，再修复：**

1. **找到能正常工作的示例**
   - 在同一代码库中定位类似且能正常工作的代码
   - 有什么与坏掉的部分类似、却能正常工作？

2. **对照参考实现**
   - 如果要实现某个模式，完整读完参考实现
   - 不要略读——逐行读完
   - 在套用之前完全理解该模式

3. **找出差异**
   - 能正常工作的与坏掉的之间有什么不同？
   - 列出每一处差异，无论多小
   - 不要假定“那无关紧要”

4. **理解依赖**
   - 这段代码还需要哪些其他组件？
   - 哪些设置、配置、环境？
   - 这段代码做了哪些假设？

### 阶段 3：假设与检验

**科学方法：**

1. **形成单一假设**
   - 清楚地陈述：“我认为 X 是根因，因为 Y”
   - 把它写下来
   - 要具体，不要含糊

2. **最小化检验**
   - 用尽可能小的改动来检验假设
   - 一次只动一个变量
   - 不要一次修多处

3. **继续之前先验证**
   - 奏效了吗？是 → 阶段 4
   - 没奏效？形成全新假设
   - 绝不要在失败的修复上继续叠加更多修复

4. **当你不知道时**
   - 说“我不理解 X”
   - 不要假装知道
   - 寻求帮助
   - 做更多调研

### 阶段 4：实施

**修根因，而不是修症状：**

1. **创建失败测试用例**
   - 尽可能简单的复现
   - 可能的话用自动化测试
   - 没有测试框架就写一次性测试脚本
   - 修复之前必须先有失败测试
   - 使用 `superpowers:test-driven-development` 技能来编写规范的失败测试

2. **实施单一修复**
   - 针对已确定的根因
   - 一次只做一处改动
   - 不做“顺手改改”式的改进
   - 不夹带重构

3. **验证修复**
   - 测试现在通过了吗？
   - 有没有破坏其他测试？
   - 问题真的解决了吗？
   - 宣称成功之前先使用 `superpowers:verification-before-completion` 技能

4. **如果修复无效**
   - 停下
   - 数一数：你已经尝试过几次修复？
   - 若 < 3：回到阶段 1，带着新信息重新分析
   - **若 ≥ 3：停下并质疑架构（下方第 5 步）**
   - 未做架构讨论，绝不要尝试第 4 次修复

5. **如果 3 次以上修复都失败：质疑架构**

   **表明存在架构问题的模式：**
   - 每次修复都在别处揭示新的共享状态/耦合/问题
   - 修复需要“大规模重构”才能实施
   - 每次修复都在别处制造新症状

   **停下并质疑根本层面：**
   - 这个模式在根本上站得住脚吗？
   - 我们是在“纯粹靠惯性坚持它”吗？
   - 我们应该重构架构，还是继续修症状？

   **在尝试更多修复之前，先与需求方讨论**

   这绝不是一个失败的假设——这是架构错了。

## 危险信号——停下并遵循流程

如果你发现自己冒出了这样的念头：
- “先快速修一下，以后再调查”
- “就试着改一下 X，看行不行”
- “加多个改动，然后跑测试”
- “跳过测试，我手动验证”
- “多半是 X，我把那个修掉”
- “我没完全理解，但这样也许行”
- “模式说的是 X，但我会换个方式套用”
- “主要问题如下：[未经调查就列出修复]”
- 在追踪数据流之前就提出解决方案
- **“再修一次试试”（已尝试 2 次以上时）**
- **每次修复都在别处揭示新问题**

**以上所有这些都意味着：停下。回到阶段 1。**

**若 3 次以上修复失败：** 质疑架构（见阶段 4.5）

## 需求方发出“你做错了”的信号

**留意这些纠偏信号：**
- “那不是根本没发生吗？”——你没有验证就做了假定
- “它能让我们看到……吗？”——你本应加入证据收集
- “别猜了”——你在没有理解的情况下提出修复
- “Ultra-think 这个”——质疑根本层面，而不只是症状
- “我们卡住了？”（沮丧）——你的方法行不通

**看到这些时：** 停下。回到阶段 1。

## 常见合理化借口

| 借口 | 现实 |
|--------|---------|
| “问题很简单，不需要流程” | 简单问题同样有根因。对简单的 bug 来说流程很快。 |
| “紧急情况，没时间走流程” | 系统化调试比瞎猜乱试快得多。 |
| “先试试这个，然后再调查” | 第一次修复就定下了后续的做法。从一开始就做对。 |
| “等我确认修复有效后再写测试” | 未经验证的修复靠不住。先写测试才能证明它。 |
| “一次修多处能省时间” | 无法隔离哪个修复起了作用。还会引入新 bug。 |
| “参考实现太长，我改编一下模式” | 一知半解必然带来 bug。把它完整读完。 |
| “我看到问题了，让我把它修掉” | 看到症状 ≠ 理解根因。 |
| “再修一次试试”（已失败 2 次以上） | 失败 3 次以上 = 架构问题。质疑模式，不要再修。 |

## 速查表

| 阶段 | 关键活动 | 成功标准 |
|-------|---------------|------------------|
| **1. 根因** | 读错误信息、复现、检查变更、收集证据 | 理解问题是什么、为何发生 |
| **2. 模式** | 找到能正常工作的示例、对照比较 | 找出差异 |
| **3. 假设** | 形成理论、最小化检验 | 得到证实或形成新假设 |
| **4. 实施** | 创建测试、修复、验证 | bug 已解决，测试通过 |

## 当流程得出“没有根因”时

如果系统化调查表明问题确实源于环境、时序依赖或外部因素：

1. 你已经完成了流程
2. 记录你调查过的内容
3. 实现适当的处理（重试、超时、错误信息）
4. 加入监控/日志，便于日后调查

**但是：** 95% 的“没有根因”案例其实是调查不完整。
