# 使用 Git 工作树

## 概览

确保工作在隔离的工作区中进行。优先使用你所在平台的原生工作树工具。只有当没有原生工具可用时，才回退到手动创建的 git 工作树。

**核心原则：** 先检测既有隔离。然后使用原生工具。再回退到 git。绝不与 harness 对抗。

**开始时宣布：**"我正在使用 using-git-worktrees 技能来建立一个隔离工作区。"

## 建树纪律

定性为 feature 或 bugfix 后立即建立工作树：feature 与 bugfix 一律建立专属工作树，不得因改动小而省略。分支名带类型前缀 `feature/<主题>` 或 `bugfix/<主题>`；bugfix 的主题取缺陷症状，与宿主无关。重定性时树保留改名：feature 与 bugfix 互转只换类型前缀。

建树前同步基线分支：先 `git fetch` 远端；本地落后则快进，本地与远端分叉则停下移交需求方。然后从同步后的基线分支顶端建树——基点永远是基线顶端，不是会话当时的 HEAD。

一棵工作树同一时刻只允许一个会话开发写入，绝不复用他人之树；基线检出上直接开发禁止。集成动作（收尾合并、登记并入、合并事件落盘、基线快进、归档移动）不属开发写入，可在目标树或基线检出执行，前置是该树干净。

## Step 0: 检测既有隔离

**在创建任何东西之前，先检查你是否已经处于隔离工作区中。**

```bash
GIT_DIR=$(cd "$(git rev-parse --git-dir)" 2>/dev/null && pwd -P)
GIT_COMMON=$(cd "$(git rev-parse --git-common-dir)" 2>/dev/null && pwd -P)
BRANCH=$(git branch --show-current)
```

**子模块防护：** 在 git 子模块内部，`GIT_DIR != GIT_COMMON` 也会成立（与链接工作树一样）。在得出"已经在工作树中"的结论之前，先验证你并不在子模块里：

```bash
# 如果这条命令返回了路径，说明你在子模块中，而非工作树 —— 按普通仓库对待
git rev-parse --show-superproject-working-tree 2>/dev/null
```

**如果 `GIT_DIR != GIT_COMMON`（且不在子模块中）：** 你已经处于一个链接工作树中。先判断该树是否承载本需求：分支名与需求主题一致，或需求方确认续作 → 复用，跳到 Step 2（项目环境配置）；否则一律新建（含在他人需求树上、在基线检出两种情形），绝不复用他人之树。

结合分支状态进行报告：
- 在分支上："已位于 `<path>` 的隔离工作区（分支 `<name>`）。"
- 分离 HEAD："已位于 `<path>` 的隔离工作区（分离 HEAD，由外部管理）。收尾时需要创建分支。"

**如果 `GIT_DIR == GIT_COMMON`（或在子模块中）：** 你处于普通仓库的检出目录中。

需求方是否已经在你的指令中表明了对工作树目录的偏好？对已经声明过的既有偏好直接遵从，无需询问。

建树是流程闸门的一环，不接受跳过。需求方坚持就地开发时，说明隔离工作区与流程闸门的必要性，并等待其改道——不在原地开始开发。

## Step 1: 创建隔离工作区

**有两种创建方式，按以下顺序尝试。**

### 1a. 原生工作树工具（首选）

定性为 feature 或 bugfix 后必须建立隔离工作区（见「建树纪律」）。你是否已有创建工作树的途径？它可能是一个名字类似 `EnterWorktree`、`WorktreeCreate` 的工具，一个 `/worktree` 命令，或一个 `--worktree` 标志。如果有，就使用它并跳到 Step 2。

原生工具会自动处理目录位置选择、分支创建和清理。在你已有原生工具的情况下还去用 `git worktree add`，会制造出 harness 看不到也无法管理的幽灵状态。

**建后校验：** 原生工具建树后核验合并基——`git merge-base --is-ancestor <同步后的基线分支顶端> HEAD` 必须成立；不符则删除该树，以 git 显式起点重建。原生工具的便利让位于基点保证。

只有当你没有可用的原生工作树工具时，才进入 Step 1b。

### 1b. Git 工作树回退

**仅当 Step 1a 不适用时才使用本节** —— 即你没有可用的原生工作树工具。用 git 手动创建工作树。

#### 目录选择

遵循以下优先级顺序。需求方的明确偏好始终优先于观察到的文件系统状态。

1. **检查你的指令中是否已声明工作树目录偏好。** 如果需求方已经指定过，直接使用，无需询问。

2. **检查是否已存在项目本地的工作树目录：**
   ```bash
   ls -d .worktrees 2>/dev/null     # 首选（隐藏）
   ls -d worktrees 2>/dev/null      # 备选
   ```
   如果找到，就使用它。如果两者都存在，以 `.worktrees` 为准。

3. **如果没有其他可用指引**，默认使用项目根目录下的 `.worktrees/`。

#### 安全验证（仅限项目本地目录）

**创建工作树之前，必须验证目录已被忽略：**

```bash
git check-ignore -q .worktrees 2>/dev/null || git check-ignore -q worktrees 2>/dev/null
```

**如果并未被忽略：** 把它加入 .gitignore，提交该改动，然后继续。

**为何关键：** 防止把工作树的内容意外提交进仓库。

#### 创建工作树

```bash
# 根据所选位置确定路径
path="$LOCATION/$BRANCH_NAME"

git worktree add "$path" -b "$BRANCH_NAME" <同步后的基线分支>
cd "$path"
```

**创建失败：** 如果 `git worktree add` 因权限错误（沙箱拒绝）或其他环境故障而失败，停下并移交需求方处理环境后重建——环境故障不解开闸门，不在当前目录中继续开发。

## Step 2: 项目环境配置

自动检测项目类型，并执行相应的环境配置步骤：

```bash
# Node.js
if [ -f package.json ]; then npm install; fi

# Rust
if [ -f Cargo.toml ]; then cargo build; fi

# Python
if [ -f requirements.txt ]; then pip install -r requirements.txt; fi
if [ -f pyproject.toml ]; then poetry install; fi

# Go
if [ -f go.mod ]; then go mod download; fi
```

## Step 3: 验证干净的基线

运行测试，确保工作区从干净状态开始：

```bash
# 使用与项目匹配的命令
npm test / cargo test / pytest / go test ./...
```

**如果测试失败：** 报告失败项，并询问需求方：是继续推进，还是先排查失败原因。

**如果测试通过：** 报告已就绪。

### 报告

```
工作树已就绪，位于 <full-path>
测试通过（<N> 项测试，0 项失败）
可以开始实现 <feature-name>
```

## 速查表

| 情形 | 行动 |
|-----------|--------|
| 已处于链接工作树中 | 判断是否承载本需求：是则复用，否则新建（Step 0） |
| 在子模块中 | 按普通仓库对待（Step 0 防护） |
| 有原生工作树工具可用 | 使用它（Step 1a） |
| 没有原生工具 | Git 工作树回退（Step 1b） |
| `.worktrees/` 存在 | 使用它（验证已被忽略） |
| `worktrees/` 存在 | 使用它（验证已被忽略） |
| 两者都存在 | 使用 `.worktrees/` |
| 两者都不存在 | 检查指令中是否已声明目录偏好，然后默认使用 `.worktrees/` |
| 目录未被忽略 | 加入 .gitignore + 提交 |
| 创建时出现权限错误 | 停，移交需求方处理环境后重建 |
| 基线分支与远端分叉 | 停，移交需求方 |
| 原生工具建树后合并基不符 | 删树，以 git 显式起点重建 |
| 基线测试失败 | 报告失败项 + 询问 |
| 没有 package.json/Cargo.toml | 跳过依赖安装 |

## 常见合理化借口

| 借口 | 现实 |
|--------|---------|
| "我显然不在工作树里 —— 不需要检查" | 运行 Step 0。harness 创建的隔离和子模块都会骗过肉眼判断；检测命令才能给出定论。 |
| "`git worktree add` 比寻找原生工具更快" | 由原生工具（如 `EnterWorktree`）负责选择目录位置、创建分支和清理。绕开原生工具且不保证基点才是第一大错误；没有原生工具时用 git 显式起点，建树后核验合并基。 |
| "工作树目录肯定已经被忽略了" | 运行 `git check-ignore`。未被忽略的工作树目录，其内容会被一并提交进仓库。 |
| "目录叫什么名字都行" | 需求方的明确指令优先于既有的项目本地目录，后者又优先于 `.worktrees/` 默认值。 |
| "工作区是全新的 —— 基线测试可以等等再跑" | 脏的基线会让之后的每一次失败都难以判断成因。现在就跑测试；带着失败继续推进是需求方的决定。 |
