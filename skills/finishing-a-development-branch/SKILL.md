# 开发分支收尾

## 概览

**核心原则：** 验证测试 → 检测环境 → 呈现选项 → 执行选择 → 清理。

**开始时宣布：**"I'm using the finishing-a-development-branch skill to complete this work."（我正在使用 finishing-a-development-branch 技能来完成这项工作。）

## Step 1: 验证测试

**免跑条件（先判，再决定跑不跑套件）：** 台账存在集成验证出口凭据（「已声明层全绿」或「带残留继续」）、凭据的 HEAD 与当前 HEAD 一致、工作区干净（`git status --porcelain` 为空）——三判据全部满足 → 免跑全量套件，直接进入 Step 2。任一不满足 → 照跑全量测试套件（单测层兜底）；其中凭据存在但 HEAD 不一致或工作区不干净的，移交「集成验证结果过期」事实——验证结论不再可信，需求方可指示重跑 superpowers:integration-verification。免跑不降门槛：出口凭据视同全绿——凭据三判据满足时，菜单出现所需的「套件全绿」条件即视同成立。

运行项目的完整测试套件（`npm test` / `cargo test` / `pytest` / `go test ./...`）。

**如果测试失败**，报告失败项并停下 —— 菜单要等测试套件全绿之后才出现：

```
测试失败（<N> 处）。必须先修复才能收尾：

[Show failures]
```

**如果测试通过：** 继续进入 Step 2。

## Step 2: 检测环境

```bash
GIT_DIR=$(cd "$(git rev-parse --git-dir)" 2>/dev/null && pwd -P)
GIT_COMMON=$(cd "$(git rev-parse --git-common-dir)" 2>/dev/null && pwd -P)
# 现在就捕获，趁还在工作区里 —— Step 5 会改变目录，
# 而之后的清理（Step 6）需要这个值
WORKTREE_PATH=$(git rev-parse --show-toplevel)
```

这一步决定呈现哪个菜单，以及清理如何进行：

| 状态 | 菜单 | 清理 |
|-------|------|---------|
| `GIT_DIR == GIT_COMMON`（普通仓库） | 标准 3 项选项 | 没有工作树需要清理 |
| `GIT_DIR != GIT_COMMON`，具名分支 | 标准 3 项选项 | 按工作树来源判定（见 Step 6） |
| `GIT_DIR != GIT_COMMON`，detached HEAD | 缩减为 2 项选项（无合并） | 外部管理 —— 原地保留 |

## Step 3: 确定基准分支

基准分支是这项工作从哪里分叉出来的 —— 通常在计划、对话或该分支的上游中已有指明。如果尚不确定，就问："这个分支是从 <your best guess> 分出来的 —— 对吗？"合并前先确认：合并到错误的基准分支代价很高，难以撤销。

## Step 4: 呈现选项

**普通仓库和具名分支工作树 —— 恰好呈现这 3 个选项：**

```
实现已完成。你想怎么做？

1. 本地合并回 <base-branch>
2. 推送并创建 PR
3. 保持分支原样（我稍后自行处理）

选哪一项？
```

**detached HEAD —— 恰好呈现这 2 个选项：**

```
实现已完成。你正处于 detached HEAD 上（外部管理的工作区）。

1. 推送为新分支并创建 PR
2. 保持原样（我稍后自行处理）

选哪一项？
```

菜单必须逐字呈现 —— 保持简洁，且每个选项都来自上面的列表。丢弃工作成果只在需求方明确开口要求时才会发生（见下文"如果需求方要求丢弃工作成果"一节）。等待需求方的回答；集成的决定权在需求方。

## Step 5: 执行选择

### 选项 1：本地合并

基准分支为 main/master 时，先做并入登记再合并：按下方「验证方案并入」小节把登记册三态登记提交到特性分支，然后才执行这里的合并命令——merge commit 使「功能代码 + 登记册更新」原子到达基准分支。

合并一律在基准分支所在工作树内执行，不切换主仓库检出（并行工作树世界里基准分支常驻自己的树，checkout 会被 git 拒绝）。前置检查：基准树必须干净（`git status --porcelain` 为空）；脏则停下，移交需求方协调——先提交或暂存。基准分支无专属工作树（罕见：仅基线检出）时，在基线检出执行——合并属集成动作，基线检出承载它合法。

```bash
# 在基准分支所在工作树内执行；该树已检出基准分支时不需要 checkout
git pull
git merge <feature-branch>

# 在合并结果上验证测试
<test command>
```

合并移动了基准分支 HEAD → 告知该分支会话「HEAD 已前移，既有验证凭据失效」。凭据新鲜度判据（HEAD 一致性）会自动拦截免跑，此处补的是告知义务：送达载体为合并提交信息注明，或控制者台账行，二选一或并用。

如果合并结果上测试失败：停下，工作树和分支都留在原地，然后排查 —— 什么都没有推送过，合并只发生在本地，可以恢复。

合并结果全绿后：清理工作树（Step 6），然后删除分支：

```bash
git branch -d <feature-branch>
```

### 选项 2：推送并创建 PR

推送之前先做并入登记：按下方「验证方案并入」小节把登记册三态登记提交到特性分支（基准分支为 main/master 时），登记提交随分支一起推送、随 forge 的合并原子到达基准分支。

```bash
git push -u origin <feature-branch>
# 从 detached HEAD 出发时，为远程上的新分支命名：
# git push origin HEAD:refs/heads/<new-branch>
```

然后用 forge（代码托管平台）自带的工具链，针对 <base-branch> 创建 pull/merge request：forge 有 CLI 就用 CLI，没有 CLI 就用多数 forge 在推送时打印的创建 URL。仓库里有 PR 模板和惯例就遵循。最后把 URL 报告给需求方。

保留工作树 —— 需求方会在那里根据 PR 反馈继续迭代。

### 选项 3：保持原样

报告："保留分支 <name>。工作树保留在 <path>。"

### 验证方案并入（基准分支为 main/master 且选「本地合并」或「推送并创建 PR」时）

前置条件：基准分支为 main/master，且需求方在菜单选「本地合并」或「推送并创建 PR」。两条件同时满足时，在合并/推送之前、仍在特性分支上把本次需求级验证方案（`docs/superpowers/specs/<date-feature>/verification.md`）并入项目级方案文件集 `docs/superpowers/verification/`，并作为一次提交落在特性分支上：逐场景按登记册条目格式（`- <场景id> | <层级 L1|L2|L3|兼容> | <资产路径> | <状态 normal|待合并|已知不修> | <期望一句话>`）三态登记进对应模块的 `modules/<module>.md` 或跨模块的 `cross-module.md`——新增（新场景）、合并（与既有场景覆盖面重复）、废弃（本次需求推翻既有行为 → 条目直接移除，不留记录）；登记册尚不存在时先初始化。登记提交先行落地，随后的 merge commit（或 forge 的合并）使「功能代码 + 登记册更新」原子到达 main/master。资产不在基线的场景状态标注「待合并」——不计为回归失败，回归报告单列呈现；「待合并」仅适用于回归时资产路径在基线不可定位的其他情形。

**并入净结果登记（发生并入事件时）：** 登记范围不是「本需求一份」，而是规格目录下全部方案的净结果集 =（源方案 ∪ 目标方案 ∪ 合并文件新增）−（被取代 ∪ 废弃），逐条按登记册行格式三态登记；多次并入按合并时间序滚动合成，每个合并事件文件在前一净结果之上做增量修订，终态为登记输入。影响分析四态到登记三态的映射：仍适用与新增 → 按新增登记；被取代 → 按新增登记、期望取合并文件新版本并注明出处；废弃且覆盖面已被包含 → 按「合并」语义不单独登记；废弃且行为已不存在 → 不登记（若已在册则移除）。基点非基线分支（并入他分支）的收尾：不登记、不归档；无方案需求（集成面判据不满足）：无可登记条目，登记册零改动，归档照走。

登记册写操作串行，不接受并行并入：写入前先同步基线上的最新登记册；仍有冲突时，能机械判定的合并（互不重叠的新增条目）自行处理，覆盖面重叠或同场景相冲突的非机械合并，与需求方讨论后决定。

基准分支不是 main/master，或需求方选「保持分支原样」不并入——按原流程走，方案留作分支上的需求级文档，也不做规格目录归档。detached HEAD 的两项菜单同理对应：「推送为新分支并创建 PR」→ 基准分支为 main/master 时按上述时序并入，「保持原样」→ 不并入。

### 合并事件记录（基准分支为另一 feature 分支时）

触发：收尾时基准分支为另一 feature 分支且需求方选「本地合并」——合并执行后当场在吸收分支新建规格目录 `docs/superpowers/specs/<日期>-merge-<源主题>-into-<目标主题>/`，内含一个验证方案文件；主题缩写从现行规格目录命名惯例推导。

文件两部分：

1. **合并事件记录：** 源分支、目标分支、日期、动机一句。
2. **影响分析：** 对源、目标既有场景逐条四态判定——仍适用（行为与期望均不变）；被取代（行为仍在但期望或判据因并入改变，新期望写入本文件、场景由本文件承载执行）；废弃（行为已不存在或其覆盖面被他场景完全包含，场景退出净结果集并写明取代行为）；新增（合并产生的组合行为无既有场景覆盖，新场景写入本文件执行）。

源与目标的原方案文件零字节改动——各自忠实记录各自门槛时验证了什么。影响分析四态判定随合并完成报告呈现需求方，异议则修订后继续。

吸收分支工作树脏 → 停，移交需求方协调（先提交或暂存）。

**PR 路径补检：** 选「推送并创建 PR」时不当场建；吸收分支收尾、并入登记前补检——发现外来规格目录无对应合并事件文件 → 从合并历史推导补建。

**HEAD 前移告知：** 本地合并移动了吸收分支的 HEAD——合并完成后告知吸收分支会话「HEAD 已前移，既有验证凭据失效」（送达载体：合并提交信息注明，或控制者台账行，二选一或并用）。

合并事件目录随吸收分支收尾时的规格目录归档全量移动（现状规则覆盖，无需新动作）。

### 规格目录归档（合并到 main/master 执行后）

feature 分支合并到 main/master 执行后，把 `docs/superpowers/specs/` 下全部内容原样移入 `docs/superpowers/archived/`——`<date-feature>` 目录照搬、遗留平面文件照搬，不要求先按新目录结构规范化；specs/ 清空，下次需求从空目录开始。归档移动并提交：

```bash
if [ -n "$(ls -A docs/superpowers/specs 2>/dev/null)" ]; then
  mkdir -p docs/superpowers/archived
  git mv docs/superpowers/specs/* docs/superpowers/archived/
fi
```

- **本地合并（选项 1）**：合并执行后当场归档——上方命令移动全部内容并提交。
- **推送并创建 PR（选项 2）**：推送时不归档——工作流不感知 forge 的合并事件；由下次 feature 分支合并到 main 时全量归档顺带完成。

「保持分支原样」与丢弃路径不归档——specs/ 内容留在原地。

### 分支纪律

三条纪律逐条约束每一笔新改动：

- **`docs/superpowers/archived/` 归档后冻结，零改动。** 今后的设计决策随新 feature 的 `docs/superpowers/specs/<date-feature>/design.md` 走完整工作流，不回写已归档文档。
- **main/master 只承载集成动作，不直接开发。** 集成动作指分支合并、验证方案并入登记册、合并事件文件落盘、基线分支快进、规格目录归档移动。任何开发性改动不得直接在 main/master 上提交——先开特性分支再动手。
- **改动二分。** 每一笔新改动要么是新 feature（新建 `docs/superpowers/specs/<date-feature>/` 目录，走 brainstorming → writing-plans → 收官把关 → 集成验证 → 收尾完整工作流），要么是 bugfix（修复 main/master 上已交付内容的缺陷——无新需求文档，合并前同样过收官把关与集成验证门槛）。不存在第三类。

三规则的上位载体：设计决策（存放位置与改动分类）归 brainstorming 技能；main/master 不直接开发由执行技能的工作区前置约束兜底——subagent-driven-development 与 executing-plans 均已含「实施只能在本需求分支上」。

上位载体：改动分类与两路径路由见 superpowers:using-superpowers 技能优先级；archived 冻结的存放策略见 superpowers:brainstorming 存放位置。

### 如果需求方要求丢弃工作成果

只有在需求方明确要求丢弃时，才会走这条路径。先确认：

```
这将永久删除：
- 分支 <name>
- 全部提交：<commit-list>
- 位于 <path> 的工作树

输入 'discard' 以确认。
```

必须等到需求方键入 'discard' 这个确切的词。收到后：

```bash
MAIN_ROOT=$(git -C "$(git rev-parse --git-common-dir)/.." rev-parse --show-toplevel)
cd "$MAIN_ROOT"
```

然后清理工作树（Step 6），并强制删除分支：

```bash
git branch -D <feature-branch>
```

## Step 6: 清理工作区

**仅适用于选项 1 和已确认的丢弃。** 选项 2 和 3 总是保留工作树。走到这里的路径此时都已位于该工作树之外（本地合并：基准分支所在工作树内或基线检出；丢弃：主仓库根目录）——移除工作树的命令必须在当前目录位于工作树之外的前提下运行——并使用 Step 2 中捕获的 `GIT_DIR`/`GIT_COMMON`/`WORKTREE_PATH` 值，也就是目录切换之前捕获的那些值。

**如果 `GIT_DIR == GIT_COMMON`：** 普通仓库，没有要清理的工作树。完成。

**如果 `WORKTREE_PATH` 位于 `.worktrees/` 或 `worktrees/` 之下：** 这个工作树是 Superpowers 创建的 —— 清理由我们负责：

```bash
git worktree remove "$WORKTREE_PATH"
git worktree prune  # 自愈式：清理任何失效的注册项
```

**如果移除被拒绝**（`contains modified or untracked files`）：工作树里有别处不存在的文件 —— 未提交的计划、笔记或随手记录的工作内容。绝不自作主张使用 `--force`。把利害关系展示给需求方并询问：

```bash
git -C "$WORKTREE_PATH" status --porcelain -uall
```

```
工作树移除被拒绝 —— 这些文件从未提交过：

<file list>

1. 清理前把它们提交到 <branch>
2. 把它们移入 <main repo root>
3. 删除它们（不可恢复）

选哪个？
```

执行所选操作，然后移除工作树。

**否则：** 这个工作区归宿主环境所有 —— 原地保留。如果你的平台提供了退出工作区的工具，就使用它。

## 速查表

| 选项 | 合并 | 推送 | 保留工作树 | 清理分支 |
|--------|-------|------|---------------|----------------|
| 1. 本地合并 | yes | - | - | yes |
| 2. 创建 PR | - | yes | yes | - |
| 3. 保持原样 | - | - | yes | - |
| 丢弃（仅限明确要求） | - | - | - | yes（强制） |

## 常见合理化借口

| 借口 | 现实 |
|--------|---------|
| "本次会话早些时候测试已通过" | 要对你即将集成的代码树运行测试套件。一次全绿只能证明当时被测的那棵代码树没有问题。 |
| "他们显然想合并它" | 集成是需求方的决定。呈现菜单并等待。 |
| "他们看起来已经完成这个功能了 —— 我来主动提出丢弃它吧" | 上面呈现的菜单就是全部选项。丢弃只在需求方明确说出口时才发生。 |
| "'嗯，把它删掉吧'就算确认了" | 只有键入的单词 `discard` 才能授权删除。 |
| "PR 已经提了，工作树现在是累赘" | PR 反馈的修复就在那个工作树里做。在工作落地之前，这个工作树一直保留。 |
| "另一个工作树看起来已废弃 —— 我顺手也清理掉" | 只清理 `.worktrees/` 或 `worktrees/` 下的工作树。其余一切都归宿主所有。 |
| "移除被拒绝 —— `--force` 只是把清理做完而已" | 拒绝意味着有些文件只存在于那个工作树里。`--force` 会永久销毁它们。把文件清单展示给需求方并询问。 |
| "合并结果的失败多半是偶发的" | 合并结果失败会让一切停摆。排查期间分支和工作树原地不动。 |
| "基准分支显然是 main" | 确认分叉点或直接询问。合并到错误的基准分支代价很高，难以撤销。 |
| "推送被拒了 —— 强推就能解决" | 推送被拒意味着远程已有变动。先排查；只有需求方明确要求时才强推。 |
