# 编写计划

## 概述

为一名没有见过这个代码库、也没有见过这份设计文档的工程师撰写实施计划。假设他们一旦知道了确切的接口、确切的边界条件与确切的验收标准，就能用项目的语言写出地道的代码；并且凡是计划留出开放选择的地方，他们都会做出合理的选择。他们无法知道的是你决定了什么：哪些文件、哪些名称与签名、设计文档中的哪些取值、哪些边界条件与验收标准证明每个任务。把这些写进文档。把整份计划拆成任务交给他们。DRY。YAGNI。TDD。频繁提交。

**计划有两类读者：** 审阅它、决定是否开工的需求方，以及执行它的工程师。计划头部与约束章面向需求方；任务规格面向执行者，但表述必须可判真伪，让需求方也能抽查。

**计划固定五章：** 改动地图、功能单元规格、设计依据、约束、风险清单。完整骨架、逐章内容要求与写作要求见 `references/plan-template.md`。计划只适用于软件项目；非软件项目止于设计文档。

**开始时宣告：**「我正在使用 writing-plans 技能来创建实施计划。」

**上下文：** 如果在隔离的工作树中工作，该工作树应当已由 `superpowers:using-git-worktrees` 技能在开始执行本计划时创建。

**计划保存到：** `docs/superpowers/specs/<date-feature>/plan.md`（`<date-feature>` = `YYYY-MM-DD-<主题>`，目录随需求建立；设计文档在同目录 `design.md`）
- 同目录同时产出 `verification.md`（需求级验证方案，触发判据见「范围检查」）——design.md / plan.md / verification.md 同目录三件套。
- （需求方对计划存放位置的偏好覆盖此默认值）

## 范围检查

如果设计文档覆盖了多个相互独立的子系统，它本应在头脑风暴阶段就被拆成子项目级的设计文档。如果没有拆，就建议把它拆成多份独立的计划——每个子系统一份。每份计划都应当能独立产出可运行、可测试的软件。

计划只适用于软件项目。收到非软件项目时，拒绝并返回设计阶段，不要套模板产出空章计划。

计划存在跨任务组装点或触及外部接口 → 同目录另产出验证方案文件 `verification.md`；载体、内容六项与质量判据见 `references/plan-template.md`「验证方案文件」段。纯单模块无接口的计划不加——不加时不产出该文件，plan.md 只含五章骨架与固定块。

## 文件结构

在定义任务之前，先梳理出将创建或修改哪些文件、每个文件各负责什么。任务如何分解，就在这一步敲定。

- 以清晰的边界和定义良好的接口来设计各个单元。每个文件应当只有一个明确的职责。
- 当代码能一次性放进上下文时，你的推理效果最好；当文件足够专注时，你的编辑也更可靠。宁选更小、更专注的文件，也不要承担太多职责的大文件。
- 一起变动的文件应当放在一起。按职责拆分，而不是按技术分层拆分。
- 在既有代码库中，遵循既有的模式。如果代码库用的就是大文件，不要单方面重构——但如果你正要修改的某个文件已经臃肿到难以驾驭，在计划里安排一次拆分是合理的。

这个结构为任务分解提供依据。每个任务都应当产出自包含、独立来看也成立的改动。

## 任务规模划定

任务是携带着自身测试循环、且值得由一名全新审查者单独把关的最小单元。划定任务边界时：哪项任务产出的交付物需要准备、配置、脚手架和文档类的工作，就把这些工作并入该任务；只有当审查者可能实质性地否决某个任务、却同时批准其相邻任务时，才在该处拆分任务边界。每个任务都以一个可独立测试的交付物收尾。

## 任务详细度

任务写到「边界条件 + 验收标准」为止。TDD 的红绿循环——写失败测试、运行确认失败、实现最小代码、运行确认通过、提交——由执行者按 superpowers:test-driven-development 从验收标准自行展开，**不在计划中预写**。

预写测试代码与实现步骤，等于把代码誊进计划：一份比它所描述的代码还长的计划是誊抄，不是计划。

## 计划文档骨架

完整骨架、逐章内容要求、任务结构与写作要求见 `references/plan-template.md`。写计划前先读它。

计划固定五章：

1. 改动地图
2. 功能单元规格
3. 设计依据
4. 约束
5. 风险清单

五章之外固定三块：开头的元数据（目标、架构、技术栈、设计文档路径、实施前决策记录 + 日期）；末尾的执行交接（执行方式、必需子技能、确认要求）；最末的独立审读处置记录附录（审读者身份、问题清单、逐条处置）。

计划是实施前的决策记录；实施后的结论由提交信息承载，计划本身不回填。

## 任务结构

每个任务用 `### Task N: <单元名>` 标题，写职责句加四段：Files、Interfaces、边界条件、验收标准；编码多路径流程的任务在 Interfaces 与边界条件之间加流程图。完整格式与示例见 `references/plan-template.md`。

任务写到「边界条件 + 验收标准」为止。TDD 的红绿循环由执行者按验收标准自行展开，不在计划中预写。

## 一个任务包含什么

当实施者依据一个任务只能写出一种合理的实现时，这个任务就算写到位了。这就是全部的要求：无歧义，而非完备。

- **Files / Interfaces：** 决策的落点——路径、签名、类型，逐字写。
- **边界条件：** 触发条件与失败行为，写成可判真伪的命题。禁止「适当处理」「必要时」「等等」这类不可判真的措辞；重要行为给 ❌/✅ 对照（❌「超长输出会被妥善处理」/ ✅「超过 30000 字符截断至 30000 并追加截断说明」）。任务触及既有代码时，边界条件写明「不得改变的既有行为」清单——它是执行者写特征测试的锁定来源；锁定范围的知识在你（计划者）手里，不写，执行者只能自己推断。
- **验收标准：** 测试要证明什么，不是测试代码本身。只有当验收标准推不出测试的写法（算法不由行为决定）时，才附一段测试思路说明。
- **对另一个任务的引用：** 被引用任务的 Interfaces 块写明要用什么；计划不重复那个任务的代码。

计划是实施者无法独自做出的那批决定的集合。什么都不决定的行（"TBD"、"处理边界情况"、"加上恰当的校验"、没有任何任务加以定义的类型或函数）是缺口；预写的测试代码与函数体（凡是验收标准与签名已能确定的）是誊抄。这两种失败自审都要抓出来。

## 自审

写完整份计划之后，用新视角重读设计文档，并对照它检查计划。这份清单由你自己来跑——不要派发子代理去做。

**1. 设计文档覆盖：** 略读设计文档中的每个小节、每条需求，特别是功能清单与「明确不做」清单。你能指出实现它的是哪个任务吗？把缺口列出来。

**2. 单元五问：** 每个任务自检五问——输入是什么、输出是什么（→ Interfaces）、边界在哪（→ 边界条件）、失败时行为是什么（→ 边界条件的失败路径条目）、拿什么证明（→ 验收标准）。五问齐备，任务即完整。

**3. 类型一致性：** 你在后面任务中用到的类型、方法签名和属性名，与你在前面任务中定义的一致吗？同一个函数在 Task 3 里叫 `clearLayers()`，到 Task 7 却叫 `clearFullLayers()`，这就是个 bug。

**4. 边界条件承接原「审查重点」的职能：** 对设计文档暗示的每一类输入或失败模式，是否有一个任务的边界条件与验收标准覆盖到了它？其中最容易坑到使用者的几类，补进最贴切任务的边界条件，并各配一条验收标准。全部覆盖了就不需要补——但这个检查必须真的做过。

**5. 比例：** 把计划的长度与设计文档的长度作比较。一份比它所实现的设计文档长出好几倍的计划，是程序的誊抄，而不是计划。如果测试代码或函数体出现在计划里，把它们换成边界条件与验收标准的措辞。

**6. 行为可判真伪与锚定：** 计划中的每条行为描述都能判真伪吗？引用既有代码或既有测试、描述其行为的地方，能在代码或测试中指到对应吗？指不到即臆写——去读代码，不要凭记忆写。

**7. 五章完整与写作要求：** 改动地图、功能单元规格、设计依据、约束、风险清单五章是否齐全？设计依据是否给了取舍论证？风险清单是否写了触发条件、影响、缓解？七条写作要求是否满足？计划是否只做实施前决策记录，没有混入实施后的内容？

**8. 实现效果：** 按任务顺序做完，设计文档功能清单的每条「输入 → 最终用户看到什么」是否真的会出现？把任务串起来看依赖、接口契约与集成点；每个任务都通过、组合起来却不工作的缺口，在这里抓。

**9. 接口可测性：** 对每个 Interfaces 块推演它的第一条测试调用——需要 mock 框架级设施才能调用吗？只断言可见行为能否覆盖该任务的验收标准？推演不出来、或必须重型 mock 才能调，就是可测性缺口：回「文件结构」改接口。可测性缺口在计划期修最便宜；这道检查没有人工兜底（确认门审的是忠实性，不是可测性），独立审读会再做一遍（见独立审读），但你是第一道。

**10. 验证方案专项：** 计划产出 verification.md 时逐项核对——四性逐查（出处锚定、双向映射、粒度判据、可操作性判据）、内容要求六项逐查（确定性固定策略、保真度声明、副作用隔离、顺序依赖显式化、既有登记册查重、失败证据采集）、出处抽查、双向映射核对。

发现问题就原地修。无需重新审查——修完就继续前进。发现设计文档的某条需求没有对应任务，就补上那个任务。

## 独立审读

保存计划并完成自审后、提交需求方确认前，先运行 `bash scripts/check-tables.sh <设计文档路径> <计划路径>`、`bash scripts/check-mermaid.sh <设计文档路径> <计划路径>` 与 `bash scripts/check-doc-structure.sh <设计文档路径> <计划路径>`，按输出修复表格列错位、mermaid 红线违规与结构槽位缺损（无该脚本环境时，由审读提示词中的排版核对兜底）；然后做一次独立审读：派一个未参与写作的全新子代理，使用本目录下的 `review-prompt.md`，同时阅读设计文档与计划，输出三张清单：完备性问题、可读性问题与实现效果问题。

返回后按顺序处置：

1. 先处置完备性问题：能由文档或项目回答的，写进计划；次要的，你自己敲定并在计划中标注这是你的决定；归需求方的，一次性带给需求方——连同你的建议答案在对话中呈报，需求方裁决前不得把答案写成已处置（计划只留「待需求方裁决」占位），裁决后按裁决结果写入。
2. 再处置实现效果问题：审读者判定「有疑问」或「不能达成」的，修订计划，或书面说明为何不改；若暴露出设计本身不可行，回到设计确认门。
3. 若补写了实质内容，把新增或改动段落交回同一个子代理快速复读。
4. 再处置可读性问题与复读新发现的问题：修订，或书面说明为何不改。
5. 把审读者身份（子代理/自审）、问题清单与逐条处置写入计划附录。

全部处置完毕，才能把计划提交需求方确认。没有子代理工具时，由你亲自使用同一份提示词自审，在附录标注「自审」，并告知需求方本次没有独立审读。

<HARD-GATE>
设计文档已在此前获批，是计划的既定基础；本步的确认对象是**计划**。在需求方明确确认计划之前，不得开始实施：不调用执行类技能，不创建工作区，不派发实施者——阅读和探索没有问题。

若撰写中发现设计层面必须改动（功能不可行、成本过高、依赖缺失）——回退规则：修订设计文档，回到该设计文档的确认环节重新确认，再回来修订计划。禁止只改计划悄悄绕过。确认意见若导致计划修订，修订后重新提交；确认前这个环节不关闭。

计划已确认、实施已开始后发现设计必须改：停止实施，回到设计确认门；返工还是回滚由需求方决定；已合入 main 的部分用新提交修正，不改写历史。
</HARD-GATE>

## 执行交接

同时按判据给出执行方式的建议：

- **子代理驱动（Subagent-driven）** ——任务边界清晰、每个任务都能写出稳定验收标准的计划，适用于这种方式。每个任务由一名全新的子代理实施，在下一个任务开始之前由一名全新审查者检查，最后再做一次整分支终审。最彻底；每个任务与每次审查各要消耗一份全新上下文。
- **会话内执行（Native）** ——强耦合的小改动、探索性强到写不出稳定验收标准的任务，适用这种方式。由你（原计划者）在本会话中亲自实施每一个任务，然后由一名运行在最强档模型上的全新审查者检查整个分支。最便宜也最快；直到最后才有一次独立审查。

**「计划已完成并保存到 `docs/superpowers/specs/<date-feature>/plan.md`。请审查：各任务的边界条件与验收标准是否忠实覆盖了设计文档的功能清单与「明确不做」清单。明确确认后，选择执行方式：子代理驱动，还是会话内执行？**

**对这份计划，我推荐 <one of the two>，理由是 <one sentence from the plan: how much the tasks depend on each other's interfaces, how many there are, what a shipped mistake would cost>。」**

**已给定执行方式时：**

**「计划已完成并保存到 `docs/superpowers/specs/<date-feature>/plan.md`。它是否忠实体现了设计文档？请确认。」**

**若选择了子代理驱动：**
- **必需子技能（REQUIRED SUB-SKILL）：** 使用 superpowers:subagent-driven-development

**若选择了会话内执行：**
- **必需子技能（REQUIRED SUB-SKILL）：** 使用 superpowers:executing-plans
