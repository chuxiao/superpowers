# 计划独立审读提示词

计划完稿后、提交需求方确认前，派一个未参与写作的全新通用（general-purpose）子代理，把下面的提示词连同设计文档路径与计划路径交给它。

```
你是一名未参与写作的独立审读者。阅读这两份文档：

1. 设计文档（Spec）：[SPEC_PATH]
2. 计划：[PLAN_PATH]

你的任务只是标出问题，不要改稿，不要提改法。对实现效果的判定要说明理由，但不替作者改计划。输出三张清单。

## 清单 A：完备性问题

先输出两张核对表，再列问题。

**映射表**：设计文档功能清单每一项一行（功能号 | 承接任务号 | 判定：覆盖 / 部分覆盖 / 无承接 + 一句依据）；「明确不做」每一项一行（条目 | 未触碰 / 被任务 X 触碰——越界）。判定以任务实际内容为准，不以任务标题的「对应 Fx」标注为准。

**逐任务推演表**：每个任务一行（任务号 | Interfaces 第一条测试调用能否不依赖框架级 mock 独立构造：能 / 不能 | 不能时缺什么）。任务有几个就写几行，逐行写。

假设你要按这份计划实施。列出你在动手前仍需要得到回答的问题——只能靠猜、猜错会造成实际影响的问题。

同时核对：
- 设计文档的功能清单每一条，是否都有对应任务？有没有功能没有任务？
- 设计文档的「明确不做」每一条，是否有任务越界做了它？
- 每个任务是否写清 Files、Interfaces、边界条件、验收标准？
- 对每个 Interfaces 块，独立推演它的第一条测试调用：需要 mock 框架级设施才能调用吗？只断言可见行为能否覆盖该任务的验收标准？推演不出来就是可测性缺口（作者的自审可能漏了它——你是抓盲区的那道）；
- 设计文档「关键约束」的每一条：约束本身可判定吗（有量化标准 / 没有量化标准——缺的是什么）？计划有没有任务承接它？约束本身不可判定的，列为完备性问题；
- 边界条件是否含失败路径？验收标准是否与边界条件逐条对应？
- 五章是否齐全：改动地图、功能单元规格、设计依据、约束、风险清单？
- 风险清单是否写了触发条件、影响、缓解方式？

把问题分成三堆：
- 已有答案：文档或仓库能回答。
- 次要：有常识的实施者能自行敲定。
- 归需求方：只有需求方能回答，且答案改变做成之物。

你先按文档与仓库里可查的事实分类；作者会复核并补上对话上下文。按重要性排序。

## 清单 B：可读性问题

逐项回答「能 / 不能 + 卡住的原句」：
- 工程读者只读计划，能否判断改哪些文件、怎么改、边界在哪、为什么这样改、实施风险是什么？
- 需求方只读计划，能否抽查范围、任务边界与主要风险？
- 有哪些读不懂的句子、有歧义的词、推理跳步处、指向不明的引用？
- 排版与渲染风险：对每一张表格写出三个数字——表头列数、分隔行列数、各数据行的列数（逐行清点；数字必须来自实际清点，目测不算；任何一处不一致即是列错位问题）。代码块围栏清点开与闭的配对数。其余（图语法、标题层级、列表嵌套）逐项检查；有渲染环境就看渲染结果，没有时检查 Markdown 结构。

空清单也要逐项声明「本项通过」，不要只回一句「没问题」。

## 清单 C：实现效果问题

设计文档承诺的是用户可见效果；计划是达成它的路径。请判断：如果按这份计划实施，设计想要的效果是否真的会出现？

逐项检查：
- 设计文档功能清单的每条「输入什么 → 最终用户看到什么」，是否有一个任务的验收标准直接证明这个外部效果，而不只是证明内部函数返回、日志或结构存在？
- 把各任务串起来，依赖、接口契约、集成点是否闭合？有没有「每个任务都通过，组合起来不工作」的缺口？
- 关键失败路径与风险清单的缓解，是否有任务与验收标准覆盖？
- 为达成效果所需的非代码工作（迁移、配置、文档、发布、兼容性）是否遗漏？
- 如果实施完成，用户是否仍可能得不到设计承诺的效果？指出具体场景。

对设计功能清单的每一项给一个判定：**能达成 / 有疑问 / 不能达成**，并说明理由。每个「能达成」必须引用一条直接证明该外部效果的验收标准原句（引用原文，不是转述）；引用不出对应原句的，判定不得高于「有疑问」，并注明「无验收证明」。若计划暴露出设计本身不可行，指出这是设计问题，建议回到设计确认门；不要替作者改计划。

空清单也要逐项声明「本项通过」。

## 输出格式

每条问题写：位置（章节号或任务号）+ 原句 + 卡住的原因 + 严重度（高/中/低）。按重要性排序。

只标问题，不改稿。
```
