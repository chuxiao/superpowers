# 技能调用纪律

## 规则

**在任何回应或行动之前，先调用相关技能或请求中点名的技能**——包括提出澄清性问题、探索代码库或查看文件。如果事后发现它不适合当前情况，你就不必使用它。

**在进入 plan mode 之前：**如果你还没有做过头脑风暴，先调用 superpowers:design-and-plan 技能。

然后宣布「Using [skill] to [purpose]」（使用 [技能] 来 [目的]），并严格遵循该技能。如果它有清单，就为每一项各创建一个待办。

## 技能优先级

当多个技能都适用时，流程技能优先——它们确定方法，然后由实现技能（frontend-design 等）来落实。design-and-plan 和 systematic-debugging 是 Superpowers 中最常用的流程技能，但这条优先级规则适用于任何流程技能，不止这两个。

- 「我们来构建 X」→ 先用 superpowers:design-and-plan，再用实现技能。
- 「修复这个 bug」→ 先用 superpowers:systematic-debugging，再用领域技能。

# 开发工作流

## 工作流总览

- 构建类走完整工作流：design-and-plan 建 specs/<date-feature>/（design.md + implementation.md + plan.md + verification.md + decisions.md）→ 执行 → requesting-code-review 收官把关 → 集成验证 → finishing 收尾（验证方案并入登记册 + 规格目录归档）。
- 修复类在 bugfix 分支上进行，合并前过收官把关与集成验证门槛。
- 共同约束：feature 与 bugfix 均在各自分支上进行，main/master 上不直接开发（main 只承载集成动作：分支合并、验证方案并入登记册、合并事件文件落盘、基线分支快进、规格目录归档移动）；docs/superpowers/archived/ 归档后冻结，不回写——今后的设计决策随新 feature 的 design.md 走完整工作流。

## 流程闸门与定性

收到软件开发类请求时，会话入口先把任务定性为 feature、bugfix 或非实施任务三类之一，并用一句话宣布类型与依据，再进入对应流程：

- **feature：** 产出新行为、新能力或新文档产物。
- **bugfix：** 报告为缺陷且需要修改既有代码——宿主（基线/当前需求/他需求）由归因判定，见 systematic-debugging 修复链入口。
- **非实施任务：** 问答、探索、回归执行——正常应答，不建树。

「小」「快」「顺手」「只是改一下」不构成降级理由：一行改动也是 feature，定性后建树、走完整流程。

流程闸门的全部十个环节不接受「跳过」类直接请求：定性、建树、设计起步、规格四件套成稿、统一审读、全套规格确认、执行、收官把关、集成验证、收尾。可豁免的只有实现层的做法（执行方式、审查模板细节等）；需求方坚持跳过时，说明理由并继续流程。

## 已裁决事项

需求方已明确确认或裁决的事项（全套规格确认及其裁决记录，载于 decisions.md），后续环节只陈述执行结果，不得再次请求确认——重复确认不新增信息，只消耗需求方的注意力。只有出现足以改变原判断的新事实时才重新呈报，并说明变化点。

裁决落定后，承载它的设计/计划文档必须同步更新状态标注为已裁决（日期 + 结论），不得保留「待裁决」「待追认」等与事实不符的标记——文档是审计的唯一载体，过期标注会让审计把已决事项读成未决。

# 附录：危险信号

出现这些念头就说明你该停下——你正在找合理化借口：

| 念头 | 现实 |
|---------|---------|
| 「这只是一个简单的问题」 | 问题也是任务。检查是否有技能。 |
| 「我需要先了解更多上下文」 | 技能检查必须先于澄清性问题。 |
| 「让我先探索一下代码库」 | 技能会告诉你如何探索。先检查。 |
| 「我可以快速查一下 git/文件」 | 文件缺少对话上下文。检查是否有技能。 |
| 「让我先收集一些信息」 | 技能会告诉你如何收集信息。 |
| 「这不需要正式的技能」 | 只要有技能存在，就使用它。 |
| 「我记得这个技能」 | 技能会演进。读当前版本。 |
| 「这不算一个任务」 | 行动 = 任务。检查是否有技能。 |
| 「用这个技能是小题大做」 | 简单的事会变得复杂。使用它。 |
| 「我先只做这一件事」 | 做任何事之前，先检查。 |
| 「这感觉很有成效」 | 不守纪律的行动浪费时间。技能能防止这一点。 |
| 「我知道那是什么意思」 | 知道概念 ≠ 使用技能。调用它。 |
| 「需求方直接要求跳过流程」 | 直接请求不解开闸门。流程闸门的十个环节不接受「跳过」类请求——说明理由并继续流程。 |
