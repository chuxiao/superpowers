# 写出好的测试

**何时加载本参考：**编写或修改测试、添加 mock，或为测试添加清理/辅助方法时。

## 概述

测试的存在是为了捕捉某一特定的破坏。这里的一切都由两条原则支配：

```
1. 每个测试都点名它要捕捉的破坏
2. 每个测试都实际运行真实实现
```

严格的 TDD 会自然而然地同时产出这两者：先写测试，并亲眼看着它在真实代码上失败——这样的测试已经证明了自己能够失败；而只有当真实依赖被证明缓慢或属于外部依赖时，它才配得到一个 mock。

## 原则 1：点名要捕捉的破坏

在写测试体之前，先回答：**什么样的生产代码改动应该让这个测试失败——以及那个改动是一个 bug，还是一个决定？**测试要靠捕捉走错的分支、缺失的副作用、错误的参数、边界情况或被破坏的契约，才配占有一席之地。

**独立推导期望值。**使用字面量和人工核验过的夹具（fixture）；带字面量 `want` 值的表驱动测试是首选形态。由被测代码——或它的辅助函数——推导出的期望值，无论那段代码做什么都会通过：

```typescript
// ❌ 镜像断言：两侧由同一个构建器算出——永远为真
const expected = buildSearchQuery({ tag: 'urgent' });
expect(buildSearchQuery({ tag: 'urgent' })).toBe(expected);

// ✅ 手工推导的字面量
expect(buildSearchQuery({ tag: 'urgent' })).toBe('tag:"urgent"');
```

**不要做变更检测器。**如果一个测试只能被刻意的决定弄失败——某个常量的值、消息的精确措辞、私有结构——那它会在重新设计时误触发，却在 bug 面前沉睡。要测的是依赖于该决定的行为：不是 `expect(MAX_RETRIES).toBe(5)`，而是“一次失败的调用会被重试 5 次，而第 6 次尝试永远不会发生”。

**测行为，不测文本。**断言某个脚本、技能或配置文件包含某一行精确文本，只能证明源码还是那份源码。让脚本在受控输入下运行，断言其输出、副作用或退出码。给 agent 下指令的文档，要靠读取该文档的 agent 的行为来测试（superpowers:writing-skills）；写给人看的散文根本不配得到测试。

**测你的代码，不测框架。**测试你的代码在其边界上立下的契约——你注册的路由、你发出的查询、你产出的载荷。上游机制自有其维护者去写测试（经典反例：断言你的路由器会调用已注册的处理器——那是框架的测试，不是你的）。当上游行为真正让你意外时，写一个窄范围的特征测试（characterization test），点名那个假设。同样的边界也适用于你的代码内部：构造器、getter、常量和琐碎的转发，只有当它们做校验、规范化、填默认值、推导、强制约束或引发副作用时才配得到测试——否则就断言第一个对消费者可见、且依赖于它们的结果。

### 闸门检查

```
必须先写测试体，再写：
  说出能让这个测试失败的那个生产代码改动。

  说不出这样的改动           → 围绕可观察行为重新设计
  “只是源码文本变了”         → 运行该工件，断言其效果
  只有刻意决定能让它失败     → 变更检测器；改测依赖于
                                该决定的行为

  确认期望值是在不借助被测代码的情况下推导出来的。
  一旦它复用了被测代码的逻辑或辅助函数：
    改用字面量或人工核验过的夹具
```

## 原则 2：运行真实实现

**mock 不配拥有断言。**针对 mock 的断言，mock 在场时通过、mock 不在场时失败——它对组件的行为只字未提。要断言真实组件的行为；如果你检查的就是 mock 本身，那就解除 mock（unmock），或删掉这条断言。

```typescript
// ✅ 真实行为
expect(screen.getByRole('navigation')).toBeInTheDocument();

// ❌ mock 的存在
expect(screen.getByTestId('sidebar-mock')).toBeInTheDocument();
```

**需求方的纠正：**“我们这是在测试 mock 的行为吗？”

**在正确的层级上 mock。**替换真实方法之前，先弄清它的每一个副作用；mock 掉缓慢或外部的操作，测试所依赖的部分保持真实。拿不准时，先让测试跑在真实实现上，观察实际需要做哪些事。

```typescript
// ❌ mock 吞掉了重复检测要读取的那次配置写入
vi.mock('ToolCatalog', () => ({
  discoverAndCacheTools: vi.fn().mockResolvedValue(undefined)
}));

// ✅ 只 mock 缓慢的服务器启动；配置写入保持真实
vi.mock('MCPServerManager');
```

**让测试替身（doubles）足够具体。**当参数、调用次数或调用顺序属于契约的一部分时，要断言它们——来者不拒的假替身什么也验证不了。给每个分支（成功、出错、格式错误）各自配备夹具或 spy，让走错的分支无法满足期望。

**完整镜像真实数据。**mock 出真实世界中的完整结构——所有已文档化的字段——而不只是你的测试读取的那几个。当下游代码读取被省略的字段时，残缺的 mock 会无声地失败：测试照常通过，集成却已经断了。

**生产类只承载生产方法。**只有测试才需要的清理逻辑放在测试工具（test utilities）里，绝不要作为 `destroy()` 挂在生产类上。自问：这个方法是否只有测试在调用？这个类是否拥有该资源的生命周期？答案表明它不属于生产类 → 放进测试工具。

**优先真实组件，而非复杂 mock。**当 mock 的搭建在体量上超过测试逻辑、mock 缺少真实组件拥有的方法、或 mock 一变测试就断时，改用真实组件的集成测试。**需求方的问题：**“这里我们真的需要用 mock 吗？”

### 闸门检查

```
在添加 mock 或测试辅助工具之前：
  列出真实方法的副作用；测试所依赖的副作用保持真实——
  在其下层的缓慢/外部环节上打 mock。

  mock 响应须镜像完整的真实结构。

  只有测试才调用的方法，放进测试工具，不进生产代码。

  正准备对 mock 本身做断言？
    解除 mock，或删掉这条断言。
```

## 测试随实现一同交付

TDD 循环——失败测试、最小实现、重构——就是“完成”的判定标准。交付该行为所需要的测试，且只交付这些测试：琐碎代码与写给人看的散文一概不配得到测试，只为满足流程而写的测试会永久拖累维护。

## 变异检查

收尾之前，在脑中对生产代码做变异；每一种现实中可能的变异，都应至少让一个测试失败：

- 错误的常量或参数
- 错误的分支处理器
- 缺失的状态变更或副作用
- 空返回或默认返回
- 缺少对零值、空值、nil、未授权或格式错误输入的校验

没有任何测试能捕捉的变异，标志着该行为未受保护——或者说明你的测试是同义反复。

## 快速参考

| 当你…… | 做法 |
|-------------|-----|
| 写任何测试 | 点名它要捕捉的破坏——是一个 bug，不是一个决定 |
| 构建期望值 | 手工推导；绝不用被测代码推导 |
| 测试脚本或文档 | 运行它／压力测试它的消费者；绝不 grep 它的文本 |
| 想给依赖写测试 | 测你自己的边界契约，而不是它们已文档化的机制 |
| 想对被 mock 的元素做断言 | 测真实组件，或解除 mock |
| 正准备 mock 一个方法 | 先弄清它的副作用；在其缓慢/外部层级上打 mock |
| 构建 mock 响应 | 完整镜像真实结构 |
| 需要只有测试在用的清理逻辑 | 放进测试工具 |
| 眼看 mock 搭建膨胀 | 改用真实组件的集成测试 |
| 完成一个测试文件 | 跑一遍变异检查 |

## 危险信号

- 搭建与断言共用同一个对象，相等因此成为必然
- 测试只能通过 panic、崩溃或选择器缺失才会失败
- 测试在每次刻意变更时失败，却从不在意外破坏时失败
- 期望值藏在循环、构建器或辅助函数背后
- 测试 grep 源码文本，或断言某个已移除的符号保持移除状态
- 假如删掉你的代码、只剩框架，这个测试依然有意义
- 测试为覆盖率而存在，却不检查任何副作用或结果
- 断言检查的是 `*-mock` 测试 ID，或者移除 mock 后测试就会失败
- 某个方法只有测试文件在调用
- mock 搭建占了测试的一半以上，或者说不出为什么需要这个 mock
- 为了“保险起见”而 mock
