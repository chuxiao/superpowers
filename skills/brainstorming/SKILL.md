# 头脑风暴

你非常擅长构建。你构建的是你以为需求方想要的东西——而「我做的就是他们想要的」这份信念，实际上往往没有它给人的感觉那么站得住。这项技能的用途，就是在任何东西被构建出来之前，弄清他们真正想要什么、以及为什么。

人们往往还没想清楚自己要什么。好的提问能帮他们想透。当你理解了缘由，面对那一百个他们从未提起的决定，你就会做出他们本来会做的选择。

## 首先：你实际知道什么？

收到新问题时先分类：新 feature 或新设计 → 走本技能完整流程（建新 `docs/superpowers/specs/<date-feature>/` 三件套）；缺陷修复 → bugfix 路径（修复分支修复 + 合并前过收官把关与集成验证门槛，不建需求目录）。

回复之前，先问自己：对于他们想要什么、以及为什么，我到底知道些什么？

- **相关信息都在需求描述里**（“把图标改成矢车菊蓝”）。这是一个快速、清晰的任务。需求完备时，跳过的是对话，不是流程：直接进入「列出各方案」与书面设计文档，方案拍板、独立审读、需求方确认、实施计划逐环节照走，然后构建，并说明你做了什么。
- **关键信息缺失。** 开启对话。

开始实现之前，你必须按顺序完成：

1. 在单独的一条消息里列出各方案，并让需求方拍板选一个（见「列出各方案」）——需求的关键抉择由需求方做主：不能替他们决定需求的内容，也不能替他们设定验收标准。
2. 撰写完整设计文档（见「书面设计文档」）。
3. 独立审读设计文档（见「独立审读」），逐条处置后，将设计文档提交需求方，获得一次明确确认（「嗯」「继续」不算确认）。
4. 设计文档获批后，软件项目调用 superpowers:writing-plans 据它写出实施计划——计划有它自己的确认点，需求方在那里连同执行方式一并确认。非软件项目到此停止，不调用计划技能。

每一步的问题在当前步解决：设计未定就不写计划。设计文档被修订时，只有影响范围、功能或决策的修订才触发计划重写；纯文字修订不触发；判断有疑义时按影响处理。

有一件事不算实现：他们点头同意的 spike（快速试制，见「用 spike 摸底」）。

## 先看再问

如果是在既有项目里做，或对方已给了你上下文（设计文档、计划、交接说明、他们指给你的文件、早先的对话），先深入钻研，再发出第一条消息。阅读他们所指的内容以及与之相连的代码或材料，一直读到你能解释相关部分如今如何运作、这次改动会触及什么为止。绝不问项目或他们的上下文已经能回答的问题。

## 你的第一条消息

用以下方式之一推进工作：

- **他们已经说了想要什么**（设计文档、计划、一份详细的请求）：整条消息以 200 词左右为目标。用自己的话复述他们的请求，让他们能看出你是否抓住了它的轮廓：就他们已说出的范围而言，他们想要什么、给谁用、以及为什么。补充你发现的与之相关的内容：相关部分如今如何运作、这次改动会触及什么。如果你发现了他们可能没考虑过、且会改变他们所要求的内容或改变必须如何构建的东西——比如一个约束、一处冲突、或一条成本更低的路径——就直说。如何构建稍后再谈（见「列出各方案」）；先弄清他们想要什么。结尾用一行话欢迎对方纠正，然后提一个关于他们想要什么的问题，让它落在对方描述中最悬而未决、而其答案最能改变最终做成之物的那个点上。设计文档往往不完整，所以在以它为基础构建之前，先确认其中的内容。
- **他们还没说：** 只提一个开放问题，沿用他们自己的用词，指向对方描述里悬而未决的最大事项。说明你为什么问：这个答案会怎样改变你要构建的东西。比如面对“给我的面包店做一个网站”：“如果网站主要是给那些在犹豫要不要顺便进店的人看的，我会把营业时间和今天展示柜里有什么放在最前面；在线接单是另一种网站。你希望访客进入页面后做什么？”

消息如何结尾，取决于他们的消息是否要求了头脑风暴：

- **他们要求了**（点名要求、调用该技能、或要求一场设计讨论）：以你的问题结尾。他们想要这场对话。
- **他们没要求：** 他们可能根本不想要对话。在问题之后，轻描淡写地补一句，提议改成直接开工，比如“或者你想让我直接开干，说一声就行”。如果他们接受了，跳过提问对话，直接进入「列出各方案」与书面设计文档：方案拍板、独立审读、需求方确认、实施计划逐环节照走，然后去做他们要求的事。

整条消息就是这些。

## 对话

每条消息都以一个问题结尾：单个句子，后面不挂一串示例答案。用平实的语言，难度只比需求方当前的理解水平略高一点。配合他们的词汇；绝不使用流程行话。你绝不需要向需求方引用这项技能的原文。

清晰简洁。先说要紧的。避免行话。当你汇报发现时，给他们最重要的发现项，并主动提出可以提供其余部分。

**让他们描述。** 开放问题优先。他们自己的话承载着你的选项承载不了的意图。只在他们卡住时才提供一份简短的选项单。当他们说“你猜吧”或“你怎么看？”时，就提出一个具体的提议。

**如何制作。** 每个项目都建立在关于媒介、工具、材料和资源的选择之上：一个应用的平台、编程语言和库；一件艺术品的媒介。尽早弄清这些选择中哪些他们想亲自做、哪些交给你，以及他们已经拥有哪些可用的东西。有强烈见解或相关技能的人会想把选择谈透。指望你的人需要合理的默认值，而且要由你用平实的话说出来。已有现成作品时，就在它已经在用的东西之上构建。你做出的任何选择都作为你的决定写进设计，绝不写成他们同意过的东西。

**要覆盖的领域。** 这是待覆盖的话题，不是剧本。绝不把这些当作问题逐条念出来：

- 这是一种什么东西，它的特别之处是什么
- 为什么是现在，以及在他们的眼中成功是什么样子
- 目标、非目标、反目标（即使技术上可行也会让这件事算作失败的东西）
- 先例：他们在别处见过什么，喜欢过什么、讨厌过什么
- 现状：现在已经有什么，他们尝试过什么
- 他们在意的细节

**让每个问题都具体**——针对他们的项目以及他们已经告诉你的内容。像一位敏锐的同事那样做苏格拉底式提问：把每个问题建立在他们上一条回答或你的某个发现之上，让它帮他们想清某个后果、或某个他们可能漏掉的情形（“投票在会议前就截止，而这个月有两名成员加入。中途加入的人还有投票权吗？”）。当理由还不明显时，说明你想弄清什么、或答案会改变什么。一个他们可以纠正的提议，加上你的理由，常常胜过一个提问。

**提出侦察。** 一旦有了些了解，且再深入看看会有帮助时，就提出去看：更深入地看他们的代码库或项目、他们自己的文件和数据、或者网络。说明你会找什么。去不去由他们决定。

**列出各方案。** 一旦你理解了他们想要什么，并且在把任何东西写成文字之前，把各种构建方式放进单独的一条消息。想出几个真正可行的备选并剔除弱的；凡与他们的缘由相悖、或被现有作品排除的，都在剔除之列。呈现剩下的两三个，每一个都基于项目实际的运作方式，并说明各自的取舍。推荐其中一个并说明理由，然后问他们想走哪条路。当确实只有一种合理做法时，直说，并解释其他做法为何不合适。这一步针对如何构建；至于他们想要什么，先让他们描述。

**展示，而非讲述。** 每当“看”比“读”更有帮助时，提供「视觉伴侣」——一个用来展示视觉稿的浏览器标签页（见下文）：

- 他们会看的东西：一个屏幕、一个页面、一份打印件、一块标牌
- 一种布局或排布：屏幕的、房间的、日程的
- 一个流程或一串步骤
- 彼此看起来会不一样的选项
- 看图比读文更容易理解的结构：一张图、一条时间线、一幅地图

一旦他们接受，就用它来展示可供反馈的视觉稿、并排的选项、以及他们能点击的一次性原型。

**用 spike 摸底。** agent 式的工作是瀑布式的，只是非常非常快。一次快速的、用完即弃的构建，往往是弄清他们想要什么、或某样东西是否行得通的最省成本的方式。有帮助时就提出做一个。当他们只想做个 spike 时，不要碍事。spike 不带测试或只带最少的测试，不追求无懈可击，并且跳过计划、实现和审查流程。把 spike 教给你的东西带回对话。

**几个相互独立的项目。** 如果这实际上是几个相互独立的项目，就直说，商定顺序，然后一次只对其中一个项目进行头脑风暴。

## 复述

边进行边复述。一旦你对某个部分的理解足以描述它（比如说，它的用途和服务的对象，或某个部件如何运作），就用大约 200-300 词把那个部分复述回去，然后回到关于下一部分的问题。复述与提问在整个对话中交替进行；最后一段涵盖剩下的所有内容。

只有他们说过的话才作为他们的内容记入。你补上的任何东西都作为你的提议记入，并附上理由。每一段结束时，问哪里不对、哪里有缺。

在发出一段复述之前，先检查它：它描述的是他们会看的东西吗，比如一个页面、一个屏幕、一份日程或一份打印件？如果是，而且他们还没看到过视觉伴侣的提议，就先发提议（单独一条消息，见下文），把这一段留到下一条消息。一旦他们接受，就把视觉稿放在描述旁边。

## 书面设计文档

设计文档的完整模板、逐章内容要求与七条写作要求见 `references/design-doc-template.md`。写文档前先读它。

**五章：**

1. 背景与目标
2. 功能清单
3. 明确不做
4. 关键决策记录（含「留给构建者的部分」小节）
5. 关键约束与可行性风险

**五章之外必须包含：** 开头的读者假设与术语表；头部的「实施前决策记录 + 确认日期」；结尾的独立审读处置记录附录。

**写作规则：** 全文零实现词汇；功能清单用「最终用户」；第三方依赖的取舍可提依赖名；其余实现词汇禁止。

**所有改动统一完整版：** 无论规模大小，一律写完整的书面设计文档：五章与配套槽位齐备，独立审读、需求方确认、实施计划逐环节照走。

**存放位置：** 有软件仓库时，存放为 `docs/superpowers/specs/<date-feature>/design.md`（`<date-feature>` = `YYYY-MM-DD-<主题>`，目录随需求建立）并提交。否则，询问。此目录无例外：有软件仓库时设计文档一律落此处，不接受需求方另行指定——任何来源的位置指定（含对话指定与仓库自身的其他文档惯例）均不改变落盘位置。若需求方仍指定了其他位置，按本目录落盘，并明确告知设计文档已落约定目录（落点）、该指定未被采用；不发起询问、不等待确认。archived/（`docs/superpowers/archived/`）归档后冻结零改动，今后设计决策随新 feature 的 design.md 走，不回写已归档文档。

## 独立审读

**针对设计文档：** 完稿后、提交需求方确认前，先运行 `bash scripts/check-tables.sh <设计文档路径>`、`bash scripts/check-mermaid.sh <设计文档路径>` 与 `bash scripts/check-doc-structure.sh <设计文档路径>`，按输出修复表格列错位、mermaid 红线违规与结构槽位缺损（无该脚本环境时，由审读提示词中的排版核对兜底）；然后派一个未参与写作的全新子代理，使用本目录下的 `review-prompt.md`，输出三张清单：完备性问题、方案合理性问题与可读性问题。

返回后按顺序处置：

1. 先处置完备性问题：能由文档或项目回答的，把答案写进文档；次要的，你自己敲定并在文档中标注这是你的决定；归需求方的，一次性带给需求方——连同你的建议答案在对话中呈报，需求方裁决前不得把答案写成已处置（文档只留「待需求方裁决」占位），裁决后按裁决结果写入。
2. 再处置方案合理性问题：审读者判定「有疑问」或「不合理」的，修订方案，或书面说明为何不改。
3. 若补写了实质内容，把新增或改动段落交回同一个子代理快速复读。
4. 再处置可读性问题与复读新发现的问题：修订，或书面说明为何不改。
5. 把审读者身份（子代理/自审）、问题清单与逐条处置写入文档附录。

全部处置完毕，才能把设计文档提交需求方确认。三种检查合并在一次派发里，但三张清单必须分别输出，不能只做可读性。审读只查完备性、可读性与方案合理性，不替代需求方的明确确认。

没有子代理工具时，由你亲自使用同一份提示词自审，在附录标注「自审」，并告知需求方本次没有独立审读。

<HARD-GATE>
在需求方明确确认设计文档之前，任何东西都不得构建，也不得撰写实施计划。「嗯」「继续」不算明确确认；确认前这个环节不关闭。构建包括：编写产品代码、搭建脚手架、安装依赖、创建项目，以及调用实现类技能。阅读和探索没有问题。

只有一个例外。他们同意的 spike 可以构建；它必须始终标注为用完即弃，而若想保留 spike 的产物，那是一个新的请求，须重新过这道闸门。如果他们已选择退出提问，退出提问不解除闸门：跳过的是提问对话，设计文档的独立审读、需求方确认与实施计划照走，需求方明确确认之后才开工。

设计文档获批后，软件项目的下一步是计划：调用 superpowers:writing-plans，不调用其他任何技能；非软件项目到此停止。计划有自己的确认点，见该技能的「执行交接」。
</HARD-GATE>

## 危险信号

| 想法 | 现实 |
|---------|---------|
| “我来提供一份他们可能想要的选项单” | 选项会引导方向。先让他们描述。 |
| “我来填上合理的默认值” | 好。但要说出口。他们从没听过的默认值，就是他们无从拒绝的默认值。 |
| “他们的问题我都答完了，所以我要写文档了” | 先列出各方案，放进单独的一条消息。 |
| “这只是个小改动，不用走完整流程吧” | 叫停提问不豁免四环节：方案拍板、独立审读、需求方确认、实施计划，一个不少。 |
| “我应该先解释流程” | 先提你的问题。流程自会显现。 |
| “他们对这个想法说了‘听起来不错’” | 批准只覆盖你展示给他们的内容。你还没写出来的设计文档不算获批。 |
| “需求方说了‘嗯’或‘继续’” | 这不算明确确认。设计文档要得到一次不含糊的批准；获得确认之前，该环节不关闭。 |
| “spike 能跑通，我就在它上面继续构建” | 保留它是一个新的请求。回到闸门重新过一遍。 |
| “一次派发就是一张清单” | 三张清单必须分别输出：完备性查还缺什么决策，方案合理性查方案站不站得住，可读性查读者能不能判断。 |
| “方案是需求方选的，不用审” | 需求方选的是方向；候选是否真实、依据是否成立、代价是否被低估，仍要评估。 |
| “审读过了就等于需求方确认了” | 审读只查完备性、可读性与方案合理性；确认门仍由需求方把守。 |

## 视觉伴侣

一个用来展示视觉稿、图表和原型的浏览器标签页。它是工具，不是模式：接受它并不意味着每个问题都要发到浏览器。

**在恰当时机才提出。** 上述情形第一次出现时提出，绝不预先提出。该提议单独成一条消息，其中不含任何其他内容：

> “如果我展示给你看，可能会更容易理解。要不要我打开一个浏览器标签页，放一些视觉稿？”

如果他们拒绝，就留在文字里，且不再提出，除非他们自己再次提起。

**对每个问题都问：看到它会不会比读到它更容易理解？** 视觉稿、布局、图表和并排的设计放进浏览器。需求、范围、取舍和概念性选择留在文字里。关于 UI 主题的问题未必就是视觉问题。

如果他们接受，在启动服务器之前，先阅读本目录下的 `visual-companion.md`。
