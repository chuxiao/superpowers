# 设计文档模板

> 读者假设：懂软件工程，不熟悉产生本文档的对话；不需要了解项目内部实现。
>
> 本文档回答：做什么、不做什么、为什么这样取舍、成本量级与主要风险。实现细节留给计划。

## 五章

### 1. 背景与目标

- 解决什么问题：写出具体场景与失效方式，不写「提升体验」这类无法判断的结论。
- 给谁用：写明最终用户是谁。
- 成功判断标准：写成可观察的行为，例如「需求方只读本文档就能确认范围」，不写「文档清晰易懂」。

### 2. 功能清单

逐项写功能卡片，六字段顺序固定；每张卡片合起来必须能回答「输入什么 → 最终用户看到什么」：

1. **定位：** 功能名 + 一句话职责。
2. **触发与输入：** 触发方式逐个列出（链路接力 / 单独调用 / 显式触发等），输入清单。
3. **执行要点：** 分点写，每点一个可判真伪的命题——禁止把多步流程写成一整段。
4. **出口表：** 功能有多个出口（≥2 种结局）时，三列表格——出口 / 条件 / 去向；单一出口一行文字即可。
5. **流程图：** 执行含决策分支、裁决循环或多出口时配 mermaid 图，先图后文（画法见写作要求第 4 条）；一张图一个主题，节点文本遵守 flowcharts 的预算规则。
6. **本次不做：** 范围与指向（§3 第 N 条）。

用「最终用户」指被设计产品的使用者；「需求方」只指提出需求、做确认的人。

### 3. 明确不做

- 逐项列出不做的事，每项附因果理由：因为 X，所以不做 Y。
- 不接受裸的「暂不做」「后续再说」。
- 本清单在确认后冻结；实施中不得回写。范围要变，回到设计确认门重新确认。

### 4. 关键决策记录

第 4 章开头放决策速览表，一行一个决策，供只查结论的读者使用；正文逐个决策展开：

| 决策 | 一句话结论 | 拍板状态 | 影响功能项 |
|------|-----------|---------|-----------|

每个决策写四段：

1. 候选方案：真正考虑过的两三种做法。
2. 选了哪个。
3. 依据：为什么选它，为什么排除其他。
4. 代价或风险，以及成本量级与主要成本来源。

写完自检方案合理性：候选方案是否真实、是否漏掉明显更简单的做法、取舍依据是否成立、代价与风险是否被低估、方案能否解决第 1 章的问题。审读者会按这五点评估。

#### 留给构建者的部分

- 逐项写：交给执行者决定什么、边界在哪、为什么交给执行者。
- 这一节属于第 4 章，不单独成章；它记录的是委托决定，不是约束或风险。

### 5. 关键约束与可行性风险

- 只列影响「做不做」的事实：依赖缺失、平台限制、时间或成本上限、兼容性要求。
- 不展开实现；不承接委托给执行者的决定。

## 五章之外

必须包含以下固定块，不计入五章，不得新增第六个内容章：

- **文首**：读者假设与术语表。
- **文首**：`实施前决策记录 + 日期：YYYY-MM-DD`。
- **文末**：独立审读处置记录附录，写明审读者身份（子代理/自审）、问题清单与逐条处置。初稿可写「待审读」，确认前必须填完。

## 写作要求

1. 每段只承载一个论点，段首句即结论；句子短，能用列表分点就不用段落。
2. 同类条目用相同句式与相近粒度。
3. 禁止「适当处理」「必要时」「等等」，改为可判真伪的命题；重要规则给 ❌/✅ 对照。
4. 先画图再补充说明：设计文档画用户流程或功能关系图；计划画模块关系或数据流图。mermaid 画法与语法红线见 superpowers:writing-skills 的 `references/flowcharts.md`（语法红线：subgraph 用 `id["标题"]` 形态、文字与特殊字符进引号、换行用 `<br/>`）；提交确认前跑 `scripts/check-mermaid.sh`。
5. 标题层级不超过 3 级，列表嵌套不超过 2 层；单文档超过约 400 行考虑拆分。
6. 交叉引用写「见 §N（内容摘要）」，不写裸引用。
7. 接口配一个调用示例及其对应行为——仅计划适用；设计文档不出现接口。调用示例是说明接口用法的最小片段，不是测试。

全文零实现词汇：不出现文件名、函数名、模块路径、目录结构。第三方依赖的取舍决策可提依赖名；其余实现词汇一律禁止。

## 小改动简短版

**判据**（三条同时满足）：单个功能点、不新增模块、不影响既有行为契约。由需求方判定；判错则升级为项目级，按完整流程重做。

简短版把五章的要点每条写一两句话，直接交给需求方。简短版不强制五章、不做独立审读、不进入完整计划流程。
