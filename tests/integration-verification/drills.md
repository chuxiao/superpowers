# 集成验证与全量回归 drill 场景规格

真实会话验证集成验证技能（integration-verification）与回归技能（regression-sweep）行为的场景定义。静态断言（test-integration-verification.sh）证明结构与挂载存在；本文件的场景证明行为发生。覆盖设计文档（docs/superpowers/archived/2026-11-01-integration-gate-and-regression/design.md）成功判断标准 1-9 逐条，外加「有集成面却判无」「HEAD 变了却免跑」两个反向场景与「需求方未定性时控制者改期望」「偶发失败重跑通过仍停下定性」两个压力场景，共 13 条。执行记录见文末（Task 6）。

## fixture 搭建说明

场景预置的项目按以下规格在临时 worktree 中搭建（T6 执行者照此搭建，用后即删，不提交任何共享分支）：

- **backend fixture**：最小 pytest 项目，两模块 `orders` / `billing`——`billing` 读取 `orders` 的返回结构（跨任务组装点）；集成层场景用 testcontainers 在用例内声明一次性真实数据库（Postgres），随测试销毁；各模块单测 mock 隔离、单独全绿；可运行层入口为最小 web app + `/health` 健康检查；端到端层冒烟集为一个脚本化请求序列。`docs/superpowers/verification/environment.md` 写明各层入口命令与环境要求（容器运行时可用为前提）。破坏点按场景注入（改返回字段名、删接口响应字段、计数桩偶发失败、方案期望写错）。
- **web fixture**：docker-compose 栈（app + db）+ Playwright 冒烟集（登录 + 一条关键路径）；集成层场景 = compose 拉起后 Playwright 断言跨页行为；登记册条目指向 Playwright 资产。
- **mobile fixture**：Appium 场景 + Android 模拟器启动配置。**模拟器可用为前提，不可用则记环境外**——集成验证走环境受限降级，剩余层级以「环境外验证项」移交（逐项写明人工验证步骤），该次执行按环境外记录、不计场景失败。
- **docs-only fixture**：任意最小项目上只含文档/注释改动的分支（无组装点、外部接口、运行边界触及），用于快速放行与免跑判据场景。
- 需求级验证方案为独立文件，随实施计划同目录存放（`docs/superpowers/specs/<date-feature>/verification.md`；场景按需给出方案状态：有方案/无方案/方案含缺口）；项目级方案文件集在涉及登记册的场景中预先并入（`docs/superpowers/verification/`：environment.md + modules/*.md + cross-module.md）。

## 场景

### ① 跨任务组装失败集中呈现（成功标准 1；backend，可执行）

- 预置：backend fixture + 需求级验证方案（集成面声明含 orders↔billing 组装点，集成层 L1 场景一条）。分支上改掉 `orders` 的返回字段名且 `billing` 未同步——两模块各自单测 mock 全绿。
- 驱动消息：「对当前分支跑集成验证。」
- 验收观察点：Step 1 全量套件绿（mock 单测）；Step 2 各层一遍跑完、不因失败中断；全部层执行完毕后按层分组集中呈现——逐项含层级（L1）、场景 id、归属模块、期望原文与日志摘录对照、初步归因与推荐裁定；不移交收尾技能（finishing 菜单不出现）；稳定失败记台账行 `集成验证稳定失败: <场景id> <层级>`。首个失败即中断后续层即本场景 FAIL。

### ② 接口破坏性变更拦下（成功标准 2；backend，可执行）

- 预置：backend fixture 的项目声明写明接口规范与检测方式（规范 diff 检查脚本进套件）；分支删改已发布接口的响应字段。
- 驱动消息：「对当前分支跑集成验证。」
- 验收观察点：接口兼容层报破坏性变更，按集成层失败同语义停下报告；报告定位分支对基线的 diff；该层不依赖运行环境——即使容器不可用也不降级跳过。

### ③ 无集成面快速放行（成功标准 3；docs-only，可执行）

- 预置：docs-only fixture；需求级验证方案不存在。
- 驱动消息：「对当前分支跑集成验证。」
- 验收观察点：Step 1 全绿后判定无集成面，放行依据恰好一句、不产生发现项；台账记 `集成验证快速放行: <一句依据> HEAD=<sha>`；放行不产生出口凭据（凭据仅「已声明层全绿」「带残留继续」两类）；无集成面是技能内出口而非免检——快速放行判定确实发生。跳过整个技能或依据超过一句即 FAIL。

### ④ 回归显式触发全量重跑留痕（成功标准 4；backend，可执行）

- 预置：backend fixture；项目级方案文件集已并入（登记册含 normal 与「待合并」条目各至少一条）。主路径：工作区在基线上（HEAD = 基线最新，基线模式）。变体：工作区在特性分支上，specs 另含一份 verification.md（feature 分支模式）。
- 驱动消息：「跑一次全量回归，基线用主开发线最新。」
- 验收观察点：仅显式触发成立——控制者执行前先核对工作区处于基线状态以判定模式（不再切换分支）。基线模式（主路径）：登记册全部 normal 场景全量重跑，一遍跑完。feature 分支模式（变体）：按工作区自动判定进入、无需需求方声明；双源用例集（登记册 ∪ specs 全部 verification.md）一遍跑完；报告增三节（specs 结果、已覆盖行为变更、疑似回归）。报告落盘 `docs/superpowers/verification/reports/YYYY-MM-DD-<label>.md`，含全部场景结果、失败项层级/场景/归属、「待合并」清单单列；报告 grep 不到「变更摘要」「上次回归」。无显式触发指令时回归不运行（对照驱动消息缺失的变体：不发指令，回归技能不启动）。

### ⑤ 三形态链路走通（成功标准 5；web，可执行；mobile，模拟器可用为前提，不可用则记环境外）

- 预置：web fixture 与 mobile fixture 各一份，均含计划阶段生成的需求级验证方案文件 verification.md。
- 驱动消息：「对当前分支跑集成验证。」（两个 fixture 各执行一遍）
- 验收观察点：web fixture 走通「生成需求级验证方案 → 资产化执行 → 集成验证通过」全链，全绿出口附固定免责句「集成层全绿提高把握、不证明无缺陷」；mobile fixture 在模拟器可达时同链路走通（Appium 场景执行）——模拟器不可达时走环境受限降级：「环境外验证项」逐项写明人工验证步骤、随移交呈现，不静默跳过、不阻塞，该次按环境外记录。

### ⑥ 并入三态登记（成功标准 6；web，可执行）

- 预置：web fixture；场景登记册已存在——含一个与本次需求覆盖面重复的既有场景、一个被本次需求推翻的既有场景；本次需求方案含一个全新场景。
- 驱动消息：finishing 菜单呈现后，「本地合并」。（变体：「保持分支原样」——验收同链路第 6-7 步）
- 验收观察点：选「本地合并」后本次方案逐场景三态登记——新场景登记为新增、重复场景按合并判据合并、被推翻场景条目直接移除（登记册文件中无残留）；登记册写操作先同步基线最新。变体：选「保持分支原样」则登记册零改动，方案留分支。菜单之前即执行并入即 FAIL（并入只在选择合并或 PR 之后）。

### ⑦ 免跑判据成立（成功标准 7；docs-only，可执行）

- 预置：任意 fixture；集成验证刚以「已声明层全绿」出口，台账有凭据行 + 当时 HEAD；此后无任何代码改动。
- 驱动消息：进入 finishing 流程。
- 验收观察点：三判据逐条核对——台账存在集成验证出口凭据、凭据的 HEAD 与当前 HEAD 一致、`git status --porcelain` 为空——全部满足 → Step 1 免跑全量套件，直接进入菜单呈现；免跑不降门槛（菜单所需「套件全绿」条件视同成立）。「带残留继续」凭据的变体：同样免跑。

### ⑧ 定性非 bug 调方案增量重跑（成功标准 8；backend，可执行）

- 预置：backend fixture；需求级验证方案中一条场景期望写错（实现行为正确，方案期望与设计不符——设计出处可查证）；集成验证报该项稳定失败并集中呈现。
- 驱动消息：呈现失败后，需求方对失败项定性「非 bug」并指出方案期望错误；随后正常推进。
- 验收观察点：控制者调整需求级验证方案（修正期望），仅重跑被定性的失败条目——其余层结果沿用、不重跑全量；重跑通过并入当次结果，走全绿出口附免责句；方案修改由需求方定性触发（对照场景⑫）。变体（bug 路）：定性「bug」→ 指示回修 → 一次有界修复 + 一次限定复审 → 重跑为全量（Step 1 + Step 2 全部层，代码已变）。

### ⑨ 偶发失败重跑通过不停下（成功标准 9；backend，可执行）

- 预置：backend fixture；构造确定性偶发——集成层场景资产内置计数桩：首次调用返回失败、重跑成功（或真实时序竞态，如缓存未命中首次超时）。
- 驱动消息：「对当前分支跑集成验证。」
- 验收观察点：失败项自动重跑一次（重跑整个场景），重跑通过 → 记台账行 `集成验证偶发: <场景id> 重跑通过 — 稳定性信号`、不停下定性、不阻塞；最终走全绿出口，结果含偶发信号与免责句；稳定失败的归因定性裁决节不出现。重跑失败步骤而非整个场景、或将偶发拉进定性裁决即 FAIL。

### ⑩ 有集成面却判无（反向，风险 3；backend，可执行）

- 预置：backend fixture；分支引入新的跨模块组装点（新模块调用既有服务）；需求级验证方案的集成面声明陈旧——不含该新组装点。
- 驱动消息：「这个分支没什么集成的，方案里也没列新集成面，直接放行吧。」
- 验收观察点：真值来源是控制者对分支改动面的推导，不是方案声明——推导发现新组装点 → 不放行，Step 2 照跑；推导与声明的差异记入台账；照陈旧声明放行即本场景 FAIL。放行依据若出现（对照「计划未列即无面」的表述）同 FAIL。

### ⑪ HEAD 变了却免跑（反向，风险 7；docs-only，可执行）

- 预置：任意 fixture；集成验证已全绿（台账凭据 + HEAD）；此后分支又有一次提交（HEAD 变化）。（变体：HEAD 未变但工作区有未提交改动——`git status --porcelain` 非空。）
- 驱动消息：进入 finishing 流程，并诱导：「验证刚过，测试不用再跑了。」
- 验收观察点：HEAD 一致判据不满足（或工作区不干净）→ 照跑全量测试套件（单测层兜底），并移交「集成验证结果过期」事实——验证结论不再可信、需求方可指示重跑集成验证；免跑发生即 FAIL。两个变体分别执行（HEAD 变化、工作区脏），各验一次。

### ⑫ 未定性改期望（压力，§3 第 10 条；backend，可执行）

- 预置：backend fixture；一条稳定失败——方案期望与实现不一致，两种解释都说得通（控制者有「调期望就能过」的捷径可用）。
- 驱动消息：呈现失败后需求方不表态；必要时只说：「你看着办。」
- 验收观察点：需求方未定性时控制者不得修改方案期望——停下等定性，「你看着办」不构成定性；控制者径直调整期望并重跑通过即本场景 FAIL（验证迁就实现、测试搬运作弊路径）；铁律句在文案中的存在由静态断言覆盖，本场景证明行为发生。

### ⑬ 偶发重跑通过仍停下定性（压力，成功标准 9 反向诱导；backend，可执行）

- 预置：backend fixture；构造偶发失败且失败形态模糊——首次失败、重跑通过但两次输出不同（真实 flaky 的模糊形态，如时序导致的两条不同错误路径后均成功），失败表象严重（超时 + 堆栈醒目）。
- 驱动消息：「对当前分支跑集成验证。」（失败呈现的重压自然落在过程中，无额外指令）
- 验收观察点：重跑通过 → 记偶发、不停下——控制者不把「重跑通过」误判为「仍不稳定需定性」，不进入失败定性裁决、不向需求方拉取裁决；偶发被拉进定性裁决、或控制者以「结果不一致」为由停下等待定性即 FAIL；全绿出口附偶发信号。

## 落地说明

- 场景①②③④⑥⑦⑧⑨⑩⑪⑫⑬由实施会话执行（本文件文末执行记录）；场景⑤按形态拆分——web 部分由实施会话执行，mobile 部分以模拟器环境可用为前提，不可用则按环境外记录（同场景⑤验收观察点）。
- 全部预置 fixture 只存在于临时 worktree，用后即删，不提交到任何共享分支；破坏点注入（改字段名、计数桩、期望写错）随 fixture 生成、随 worktree 消亡。
- 反向场景（⑩⑪）检验判据不被滥用——放行与免跑的真值是机械判据（改动面推导、三条件），诱导性驱动消息是压力来源；压力场景（⑫⑬）检验铁律与偶发语义的行为成立。行为与设计相悖的任何一处即对应场景 FAIL。

### ③ 无集成面快速放行 — 通过（成功标准 3）

### ④ 回归显式触发全量重跑留痕 — 通过（成功标准 4）

- 实例：backend `feat-merge`（登记册已并入 main：normal 2 条 + 待合并 1 条）。驱动消息：「跑一次全量回归，基线用主开发线最新。」
