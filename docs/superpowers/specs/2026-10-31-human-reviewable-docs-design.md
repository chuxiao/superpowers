# 人工可审阅的设计与计划文档：产品功能说明

> 读者假设：懂软件工程，不熟悉本次改动的来龙去脉；了解「头脑风暴 → 设计文档 → 计划 → 实施」这条流程。
>
> 本文回答：做什么、不做什么、为什么这样取舍、有什么风险。实现细节见后续的技术实现方案。

## 术语表

| 术语 | 含义 |
|---|---|
| **需求方** | 提出需求、作出确认的人。 |
| **最终用户** | 被设计产品的使用者。 |
| **设计文档（产品功能说明）** | 头脑风暴阶段的产出，回答做什么、不做什么、为什么。 |
| **计划（技术实现方案）** | 计划阶段的产出，回答改哪里、怎么改、边界在哪、有什么风险。 |
| **完备性检查** | 独立审读的一部分：问「下一环节还缺哪些决策」（设计文档→计划；计划→实施）。原 builder check 并入独立审读。 |
| **独立审读** | 派一个未参与写作的子代理，按专用提示词查完备性、可读性与方案合理性（设计文档），或完备性、可读性与实现效果（计划），输出对应清单。 |
| **合并审读** | 独立审读的执行方式：一次派发、按文档类型输出三张清单——设计文档：完备性、可读性、方案合理性；计划：完备性、可读性、实现效果。 |
| **spike** | 用完即弃的快速试制。 |
| **SDD** | 子代理驱动开发：每个任务由全新子代理实施，任务后由独立审查者把关。 |

## 1. 背景与目标

**问题**：一次复刻外部产品的实践中，头脑风暴与需求讨论混在一起，没有留下成文的产品说明；计划成为唯一成文产物。计划按执行顺序组织，面向机器执行而非人工阅读。结果是：需求方在前期无法确认「复刻哪些功能、不做什么、为什么这样取舍」；后期开发质量也失去判断依据。

**失效机制**：流程没有要求「写计划之前必须有一份成文、经确认的产品说明」。头脑风暴的讨论可以一直停留在对话里，计划却可以照常产出。计划于是同时承担两种使命：让人确认做什么，以及让执行者知道怎么改。两种使命的读者、组织方式、验收标准都不同，挤在一份文档里，两边都不合格。

**目标**：

- 设计文档回答：给谁用、做什么、不做什么、为什么这样取舍、成本量级与风险。
- 计划回答：改哪些文件、每个功能单元的输入输出与边界、为什么这样实现、有什么实施风险。
- 两份文档在提交确认前，各由一个未参与写作的子代理独立审读；设计文档查完备性、可读性与方案合理性，计划查完备性、可读性与实现效果。
- 两份文档都提交进版本库，合入 main 后保留。

**成功标准**（全部可观察）：

1. 需求方在确认设计文档时，不回到对话、不读代码，就能作出确认或提出修改。
2. 需求方抽查计划时，不读代码，就能指出改哪里、边界是否清楚、主要风险是什么。
3. 每份文档附处置记录附录：审读提出的每条问题都有处置——修订，或书面说明为何不改。
4. 合入 main 后，两份文档仍能在版本库的文档目录中找到。
5. 新流程至少在一个真实小场景跑通一次，由需求方判定两份文档可审阅；未跑通则修订后重跑，不进入实施。

## 2. 功能清单

### 2.1 设计阶段产出「设计文档（产品功能说明）」

- **用户可见行为**：头脑风暴结束、方案选定后，产出一份设计文档，固定包含五章：
    1. **背景与目标**：解决什么问题、给谁用、成功的判断标准。
    2. **功能清单**：逐项写「输入什么 → 最终用户看到什么」，每项附本次不做的范围。
    3. **明确不做**：逐项附理由，理由须说明因果（因为 X，所以 Y），不接受裸的「暂不做」。
    4. **关键决策记录**：每个决策写候选方案 → 选了哪个 → 依据 → 代价或风险，并给出成本量级与主要成本来源。
    5. **关键约束与可行性风险**：只列影响「做不做」的事实，不展开实现。
- **五章之外**：文档必须包含开头的读者假设与术语表、结尾的独立审读处置记录附录；这些是固定块，不计入五章，不得新增第六个内容章。现行技能「书面设计文档」节列出的内容比五章多，两处需要归位：「方案」（考虑过的构建方式、取舍、选了哪个、为什么）并入新模板第 4 章「关键决策记录」；「留给构建者的部分」（明确交给执行者决定的事项）作为新模板第 4 章下的一小节，逐项写「交给执行者决定什么、边界在哪、为什么」。第 5 章只保留影响做不做的事实，不承接委托决定。
- **写作规则**：全文零实现词汇——不出现文件名、函数名、模块路径、目录结构。第三方依赖的取舍决策可提依赖名，其余实现词汇一律禁止。本文讨论技能行为时提到的「技能主文件」「参考文件」「字节上限」是可行性约束，不是功能描述，不受此限。
- **小改动简短版**：维持现状——小改动由需求方判定（单个功能点、不新增模块、不影响既有行为契约），写简短版即可；不强制五章，不做独立审读，不进入完整计划流程。判错则升级为项目级，按完整流程重做。
- **本次不做**：不改变头脑风暴的提问方式、视觉伴侣、spike 流程；不要求设计文档覆盖实现细节；不取消小改动简短版。

### 2.2 计划阶段产出「计划（技术实现方案）」

- **用户可见行为**：设计文档确认后，产出一份计划，固定包含五章：
    1. **改动地图**：新增模块与修改文件逐个列出，各配一句话职责，说明依赖方向与分层归属。
    2. **功能单元规格**：每个任务写清文件、接口、边界条件、验收标准；接口以目标实现语言逐字书写，标注上下游依赖。
    3. **设计依据**：为什么这么改——与参照实现的对照、关键取舍的完整论证。
    4. **约束**：执行期红线——分层边界、依赖白名单、兼容性要求。
    5. **风险清单**：逐条写触发条件、影响、缓解方式。
- **五章之外**：文档必须包含开头的目标、架构、技术栈、设计文档路径元数据块；末尾的执行方式交接块；文末的独立审读处置记录附录；三者都不计入五章。
- **对现行计划骨架的变更**：删除「实施后记」，实施完成后不回填；原「全局约束」并入第 4 章「约束」。
- **写作规则**：接口配一个调用示例及其对应行为；行为与规范可判真伪，重要规则给 ❌/✅ 对照；不预写 TDD 红绿步骤与测试代码。调用示例是说明接口用法的最小片段，不是测试。
- **适用范围**：计划只适用于软件项目。非软件项目在头脑风暴交接时即停止，不调用计划技能；计划技能收到非软件项目时拒绝并返回。
- **本次不做**：不设「实施后记」，不要求实施完成后回填；不改变任务的四段式结构（文件、接口、边界条件、验收标准）与 SDD 的兼容性。

### 2.3 两份文档各配独立审读

- **用户可见行为**：每份文档初稿完成、提交需求方确认前，派一个未参与写作的子代理，按该文档类型的专用审读提示词通读，返回三张清单：设计文档为完备性问题、可读性问题、方案合理性问题；计划为完备性问题、可读性问题、实现效果问题。作者逐条处置；处置记录作为文档附录随文档留存，写明审读者身份（子代理/自审）、问题清单与逐条处置。全部处置完毕才能提交确认。
- **完备性检查（原 builder check 并入）**：设计文档问「为制定计划还缺哪些决策」，计划问「为实施还缺哪些决策」。问题分三堆：已有答案（文档或仓库能回答）、次要（有常识的后续环节执行者——计划撰写者或实施者——能自行敲定）、归需求方（只有需求方能回答，且答案改变做成之物）。审读者先按文档与仓库可查的事实提出分类；作者复核并补上对话上下文，最终分类由作者负责。归需求方的问题，由作者一次性带给需求方。
- **可读性检查**：验收集逐项回答「能 / 不能 + 卡住的原句」；标出读不懂的句子、有歧义的词、推理跳步处；检查排版与渲染风险。空清单也要逐项声明「本项通过」。
- **方案合理性检查（仅设计文档）**：审读者评估设计方案本身——候选方案是否真实、是否漏掉明显更简单的做法、取舍依据是否成立、代价或风险是否被低估、方案能否解决背景里的问题。每个关键决策给「合理 / 有疑问 / 不合理」判定并说明理由。判为有疑问或不合理的，作者修订方案，或书面说明为何不改。
- **实现效果检查（仅计划）**：审读者判断按计划实施后，设计文档承诺的用户可见效果是否真的会出现——每条「输入 → 最终用户看到什么」是否有任务的验收标准直接证明；任务串起来依赖、接口契约、集成点是否闭合；关键失败路径是否有任务覆盖；非代码工作是否遗漏。对每条设计功能给「能达成 / 有疑问 / 不能达成」判定并说明理由。判为有疑问或不能达成的，作者修订计划，或书面说明为何不改；若暴露设计本身不可行，回到设计确认门。
- **设计文档的审读验收集**：需求方只读设计文档，能否回答做什么、不做什么、为什么、成本量级与风险是否可接受；审读者是否认为设计方案合理。
- **计划的审读验收集**：工程读者只读计划，能否判断改哪、怎么改、边界在哪、为什么这样改、实施风险是什么；需求方能否抽查；按计划实施能否达成设计承诺的效果。
- **合并后的顺序**：① 子代理一次通读，输出三张清单；② 作者先处置完备性问题（补写或改结构）；③ 设计文档再处置方案合理性问题，计划再处置实现效果问题：修订方案或计划，或书面说明为何不改；④ 若补写了实质内容，把新增或改动段落交回同一个子代理快速复读；⑤ 处置可读性问题与复读新发现的问题；⑥ 提交确认。
- **审读提示词的内容**：必须写明该文档类型的验收集、三张清单的输出格式（位置 + 原句 + 卡住的原因 + 严重度）、以及「只标问题、不改稿」的边界。
- **渲染检查**：有渲染环境时看渲染结果；没有时检查 Markdown 结构——表格列数是否对齐、代码块围栏是否闭合、图语法是否完整、标题层级是否跳级、列表嵌套是否过深。
- **无子代理工具时**：作者用同一份审读提示词自审，并在处置记录中明确标注「自审」，不阻塞确认门；同时告知需求方本次没有独立审读。
- **本次不做**：不让审读者改稿；不用审读替代需求方确认；不把完备性、方案合理性或实现效果检查砍掉。

### 2.4 两道确认门保持不变

- **用户可见行为**：设计文档获得需求方明确确认后，才撰写计划；计划获得需求方明确确认后，才进入实施。「嗯」「继续」不算明确确认。
- **修订粒度**：设计文档被修订时，只有影响范围、功能或决策的修订才触发计划重写；纯文字修订不触发。是否影响范围、功能或决策由作者判断，判断有疑义时按影响处理。
- **回退规则**：计划撰写中发现设计层面必须改动，回到设计确认环节。计划已确认、实施已开始后才发现设计必须改：立即停止实施，回到设计确认环节；返工还是回滚由需求方决定；已合入 main 的部分用新提交修正，不改写历史。
- **流程**：

```
头脑风暴对话
  └─► 设计文档初稿
        └─► 独立审读（完备性 + 可读性 + 方案合理性）→ 处置 → 新增内容复读
              └─► 【确认门一】需求方确认设计文档
                    └─► 计划初稿
                          └─► 独立审读（完备性 + 可读性 + 实现效果）→ 处置 → 新增内容复读
                                └─► 【确认门二】需求方确认计划
                                      └─► 实施
```

- **本次不做**：不把两份文档合并为一次确认；不改变「确认前该环节不关闭」的规则。

### 2.5 两份文档提交并保留

- **用户可见行为**：设计文档与计划在确认后提交进版本库；开发完成、合入 main 后两份文档仍保留，不删除、不归档、不依赖实施后回填。设计文档与计划分处不同文档目录，沿用现状。
- **范围清单冻结**：「明确不做」清单在确认后冻结；实施中不得回写。需要变更范围时，回到设计确认门重新确认，再更新计划。
- **过时风险的缓解**：两份文档头部标注「实施前决策记录」+ 确认日期（YYYY-MM-DD）；实施后的结论以提交信息为准，文档本身不承诺与最终实现逐字一致。
- **本次不做**：不引入归档目录；不改变两份文档现有的存放分区；不新增实施后结论的持久化载体。

### 2.6 写作质量要求（两份文档共同遵守）

1. 每段只承载一个论点，段首句即结论；句子短，能用列表分点就不用段落。
2. 同类条目用相同句式与相近粒度。
3. 禁止「适当处理」「必要时」「等等」，改为可判真伪的命题；重要规则给 ❌/✅ 对照。
4. 先画图再补充说明：设计文档画用户流程或功能关系图；计划画模块关系或数据流图。
5. 标题层级不超过 3 级，列表嵌套不超过 2 层；单文档超过约 400 行考虑拆分。
6. 交叉引用写「见 §N（内容摘要）」，不写裸引用。
7. 接口配一个调用示例及其对应行为——仅计划适用；设计文档不出现接口。调用示例是说明接口用法的最小片段，不是测试。

两份技能各自完整承载这七条，不互相引用；同一处改动同时改两份，保持措辞一致。流程交接可以点名下一个技能，但这不算写作要求上的互相引用。

## 3. 明确不做

1. **不合并两道确认门**。理由：合并会让产品判断与实现判断挤进一次确认，确认粒度变粗，且违背 superpowers 现有的两道门流程。
2. **不要求两份文档同目录**。理由：两份文档的读者与生命周期不同；沿用设计文档与计划分区的现状即可，合入 main 后同样保留。
3. **不保留「实施后记」**。理由：需求方明确不要；两份文档定位为实施前的决策记录，实施后的结论只由提交信息承载。
4. **不改执行环节技能**（会话内执行、子代理驱动开发、分支收尾）。理由：本次只解决写作与审读；执行环节已引用设计文档与计划，不受影响。
5. **不抽共享写作规范文件**。理由：选了「两个技能各自升级、各配专用审读提示词」这一方案（见 §4 决策 1）；避免跨技能文件依赖，审读标准按文档类型定制。
6. **不重写历史设计文档与计划**。理由：历史文档是时间点记录，重写会改写历史；本次只约束新产出的文档。
7. **不改变头脑风暴的对话流程**。理由：提问、视觉伴侣、spike、方案选择都已在现有技能中验证；本次只改产出文档的结构与审读。
8. **不砍掉完备性、方案合理性与实现效果检查**。理由：完备性查还缺什么决策，方案合理性查设计站不站得住，实现效果查按计划做完能否兑现设计，可读性查读者能不能判断；四者是不同问题，合并审读不等于合并问题。
9. **不改小改动简短版**。理由：简短版服务于小改动，强制五章与独立审读会让流程成本超过收益；完整要求只约束项目级。
10. **不把处置记录留在对话里**。理由：对话会压缩、会消失；处置记录作为文档附录随文档提交，才能满足「随文档留存」。
11. **不新增实施后结论的持久化载体**。理由：需求方明确不要实施后记；若需要留存，由提交信息承载。

## 4. 关键决策记录

### 决策 1：两个技能各自升级，各配专用审读提示词

- **候选**：A. 两个技能就地升级 + 各自专用审读提示词；B. 抽一份共享文档质量规范；C. 只强化计划。
- **选择**：A。
- **依据**：改动边界清楚；两份文档的读者不同，审读验收集可以按文档类型定制；C 不解决「前期没有产品设计文档」的根因。
- **代价/风险**：写作要求在两处重复，未来可能漂移；维护时同一改动要同时改两处。成本量级：两个技能各改一次，审读提示词各新增一份。

### 决策 2：拆成两份文档，而不是把一份文档改得更易读

- **候选**：一份文档重排章节；拆成设计文档与计划两份。
- **选择**：拆成两份。
- **依据**：两种使命的读者不同——需求方确认做什么，执行者知道怎么改；一份文档无法同时让两类读者高效判断。拆开后，设计文档可以完全不出现实现词汇。
- **代价/风险**：需求方需要读两份、确认两次；每份文档各增加一次独立审读与一轮处置。成本量级：每个项目多两轮子代理审读。

### 决策 3：保留两道确认门

- **候选**：一次确认两份；设计、计划各确认一次。
- **选择**：各确认一次。
- **依据**：superpowers 现有技能已把设计与计划分成两道确认门；设计变更会导致计划重写，分开确认避免把返工藏进同一次确认。
- **代价/风险**：需求方需要读两次文档。

### 决策 4：两份文档分目录存放

- **候选**：同一需求目录下放两份；沿用现有设计文档与计划分区。
- **选择**：沿用现有分区。
- **依据**：两份文档的读者与生命周期不同；现有路径已被执行环节与审查环节引用。
- **代价/风险**：读者需要在两个目录间跳转。

### 决策 5：删除「实施后记」

- **候选**：保留并要求实施后回填；保留但不要求回填；删除。
- **选择**：删除。
- **依据**：需求方明确不要；避免执行环节追加维护负担。
- **代价/风险**：实施后的裁决与延后项只留在提交信息里，文档本身不承载；保留的文档可能与最终实现不一致。

### 决策 6：保留文档，不归档

- **候选**：合入 main 后归档；合入后保留在原目录。
- **选择**：保留在原目录。
- **依据**：需求方要求两份文档在合入 main 后均保留；保留在原目录便于后续维护者从当前文档追到历史决策。
- **代价/风险**：文档目录会随时间增长；旧文档可能与实现不一致。

### 决策 7：独立审读按文档类型分开

- **候选**：一份通用审读提示词；设计文档与计划各一份。
- **选择**：各一份。
- **依据**：两类文档的读者与验收问题不同；通用提示词容易退化成泛泛的「检查清晰度」。
- **代价/风险**：两份提示词需要同步维护。

### 决策 8：详细模板与写作要求放参考文件

- **候选**：全部写入技能主文件；模板与写作要求放参考文件。
- **选择**：主文件保留流程与必做步骤，体量大的模板与写作要求放参考文件。
- **依据**：仓库测试对技能主文件施加 20,000 字节上限（按字节计数，比 Claude Code 压缩后 20,000 字符的重新附加限制更严格）；主文件越短，压缩后越不容易丢关键指令。当前两个目标技能的主文件分别约 17.3KB 与 12.2KB。
- **代价/风险**：参考文件增多，需要主文件在正确步骤指向它。

### 决策 9：合并完备性、可读性与方案合理性/实现效果检查为一次派发

- **候选**：多次独立派发；合并为一次派发、按文档类型输出清单。
- **选择**：合并为一次派发；设计文档三张清单（完备性、可读性、方案合理性），计划三张清单（完备性、可读性、实现效果）；补写实质内容后交回同一子代理复读。
- **依据**：三者都是「未参与写作者通读同一份文档」，合并减少一轮派发与处置；设计文档不只描述做什么，也提出怎么做，方案本身需要被评估；计划不只列任务，还要证明按任务做完能兑现设计承诺的效果。
- **代价/风险**：一个子代理可能只做可读性而漏掉完备性、方案合理性或实现效果，或把不同问题混成一张清单；补写内容若不复读，会留下未审内容。缓解：提示词强制清单分别声明；补写实质内容必须复读。

### 决策 10：确认后冻结「明确不做」，取消实施中回写

- **候选**：保留现行「活文档」规则，实施中回写；确认后冻结，范围变更回到设计确认门。
- **选择**：冻结。
- **依据**：需求方明确不要实施后记；两份文档定位为实施前决策记录。回写会让文档在实施中继续变化，与「不依赖实施后回填」冲突。
- **代价/风险**：实施中临时砍掉或补做的项不会自动出现在文档里；需要范围变更时必须停下走确认门，成本更高。

### 决策 11：实施开始后的设计变更由需求方决定返工或回滚

- **候选**：由实施者自行决定；由需求方决定。
- **选择**：由需求方决定；实施立即停止，回到设计确认门。
- **依据**：返工与回滚的代价不同，只有需求方能判断哪种可接受；已合入 main 的部分用新提交修正，不改写历史。
- **代价/风险**：变更会阻塞实施，直到设计重新确认。

## 5. 关键约束与可行性风险

- **技能主文件字节上限**：仓库测试对技能主文件施加 20,000 字节上限（按字节计数，比 Claude Code 压缩后 20,000 字符的重新附加限制更严格）。当前头脑风暴技能主文件约 17.3KB，计划技能约 12.2KB。头脑风暴侧新增空间很小，必须把模板与写作要求放进参考文件；这是本次改动的硬约束。
- **技能改动难以自动验证**：本仓库的评测工具不在本地工作区，本次无法运行完整评测。验证方式：用一个真实小场景完整跑一遍新流程，由需求方判定两份文档是否可审阅；未通过则修订技能后重跑。
- **行为塑造风险**：技能可能跳过「派独立子代理审读」这一步，或审读流于形式。缓解：写成必做步骤；审读提示词要求逐项回答验收集；处置记录附录必须包含审读者身份与问题清单。
- **合并审读的角色塌缩**：一个子代理可能只做可读性、漏掉完备性、方案合理性或实现效果，或把不同问题混成一张清单。缓解：提示词强制清单分别声明；补写实质内容后交回同一子代理复读。
- **模板只有标题、没有内容要求**：只规定五章标题时，产出可能是五个空章。缓解：模板逐章写内容要求与示例；验收逐章检查关键内容，不只看标题。
- **重复写作要求漂移**：两份技能各自完整承载七条写作要求，同一改动要改两处。缓解：措辞逐字一致；把「两份同时改」写进技能维护说明。
- **保留文档过时**：文档不回填，实施中的偏离、裁决、延后项不会回到文档，保留的文档可能与最终实现不一致。缓解：文档头部标注「实施前决策记录 + 日期」，读者以提交信息为准。
- **非软件项目不适用计划**：头脑风暴面向非软件工作，但计划的五章是软件概念。缓解：明确计划只适用于软件项目，非软件项目止于设计文档。
- **问题频率未知**：本次改动基于一次复刻实践，无法判断同类问题是否高频。成本是每个项目的两份文档各增加一轮独立审读与处置；收益是前期确认与后期质量有据可依。
