# TDD 技能改造设计

## 1. 背景与要解决的四个问题

fork 的 superpowers 将替换本机安装的插件。以下四个问题都要在技能层解决——前两个是本次改造的起点，后两个是设计过程中追加的：

| # | 问题 | 现行技能的缺口 |
|---|------|----------------|
| P1 | **遗留项目上 TDD 会误导**。特征测试（characterization test，写完直接绿、锁定既有行为）是遗留项目的安全网，但技能把「测试立即通过」列为危险信号（SKILL.md:236），规定「测试通过了？你测的是既有行为。修改测试」（:126）——特征测试会被当成违例：要么拒绝写，要么写完被改掉 | 没有区分两类测试的可观察判据 |
| P2 | **逐行为循环浪费往返**。5 条验收标准的任务按逐行为红绿循环要 ~11 次验证往返，而红绿的证据价值只需任务级批量即可保全 | 循环粒度没有定义 |
| P3 | **计划设计的接口可能不可测**。接口由计划的 Interfaces 块前置决定，TDD 的「测试塑造 API」职能已由计划层承担；但技能卡住时表写着「测试难写 = 设计不清晰，听测试的，简化接口」——在计划驱动语境里这是私自改接口的许可证 | 执行期没有分级处置；计划自审没有可测性检查 |
| P4 | **既有代码纠缠到锁不上测试**。解依赖有鸡生蛋问题：规则说「先锁再改」，可锁本身写不出来；卡住时表的「用依赖注入」「简化设计」在遗留语境是自由重构许可证 | 没有引导顺序；agent 没有 IDE 重构保障，现行建议的隐含前提不成立 |

出路一览（详细设计见对应章节）：

| 问题 | 出路 | 章节 |
|------|------|------|
| P1 | 铁律改写为双形态 + 特征测试手册 | §3.1 / §3.4 |

## 2. 目标 / 非目标 / 反目标

**目标**
- agent 在遗留代码上正确使用特征测试：先锁后改，bug 不就地修，快照有意更新。
- 多验收标准任务的 TDD 往返从逐行为降到任务级批量（~11 次 → ~3 次），证据等级不降。
- 与既有机制（完成契约、任务审查、fix-loop）零冲突。

**非目标**
- 不动审查基准、完成契约、修复循环的严格度——只改达成方式。
- 不引入新测试框架或测试类型；特征测试就是普通测试，同套件同跑法。
- 不给上游提 PR；不引第三方依赖。

**反目标（出现即失败）**
- 双形态表述让 agent 在绿地新功能上放松了「先红」纪律（基线对照必须排除）。
- 特征测试成为「事后补测试」的新借口——特征测试也必须在改动**之前**写。
- 批量实现导致过度构建无人拦截。
- 提交历史出现失败测试单独占据的「红提交」，或快照值回填自实现后的输出（回声复辟）。回声测试：断言值抄自代码实际输出、恒真、什么也证明不了的测试。

## 3. 核心设计

### 3.1 铁律改写为双形态

**现行：**「没有先行失败的测试，绝不写生产代码」。
**问题：** 特征测试天然先绿。不设例外条款（细微让步会重新打开讨价还价的空间），而是给铁律补上第二形态——例外是「豁免」，第二形态是「覆盖」：

```
没有测试证据，绝不改动行为。

证据的两种形态：
- 驱动新行为：先亲眼看它失败（RED），再亲眼看它通过（GREEN）
- 保持既有行为：先亲眼看它通过（锁定），改动之后再亲眼看它通过（回归）

两种形态都要求测试先于改动存在。
```

**判据（可观察谓词，决定一条测试属于哪类）：** 这条断言的期望值，是从需求/规格**推出来**的，还是从当前代码的实际输出**读出来**的？推出 → 新行为测试；读出 → 特征测试。

**时间序防御：** 特征测试必须在生产代码改动**之前**写下并跑绿。改动之后才补的「特征测试」是在验证记忆，不是锁定现状。

### 3.2 默认循环：任务批量红绿

替换现行的逐行为红绿循环，粒度为任务：

1. **写全任务的测试**：新行为测试（断言尚不存在的行为）与特征测试（断言本次改动必须保持的既有行为）混合写出。
2. **RED 运行（一次）**，两类各查各的：
   - 新行为测试逐条失败，失败原因全部为「未实现」类（断言失败、缺符号）。出现错误型失败（导入失败、语法错误、fixture 崩溃）→ 先修测试本身再重跑，那不算 RED。
   - 特征测试逐条**通过**。失败的 = 对现状理解有误或断言写错：先实际运行/观察目标代码的输出，把断言对齐到**观察值**，修测试到通过。**绝不为此修代码。**
3. **批量实现**：写到全部测试通过为止，不加测试未要求的功能（过度由任务审查「多余」类发现项兜底）。
4. **GREEN 运行（一次）**：新行为测试全绿；特征测试必须**仍然**全绿——失败 = 既有行为被碰坏，**修代码**。
5. **REFACTOR**：特征测试 + 全量套件保护下清理；无特征测试的任务由新测试本身保护。
6. **task-done**：全量套件收口（既有契约，不变）。

**时点语义（必须显式写进技能）：** 同一句「改测试还是改代码」，两个时点含义相反——
- RED 时点特征测试失败 → 修**测试**（你理解错了现状）；
- GREEN 时点特征测试失败 → 修**代码**（改动碰坏了既有行为）。

**两条纪律：**
- **批量 RED 完成前不得开始实现**——全部测试已写完、已跑过一次红，才允许写第一行实现。边写测试边写实现交替进行，会丧失 RED 证据的完整性。
- **提交切分保「每提交皆绿」**：特征测试可先行单独提交（绿）；新行为测试与实现同批提交——失败测试单独成提交会制造「红提交」，让 bisect 把它误判为坏提交。遗留任务的提交序列：①特征测试（绿）②开缝（绿，附对照）③新测试+实现（绿）。

### 3.3 例外与退化

细粒度循环保留为三个例外条款：

1. **bug 修复**：本来就是「复现失败测试 → 修 → 绿」单循环，无批量可言。
2. **算法核心**：下一条测试的设计依赖上一条实现的形态。
3. **接口未定的探索任务**：应按执行技能的停止条件回溯计划，不是靠微循环在执行期补设计。

退化情况：
- 单验收标准任务 = 经典循环（批量自然退化）。
- 纯重构任务：新行为测试为空、全是特征测试，RED 运行全绿是**合法**的。
- 但「任务声称交付新行为而 RED 全绿」= 坏测试或对任务的理解错了。

### 3.4 遗留代码手册（第二形态的实战）

**锁什么、怎么锁**
- 锁外部可见行为（输出、副作用、状态迁移），不锁内部实现细节——锁实现会阻止它要保护的重构。
- 非确定性目标先固定：时钟、随机种子、集合用无序断言。
- 将被本次任务有意改变的行为**不锁**——锁定只保护必须存活的东西。
- 锁定范围 = 本次改动的回归面（童子军法则）。计划边界条件若列出「不得改变的既有行为」，以它为锁定清单；执行中读代码发现额外回归面，补锁并记台账。不为没碰的代码补网（范围蔓延由审查「多余」兜底）。
- 锁定测试要有**身份标记**：命名或注释标明「快照：记录现状，非规格」（如 `test__characterization__` 前缀），否则日后没人分得清哪些可随手改。

**发现现状是 bug**
- 记台账（Ruling），**不就地修**。bugfix 走独立单循环（新行为形态：断言正确行为 → 失败 → 修 → 绿）。
- bugfix 落地后由该循环更新特征快照：**新值 = 复现测试断言的那个值（来自需求），不是修正后代码的实际输出**——拿输出回填断言就是回声测试换了件衣服。更新须附「行为有意变更」的理由；快照是快照不是永久契约，但更新必须显式、有据。

**锁不上时：解依赖的引导顺序**（缝 = seam，不改行为打开的测试插入点）
- **先找最近的既有缝**：测试不必打在被改函数上——沿调用链向上找任何能观察目标行为的入口（上层函数、模块入口、CLI/HTTP 端点），先在那层锁。网眼粗总比没网好；粗网是集成级保险，此时把锁定范围收缩到真正受威胁的回归面，缝成之后鼓励把锁定下沉到更细的观察点，粗网不必退役。
- **开缝协议**：锁不上才开缝。第一道缝在「没有细网」的状态下做，约束必须更严而非更松：机械小步（提取并重写、参数化构造器、子类重写）、一次只开一道缝、开缝前后在最近缝上做行为对照（改前观察 = 改后观察）、单独提交。**agent 没有 IDE 重构保障**——提取、参数化都是手工文本变换，语义等价没有工具兜底，所以步子要更小，拿不准语义等价的变换不做。开缝仍属第二形态（保持既有行为：改前改后证据一致），不为它开铁律例外。
- **嫩枝法（sprout）**：遗留区域的新行为不塞进纠缠函数——新逻辑长在新的、可测的方法/类里（全程新行为形态 TDD），遗留处只留一行调用。遗留 diff 极小、可审；这是既有代码无法顺利测试时加新功能的默认姿势。
- **实在锁不上**：任何缝都开不出（成本荒谬或无任何观察点）时，改动压到最小且纯机械，`Ruling: 无法锁定 X — 理由 — 错了的代价` 记台账；若连「改动保持行为」都无法观察，属于「每条前进路径都只能靠猜」，按停止条件停下问人。监控/日志可作为替代证据来源。

**诚实边界**
- 目标不是覆盖率，是每次修改让碰过的地方变安全。不追求把项目补成 TDD。

### 3.5 计划接口的可测性

**定位：** 本体系中 TDD 不承担接口发现——接口由计划的 Interfaces 块前置决定，「测试塑造 API」的职能由计划层与两道确认门承担。因此「接口难测」是计划缺陷信号，不是执行期自由改接口的许可。

**防线主体在计划期**：计划自审的可测性检查（§4.4）+ 独立审读的可测性维度（§4.6）是主防线；下面的执行期分级是兜底——自审有作者盲区，有些不可测性只有动手写第一条测试才暴露，兜底删掉后 agent 遇到时就只剩私自改接口或卡死两条路。注意两道人工确认门**不承担**可测性检查：它们审的是计划对设计文档的忠实性——这意味着可测性风险没有人工兜底，独立审读必须是强制的。

执行期分级处置：
- **可测性小修**（参数顺序、注入点、拆出一个纯函数）→ 执行者 Ruling：以最小改动实现同一验收标准，`Ruling:` 记台账；审查者与终审从台账读到偏离依据。
- **架构级取舍**（多种可行方案、模块边界重划）→ 按执行技能停止条件停下上报（executing-plans 四停 / SDD BLOCKED），回到计划层决定。
- **验收标准不可观察**与接口不可测同源同分级：展开不出测试的验收标准是计划缺陷，走同一路径。
- **接口 Ruling 必须传给后续消费方**：改了被其他任务消费的接口，控制者把该 Ruling 写进后续任务的简报（executing-plans：触及同一接口的任务从台账读它；SDD：简报携带更早任务的接口与裁定）。

### 3.6 问题纠缠时的处置

四个问题域——P1 遗留特征测试、P2 批量红绿、P3 接口可测性、P4 解依赖——很少单独出现。纠缠时的固定处置：

| 纠缠 | 处置 |
|---|---|
| P1×P2（遗留任务要批量） | §3.2 混合批次：特征测试直接绿、新行为测试先红，一次 RED 运行分批验证 |
| P1×P3（遗留 + 接口要改） | 锁定的对象是**行为**不是接口：先在旧接口上锁 → 接口 Ruling → 迁移实现 → 锁定组迁到新接口；迁移本身在旧网保护下完成 |
| P1×P4（遗留且锁不上） | §3.4 引导协议：最近缝粗锁 → 开缝 → 锁下沉 → 再改 |
| P2×P3（批量展开时发现接口不可测） | 不是坏测试，是计划缺陷：停止展开，走 §3.5 分级；小修 Ruling 后**改完已写测试的签名再继续批量**；架构级上报 |
| P2×P4（批量中部分代码锁不上） | 优先把该部分**拆成独立小任务**（值得审查者单独把关的最小单元）；拆不动才用最近缝粗网并入批量 |
| P3×P4（接口不可测因为代码纠缠） | 开缝（行为保持）与接口变更（可能改行为）**分属不同提交**：先缝后变更，禁止在开缝提交里夹带接口改动——它会让缝的行为对照失真 |
| P1×P2×P4（三重：遗留纠缠任务要批量） | 任务内标准序列：①最近缝粗锁（提交）②开细缝（提交，附对照）③锁定组定稿/下沉（提交，全绿）④批量写全部新行为测试 → RED ⑤实现+GREEN（同批提交）⑥REFACTOR ⑦task-done 全量 |

纠缠处置的总原则：**每一步要么在拿证据，要么在改变现，两类操作不进同一个提交。**

## 5. 边界情况速查表

| 情况 | 处置 |
|---|---|
| RED 运行出现错误型失败（导入/语法/fixture） | 不算 RED；修测试本身，重跑 |
| RED 时特征测试失败 | 先观察实际输出，对齐断言到观察值；不修代码 |
| GREEN 时特征测试失败 | 回归；修代码 |
| 新行为测试在 RED 通过 | 坏测试（测的是既有行为）：加严到会失败，或识别出它本该是特征测试 |
| 任务声称有新行为但 RED 全绿 | 坏测试或理解错任务；停下核对 |
| 纯重构任务 RED 全绿 | 合法（全是特征测试） |
| 快照锁住了 bug | 记台账不就地修；bugfix 独立循环；落地后更新快照，新值 = 复现断言值并附理由 |
| 批量实现后仍有测试不过 | systematic-debugging 找根因；不许弱化断言；验收标准本身错 → 按执行技能停止条件处理 |
| 解依赖本身引入行为变化 | 特征测试在开缝后立刻抓出；开缝是 REFACTOR，禁止夹带行为变更 |
| 目标函数完全无法直接调用 | 沿调用链向上找最近可观察入口，先在那层锁（§3.4） |
| 遗留区域要加新行为 | 嫩枝法：新逻辑长在新可测单元，遗留处留一行调用（§3.4） |
| 开缝时无任何观察点可用 | Ruling 记台账；「保持行为」不可观察 = 停止条件，停下问人（§3.4） |
| 非确定性输出（时间/随机/无序） | 快照前先固定：时钟、种子、无序断言 |
| 批量导致过度实现 | 审查者「多余」类发现项兜底（既有机制） |
| 边写测试边写实现交替进行 | 违反批量 RED：实现开始前全部测试必须已写完且跑过红（§3.2 纪律） |
| 失败测试单独成提交 | 禁止；新行为测试与实现同批提交，保每提交皆绿（§3.2 提交切分） |

## 6. 验证方案（writing-skills 合规）

本次改动属**技法类**（条件分支与循环粒度），按 writing-skills 形式匹配表用**应用场景**验证，不适用纪律类的压力叠加。3 个场景 × 改前/改后 = 6 次子代理运行：

- **场景 1（遗留）**：无测试的 Python 模块（含一个潜伏 bug + 一段需解依赖的纠缠代码），任务 = 一处小改 + 解依赖。基线记录：是否先锁？是否把快照当违例？是否就地修 bug？
- **场景 2（批量）**：一个 4-5 条验收标准的任务。基线记录：往返次数、是否逐行为、是否出现回声测试。
- **场景 3（复合：纠缠遗留 + 接口难测）**：一段深度纠缠（I/O 死耦合、核心无法直接调用）的遗留模块 + 一个计划接口经审读认定难测的任务。基线记录：是否先找最近缝？是否私自改接口（而非 Ruling/上报）？是否嫩枝？改后对照：引导协议顺序、分级处置、提交保绿。

**成功标准（可判真伪）：**
- 场景 1：特征测试先于任何生产代码改动存在且改前跑绿；bugfix 用独立复现循环；快照更新（如有）附理由。
- 场景 2：核心 RED/GREEN 往返 ≤ 3 次（不含 task-done 全量）；每条新行为测试有先红证据；绿地「先红」纪律无退化。
- 场景 3：处置遵循纠缠矩阵的固定序列；无私自改接口；提交历史全绿。

场景文件放临时目录（不入库），基线与对照结果报告在会话中。

## 7. 我替你做的决定（审查时重点看这几条）

1. 铁律改写为**双形态**而非加例外条款——writing-skills 禁止细微让步条款；例外必须是可观察谓词的条件式。
2. 特征测试不引入新框架，就是普通测试，同套件同跑法。
3. 术语只用两个：**特征测试**（技术名）与**新行为测试**（对照名），不造「组」类黑话。
4. writing-plans 的可选改动（§4.4）**纳入**；理由如该节。
5. 批量规则定义在 TDD 技能内（单一事实来源），执行技能只做表述同步。
6. 基线场景用真实子代理跑（共 6 次），成本换证据。
7. 解依赖不作为铁律的例外——它就是第二形态（保持既有行为）在粗网眼下（最近缝上对照）的应用；嫩枝法与引导协议一并纳入遗留节。
8. 批量模式下提交粒度保「每提交皆绿」：特征测试可先行提交，新行为测试与实现同批提交；纠缠处置总原则「拿证据与改变现不进同一提交」。
9. 接口可测性防线的层级：计划期自审 + 独立审读为主（§4.4、§4.6），执行期 Ruling/上报为兜底（§3.5）——防线主体在计划阶段，不在 SDD 环节。
