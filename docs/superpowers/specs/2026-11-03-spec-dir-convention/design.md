## 1. 背景与目标

- **解决什么问题：** 现行两处技能文案保留了「需求方偏好覆盖约定目录」的口子：设计阶段的存放位置段写着「需求方的偏好优先于以上两者」，计划阶段写着「需求方对计划存放位置的偏好覆盖此默认值」。失效方式：某次需求按偏好落到约定目录之外 → 集成验证全量遍历约定目录下的验证方案时找不到它，回归的「登记册 ∪ 约定目录」双源同样扫不到 → 集成验证按其原文「一篇都找不到按未声明」降级——该需求的验证环节实际缺失，且不产生任何指向本需求的标注。
- **给谁用：** 最终用户是执行工作流的编码代理——它们不再需要判断「偏好是否覆盖约定」；需求方是仓库维护者——产物位置从此可预测，验证与归档链路不再有漏检口子。
- **成功判断标准：** 三条可观察行为——(1) 两处文案中不再存在任何「偏好或指定可改变产物目录」的表述，取而代之是位置固定、不接受指定的显式句；(2) 有软件仓库时，需求方在对话中指定其他位置，最终用户仍按约定目录落盘，并告知产物已落约定目录（落点）与该指定未被采用；(3) 集成验证既有测试全绿，产物目录扫描链路无缺口。

## 2. 功能清单

### 2.1 产物目录唯一约定

- **定位：** 产物存放位置的唯一约定——有软件仓库时三件套一律落约定目录，取消位置输入通道（见术语表）。
- **触发与输入：** 触发方式——设计阶段落盘设计文档时、计划阶段落盘计划时；输入清单——需求描述与本工作流的目录约定。需求描述中的任何位置指定不再是有效输入；仓库自身的其他文档惯例不构成例外（扫描路径由集成验证原文固定——此为我依仓库可查事实敲定的决定，非需求方裁决）。
- **执行要点：**
  1. 有软件仓库时，三件套一律落约定目录（日期-主题命名、随需求建立、三件套同目录），文案不再出现「偏好优先」「偏好覆盖」表述。
  2. 需求方在对话中另行指定位置时，最终用户按约定目录落盘，不发起询问、不等待确认，但明确告知产物已落约定目录、该指定未被采用（否则需求方按其指定位置查找会扑空，违背 §1「位置可预测」目标）。
  3. 目录约定的位置规则无例外：优先于设计技能内任何「按需求方要求去做」类条款（含选择退出提问后的照办路径）——位置不是可被要求改变的对象。
  4. 没有软件仓库时，维持既有行为：询问存放位置（约定以仓库存在为前提，此场景无约定可循）。
- **出口：** 单一出口——按约定目录落盘。
- **流程图：** 不配图——本功能的实质正是消除分支（偏好判断分支被删除），无决策点、无多出口。
- **本次不做：** 见 §3（明确不做）第 1-5 条。

## 3. 明确不做

- **不改工作树技能的任何表述（含其目录偏好相关段落）**：因为工作树是运行时隔离环境的选择，不是产物目录，二者覆盖不同对象，混改会扩大行为塑形改动的审查面而无对应问题；实施时以整文件不触碰为界，不以句数计数为界。
- **不改设计技能的「选择退出提问后按其要求去做」与「按正常工作流去做他们要求的事」两条通用条款**：因为它们是技能通篇交互骨架的一部分，为目录一处特判会破坏条款完整性；目录的位置固定性由 §2.1 执行要点 3 的上位性规则覆盖，不动原文。
- **不改「没有软件仓库时，询问」：** 因为该场景下约定不存在（无仓库即无约定目录可落），询问是必要兜底；需求方的「无法指定」裁决针对的是约定存在时的产物目录。
- **不写多步对抗剧本：** 因为需求方裁决的语义是「此输入通道不存在」，一句话固定即可；展开「如何应对需求方坚持」的话术会引入不存在的交互场景，且行为塑形内容每多一句都是审查负担。
- **不改归档链路：** 因为归档目录与移动动作已有固定约定且从未留偏好口子，本次问题不存在于该链路。

### 决策 1：口子消除的强度

- **候选方案：** A. 纯删除两处偏好句，约定成为沉默的唯一默认；B. 删除偏好句 + 各补显式固定句（位置固定、不接受指定；审读处置中 B 扩展为另含无例外上位性规则与告知义务，见依据段与「留给构建者的部分」）。
- **选了哪个：** B。
- **依据：** 需求方裁决的字面义是「需求方无法指定此目录或文件位置」。纯删除（A）只消除了文案里的口子；最终用户面对「需求方坚持指定位置」时是否会让步，是无验证的行为判断——本设计按保守方向处置：宁可多一句显式规则，不赌沉默默认足够。审读补查发现设计技能内另有两条「按需求方要求去做」的通用条款（选择退出提问后的照办路径、退出对话后按正常工作流行事），纯删除在这些路径上仍留口子；B 方案因此追加无例外的上位性规则（§2.1 执行要点 3）覆盖这些路径，不修改通用条款原文（见 §3）。B 与需求方裁决语义逐字对应。
- **代价或风险：** 新增对抗性文案，触行为塑形内容的高门槛；成本量级极小（两处各一句）。缓解：本改动有明确动机（验证链路完整性漏洞）与需求方明确裁决，非无证据的文案重构；措辞克制，不展开剧本（§3）。行为级效果（指定场景下是否真按约定落盘）无法由文案级断言证明——是否追加跨会话压力测试或前后对比评估，已于 2026-11-03 会话裁决：**不追加**，接受「文案级断言 + 实际会话观察」的弱验证路径（需求方依建议选项裁决）。

### 决策 2：调整范围

- **候选方案：** A. 仅产物目录（两处文案）；B. 连工作树技能的目录偏好一并去除。
- **选了哪个：** A。
- **依据：** 需求方原文是「设计和计划的目录」；工作树目录是运行环境隔离的选择，与产物存放是两类对象。需求方在对话中对「不动工作树偏好」的默认未提出异议，并补充裁决「需求方无法指定此目录或文件位置」，语义收敛于产物。范围界定最初按「偏好」一词的字面检索完成，审读补查发现「按其要求去做」类条款同样构成位置让步路径——该路径的覆盖归决策 1 的上位性规则（§2.1 执行要点 3），改动仍限于两处文案，本决策范围不变。
- **代价或风险：** 工作树偏好口子保留——但那不产生验证链路漏检（工作树不影响产物落盘位置），风险可忽略。

### 决策 3：规模判定

- **候选方案：** A. 按小改动简短版（不做独立审读、不进完整计划）；B. 按项目级完整流程。
- **选了哪个：** B。
- **依据：** 小改动判据三条须同时满足（单个功能点、不新增模块、不影响既有行为契约），本改动修改的正是「目录位置覆盖规则」这一行为契约，第三条不满足，不满足即不应按简短版处理。判据规定由需求方判定，审读前我按当时文本代行了判定，结论落在判据语义的保守侧；且与同日兄弟需求（uniform-full-workflow）「所有改动都产出设计文档与实施计划」的口径一致。该判据字面属兄弟需求的清零对象，本文档引用它仅作成稿时点的判定记录，不依赖其存续。
- **代价或风险：** 文档与审读的形式成本高于两处文案改动的直观体量；换来的是行为塑形改动的审查纪律不破例。

#### 留给构建者的部分

- **显式固定句的具体措辞：** 交给执行者。边界：固定句单句、含「有软件仓库时不接受指定」语义、须表达无例外的上位性（§2.1 执行要点 3）、不得展开应对剧本；固定句之外各伴一句告知要求（承载 §2.1 执行要点 2 的两成分告知义务——产物已落约定目录（落点）与指定未被采用，不得并入固定句）；两处文案各自独立成句（技能独立加载，不做跨技能引用）。为什么交给执行者：措辞须融入各技能现有行文，设计只锁语义不锁字面。
- **是否新增反向断言锚定：** 交给执行者。现状：集成验证测试锚定了收尾技能的上位载体句，但未锚定这两处偏好句——删除不会破坏既有断言；可选做一条反向断言（偏好句不得回归）。为什么交给执行者：断言增补涉及测试脚本的既有编排惯例，由执行者按现场惯例决定。
- **执行方式：** 交给计划阶段确认点。边界：分支策略与本需求同兄弟需求（同日、同触工作流技能正文与集成验证测试文件）的合并顺序在计划里定。为什么交给执行者：分支操作不属设计管辖。

## 5. 关键约束与可行性风险

- **行为塑形内容门槛：** 仓库纪律要求技能改动有证据、不无据重构调优内容。本次满足：有具体失效场景（验证方案脱离全量遍历与双源扫描、按未声明漏检）+ 需求方明确裁决。
- **既有断言兼容：** 集成验证测试未锚定这两处偏好句，删除不破坏既有断言；执行后跑集成验证测试确认全绿。
- **上游同步分叉：** 本 fork 纪律明确 fork 特有改动不上游，分叉无实际代价。
- **兄弟需求同文件交叉：** 同日兄弟需求（uniform-full-workflow）的断言清零清单含「判错则升级」等短语，与本需求同触工作流技能正文与集成验证测试文件。本设计不与之冲突——决策 3 结论与其口径一致；分支与合并顺序留计划（见「留给构建者的部分」）。
