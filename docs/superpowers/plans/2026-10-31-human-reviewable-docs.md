# 人工可审阅的设计与计划文档：技术实现方案

> 读者假设：已读产品功能说明 `docs/superpowers/specs/2026-10-31-human-reviewable-docs-design.md`（为什么要改、改什么、不做什么、主要取舍）。
>
> 实施前决策记录 + 日期：2026-10-31。

**目标：** 让两个写作技能产出符合五章结构、可人工审阅的设计文档与计划；两份文档各经一次合并审读；保留两道确认门；两份文档提交并保留。

**架构：** 两个技能各自就地升级。主文件保留流程与必做步骤；体量大的模板与写作要求移入各自的 `references/`；合并审读提示词放在技能根目录。删除被合并的 builder check 提示词。

**技术栈：** Markdown 技能文档；仓库现有 shell 测试（skill-size、render-graphs、shell-lint）。

**设计文档（Spec）：** `docs/superpowers/specs/2026-10-31-human-reviewable-docs-design.md`

## 2. 功能单元规格

### Task 1: brainstorming 设计文档模板

**Files:**
- Create: `skills/brainstorming/references/design-doc-template.md`

**Interfaces:**
- Consumes: 产品功能说明 §2.1（设计文档五章、五章之外固定块、写作规则、小改动简短版）、§2.5（头部标注与范围冻结）、§2.6（七条写作要求）。
- Produces: 模板文件，固定标题为 `# 设计文档模板`、`## 五章`、`## 五章之外`、`## 写作要求`、`## 小改动简短版`；五章逐章写内容要求。

**边界条件:**
- 五章顺序固定：背景与目标、功能清单、明确不做、关键决策记录、关键约束与可行性风险。
- 每章必须写出内容要求：背景与目标含成功判断标准；功能清单逐项写「输入什么 → 最终用户看到什么」并附不做范围；明确不做逐项写因果理由；关键决策记录写候选 → 选择 → 依据 → 代价/风险与成本量级，并设「留给构建者的部分」小节，逐项写交给执行者决定什么、边界在哪、为什么；关键决策记录还写方案合理性自检（候选是否真实、依据是否成立、代价是否被低估、是否有更简单做法、能否解决第 1 章的问题）；关键约束与可行性风险只列影响做不做的事实，不承接委托决定。
- 五章之外必须包含：读者假设与术语表、独立审读处置记录附录（初稿可写「待审读」）、头部标注「实施前决策记录 + 日期」。不得新增第六个内容章。
- 写作要求七条逐字来自产品功能说明 §2.6；设计文档不出现接口、文件名、函数名、模块路径。
- 第三方依赖的取舍决策可提依赖名；其余实现词汇禁止。
- 小改动一节写明判据（单个功能点、不新增模块、不影响既有行为契约）、简短版、判错升级为项目级并重做。
- 「明确不做」一节注明：确认后冻结，实施中不回写；范围变更回到设计确认门。

**验收标准:**
- 五条独立命令全部通过：分别 `grep -q "背景与目标"`、`grep -q "功能清单"`、`grep -q "明确不做"`、`grep -q "关键决策记录"`、`grep -q "关键约束与可行性风险"`。
- `grep -q "输入什么 → 最终用户看到什么"`、`grep -q "候选"`、`grep -q "成本量级"`、`grep -q "留给构建者"`、`grep -q "方案合理性"`、`grep -q "明确不做.*冻结"` 全部通过。
- `grep -q "实施前决策记录"` 通过；`grep -q "小改动"` 通过；七条写作要求逐条存在。
- `grep -q "第三方依赖"` 通过（依赖名例外存在）。
- `tests/skill-size/test-skill-size.sh` 通过（本任务不改主文件，作为基线检查）。

### Task 2: brainstorming 合并审读提示词

**Files:**
- Create: `skills/brainstorming/review-prompt.md`
- Delete: `skills/brainstorming/builder-check-prompt.md`

**Interfaces:**
- Consumes: 产品功能说明 §2.3（设计文档三张清单、三堆分类、输出格式、设计文档验收集、方案合理性、渲染检查、无子代理降级）。
- Produces: 审读提示词文件；供 Task 3 在 SKILL.md 中引用。

**边界条件:**
- 提示词要求一次通读，输出三张清单：完备性问题、可读性问题、方案合理性问题。空清单也要逐项声明「本项通过」。
- 完备性问题分三堆：已有答案（文档或仓库能回答）、次要（后续环节执行者能自行敲定）、归需求方（只有需求方能回答且答案改变做成之物）。审读者先按文档与仓库事实分类；作者复核并补对话上下文。
- 方案合理性：审读者评估候选方案是否真实、取舍依据是否成立、代价/风险是否被低估、是否漏掉更简单的做法、方案能否解决问题；每个关键决策给「合理 / 有疑问 / 不合理」判定与理由。
- 输出格式：位置 + 原句 + 卡住的原因 + 严重度；只标问题，不改稿；方案合理性判定可评价方案，但不替作者改方案。
- 可读性验收集逐项回答「能 / 不能 + 卡住的原句」：需求方只读设计文档，能否回答做什么、不做什么、为什么、成本量级与风险是否可接受。
- 渲染检查：有渲染环境看渲染结果；没有时检查 Markdown 结构（表格列数、代码块围栏、图语法、标题层级、列表嵌套）。
- 提示词不要求审读者改稿，也不要求它替代需求方确认。

**验收标准:**
- `test -f skills/brainstorming/review-prompt.md` 通过。
- `grep -q "完备性"`、`grep -q "可读性"`、`grep -q "方案合理性"`、`grep -q "已有答案"`、`grep -q "次要"`、`grep -q "归需求方"` 全部通过。
- `grep -q "有疑问"`、`grep -q "严重度"`、`grep -q "不改稿"`、`grep -q "Markdown 结构"` 全部通过。
- `test ! -f skills/brainstorming/builder-check-prompt.md` 通过。
- `grep -rn "builder-check-prompt" skills/` 无输出。

### Task 5: writing-plans 合并审读提示词

**Files:**
- Create: `skills/writing-plans/review-prompt.md`

**Interfaces:**
- Consumes: 产品功能说明 §2.3（计划三张清单、三堆分类、输出格式、计划验收集、实现效果、渲染检查）；设计文档路径与计划路径。
- Produces: 审读提示词文件；供 Task 6 在 SKILL.md 中引用。

- 实现效果：判断按计划实施后，设计承诺的用户可见效果是否真的出现；每条设计功能给「能达成 / 有疑问 / 不能达成」判定与理由；任务组合、接口契约、集成点、失败路径与非代码工作都要覆盖。
- 可读性验收集：工程读者只读计划，能否判断改哪、怎么改、边界在哪、为什么这样改、实施风险是什么；需求方能否抽查范围、任务边界与主要风险。
- 输出格式：位置 + 原句 + 卡住的原因 + 严重度；只标问题，不改稿；空清单逐项声明「本项通过」。
- 渲染检查：有渲染环境看渲染结果；没有时检查 Markdown 结构。

## 3. 设计依据

- **模板移入 `references/`**：仓库测试对技能主文件施加 20,000 字节上限（按字节计数，比 Claude Code 压缩后 20,000 字符的重新附加限制更严格）。头脑风暴主文件当前约 17.3KB，新增五章模板、七条写作要求、合并审读流程会逼近上限；移出后主文件只保留流程与指针。
- **删除 `builder-check-prompt.md`**：产品功能说明决策 9 把完备性检查并入独立审读。保留两个提示词会让执行者不知道用哪个，也会让一次派发退化成两次派发。
- **计划保留 `### Task N` 与四段任务结构**：SDD 的 `task-brief` 脚本按 `#+ Task N` 机械切分，不解析字段；保留标题即可兼容。四段结构是执行者不读整份计划也能工作的信息集。
- **删除实施后记**：需求方明确不要。计划定位为实施前决策记录，实施后的结论由提交信息承载。
- **两个技能不互相引用写作要求与审读提示词**：产品功能说明决策 1 选择各自升级；流程交接仍可点名下一个技能，但写作要求与审读标准各自完整承载，避免跨技能缺文件与措辞漂移。
- **合并审读按文档类型出清单**：一个子代理通读一次；设计文档输出完备性、可读性、方案合理性三张清单，计划输出完备性、可读性、实现效果三张清单；补写实质内容交回同一子代理复读，避免「补写部分未审」。
- **计划限定软件项目**：计划的五章（模块、文件、接口、分层）是软件概念；非软件项目止于设计文档，避免套模板产生空章。
- **确认后冻结「明确不做」**：与「不依赖实施后回填」一致；范围变更走设计确认门，避免文档在实施中继续变化。

## 4. 约束

- 两个技能主文件各自小于 20,000 字节；超限即改结构，不删关键指令。
- 保留 `### Task N` 标题锚点与任务四段式；不预写测试代码与实现步骤。
- 不改变头脑风暴的提问方式、视觉伴侣、spike 流程；不改变执行环节技能。
- 设计文档不出现接口、文件名、函数名、模块路径；计划可以出现文件、接口、代码。
- 两份文档各走一道确认门；「嗯」「继续」不算明确确认。
- 所有技能文本用简体中文；术语与现有技能保持一致。
- 实施期间的修改只留在工作区，需求方确认后再提交。

## 5. 风险清单

| 风险 | 触发条件 | 影响 | 缓解 |
|---|---|---|---|
| 主文件仍超 20KB | 新增内容过多或移除不彻底 | 仓库测试失败；压缩后关键指令丢失 | 改完立即跑 skill-size；超限则把更多细节移入 references |
| 模板只有标题、没有内容要求 | 只写五章标题 | 产出五个空章，验收仍通过 | 模板逐章写内容要求与示例；验收逐章检查关键内容 |
| 合并审读角色塌缩 | 提示词只强调可读性 | 完备性、方案合理性或实现效果问题被漏掉 | 提示词强制清单分别声明；补写内容复读；小场景验证 |
| 删除 builder check 留下引用 | 其他文件仍指向旧文件或旧措辞 | 执行者找不到提示词，或按旧流程执行 | 删除前 grep；删除后 grep 文件名与「builder check」 |
| 计划模板改动破坏 SDD | 任务标题或字段变化 | `task-brief` 切不出任务 | 保留 `### Task N` 与四段式；用本计划跑 task-brief |
| 两份技能措辞漂移 | 只改一处写作要求 | 两份文档标准不一致 | Task 7 用 diff 比对七条要求；五章名称逐项比对 |
| 小场景验证不代表真实使用 | 场景过小或子代理未按技能执行 | 验证通过但真实使用仍失效 | 选一个完整小需求；审读者按 review-prompt 执行；记录局限 |
| 实施后设计变更阻塞 | 设计必须改但已开始实施 | 返工或回滚成本高 | 停止实施，回到设计确认门；返工或回滚由需求方决定 |
