## 0. 改造总览

| 项 | 现状 | 改为 |
|----|------|------|
| 技能数量 | brainstorming + writing-plans 两个 | 合并为一个（建议名 `design-and-plan`，见 §2.1） |
| 产物文件 | design.md + plan.md + verification.md | design.md + **implementation.md（新增）** + plan.md + verification.md + **decisions.md（新增）** |
| plan.md 角色 | 计划（混装实现设计与任务规格） | **仅实施工作单**（下游执行技能零改动） |
| 审读 | 两 skill 各自审、上下文割裂 | 一个审读子代理审全套产物、跨文件一致性核对 |
| 设计文档 | 纯文字 | 条件化章节 + UI 效果图冻结落盘 + 数据字典 |
| 呈报纪律 | 无分离规则（发生过确认语义事故） | 裁决与确认强制分离的硬规则 |
| 确认门 | 设计确认 + 计划确认两道 | **全套规格一次确认**（实施前唯一门，见 §4） |

**不动的部分**（实践验证有效，勿改）：
- 流程闸门骨架：定性 → 设计与计划成稿 → 独立审读 → 需求方确认 → 执行；
- 独立审读子代理制度（未参与写作的全新代理）；
- HARD-GATE 实质：**全套规格确认前不得实施**；确认语义不含糊；
- plan.md 的任务格式（Files / 边界条件 / 验收标准）——执行与把关的实际价值所在。

## 2. 合并后的技能设计

- 建议名：`superpowers:design-and-plan`（语义直白：从想法到可执行工作单）。

### 2.3 SKILL.md 流程（一条线）

```
定性（feature/bugfix/非实施）
→ 需求对话（复述与提问交替；视觉伴侣在第一次复述 UI 相关内容前即提议，不等到聊完）
→ 四件套成稿：design.md（含形态声明、条件章、界面效果图冻结、数据字典）
   + implementation.md + plan.md（工作单）+ verification.md + decisions.md 随裁决追加
→ 自查（把审读检查清单前置，见 §5.5）→ 排版脚本检查
→ 一个审读子代理审全套产物（见 §5.4）——含跨文件一致性核对
→ 修订（批量，§5.2）→ 收敛复读（§5.3）
→ 结构化呈报：裁决项（独立段）‖ 全套规格确认（独立段，对象显式写全四件），见 §4
→ 需求方确认后 → 执行交接（子代理驱动 / 会话内，沿用现有规则）
```

要点：
- **单确认门**：全套规格（design / implementation / plan / verification）确认一次即进入执行。确认请求的审查负担用呈报摘要缓解：呈报消息附「决策速览表 + 建议重点抽查点（≤3 处）」。
- **确认后回改**：确认后任何文档需要修改（含实施中发现设计必须改）→ 停止实施，修订 → 审读（可收敛为增量审读）→ 重新确认；门重开期间不写产品代码。
- **审读一次覆盖四件**：正因四件在确认前全部成形并被同一审读者核对过，单门才安全——若某件产物未成形就进入呈报，必须退回成稿，不得以「骨架+后续确认」替代单门。

## 3. 产物规格（五件套）

### 3.1 design.md 模板改造

原有五章保留：背景与目标 / 功能清单 / 明确不做 / 关键决策记录（含留给构建者的部分）/ 关键约束与可行性风险。新增与修改：

**a) 文首新增「形态声明」**

```
产物形态：纯 API / Web 应用 / 桌面 App / 移动 App / CLI / 库或 SDK / 混合
章节裁剪推导：条件章哪些适用、不适用的原因——无推导不合法
```

**b) 新增条件章「界面规格」（形态含 UI 时必设）**

- 每个界面一节：**冻结的效果图**（相对路径引用 `mockups/` 下落盘文件）+ 两级标注：
  - **约束级**：布局结构、字段清单、状态清单（空态/错误态/特殊态逐个列出）——必须实现；
  - **示意级**：间距、配色、字号——留给实现。
- **视觉稿定稿冻结机制**：需求方每确认一块视觉稿，立即将 HTML/截图落盘到 `specs/<date-feature>/mockups/` 并随仓库提交（截图可用 `chrome --headless --screenshot` 等无头方式生成）；design.md 只允许引用已冻结文件，禁止引用会话临时目录——杜绝「无锚引用」。
- 纯 API 等无 UI 形态不设本章，但须在裁剪推导中写明「响应/输出即用户可见面」的对应保障（如错误码全集归入接口章）。

**c) 新增条件章「数据字典」（产物涉及持久化或外部格式时必设）**

- 记录**产品级**数据形态（用户可感知、可手改的）：实体、字段、语义、外部格式、权限、手改语义。
- 与 implementation.md 的「数据与状态设计」分工：design 管「是什么」（行为承诺），implementation 管「怎么存」（物理实现）。示例：design 数据字典写「模型 = 显示名 + 接入点 + 密钥 + 档位映射，配置文件用户可手改」；implementation 数据设计写「config.json 的完整 schema、0600 权限、读写原子性」。

**d) 措辞纪律新增一条**：禁止无锚引用——凡「已确认/已验证」必须能指到仓库内文件或对话裁决记录（decisions.md），否则删掉断言或先落盘再引用。

### 3.2 implementation.md 新模板（实现设计，审查用；给人看）

```markdown
# <项目> 实现设计

> 读者：审查者（需求方/审读子代理）与计划撰写者。本文是数据与接口的唯一权威定义；
> plan.md 工作单只引用本文章节号，不复制签名。

## 0. 形态声明
产物形态：……
章节裁剪推导：……

## 1. 结构设计
- 模块划分图（mermaid）、各模块一句话职责、依赖方向与分层
- 任务拆分依据（为什么这样切任务）

## 2. 数据与状态设计
- 每个持久化实体一张字段表：字段 / 类型 / 语义 / 约束 / 来源 / 示例值
- 存储位置、权限、并发与原子性语义
- 外部格式（如需读写外部系统拥有的文件）：转换规则 + 输入输出示例逐字对照
- 状态机（如有）：状态、事件、迁移表

## 3. 接口设计
按「先外部后内部」组织。接口 = 跨越边界的约定：
- 外部接口（对外承诺）：HTTP endpoint / 公共库 API / CLI 参数与退出码 / 事件消息——逐字严格；
- 内部接口（模块间）：六段式（见 §3.2.1）。

### 3.2.1 接口六段式（每接口固定六段）
1. **职责**：一句话，解决什么问题；
2. **签名**：精确（给执行者）；
3. **参数表**：参数 / 类型 / 含义 / 约束与非法值；
4. **错误表**：条件 → 错误 → 调用方应对；
5. **示例**：一次调用 + 对应行为（结果逐字）；
6. **被谁依赖**：哪些流程/模块经由它。

### 3.2.2 外部接口补充段（对外承诺级）
7. **契约**：请求/响应全文示例、错误码全集、版本与兼容承诺（纯 API 项目本节为文档主体）。

## 4. 流程设计
- 关键链路 mermaid 顺序图（sequenceDiagram）：参与者、消息次序、数据流
- 每条链路标注涉及接口章节号

## 5. 界面实现规格（条件：有 UI）
- 视图结构、状态管理方案与归属、与 design.md 界面规格章的映射
- 平台能力约束实测结论（如：构建工具链能力边界、自动化测试可用性）

## 6. 运行与部署形态（条件：需运行的产物）
- 进程模型 / 部署目标 / 环境要求 / 分发方式 / 最低系统版本

## 7. 规模评估
- 指标随形态选：代码量分布（模块×预估行数）/ QPS·并发·延迟预算（服务）/ 页面数·包体（Web）/ 内存·体积（App）/ API 面大小（库）
- 复杂度热点与对策

## 8. 设计依据 / 约束 / 风险清单
- 与 design.md 决策的承接关系；实施层新增取舍按「候选/选择/依据/代价」四段
```

**章节裁剪速查（形态 × 条件章）：**

| 章 | 纯 API | Web | 桌面/移动 App | CLI | 库/SDK |
|----|--------|-----|--------------|-----|--------|

### 3.3 plan.md 改造（实施工作单；给执行者）

- **角色收缩**：只保留任务规格（现有格式：`### Task N` + 职责 / Files / 边界条件 / 验收标准 + 流程图）+ 元数据 + 执行交接 + 附录。
- **Interfaces 块瘦身**：不再复制签名，写 `Consumes: implementation.md §I-3（SettingsWriter）`；Produces 仍须列出本任务新增物的名字与所在章节号（供下游引用与审读核对）。
- **新增文首「任务依赖图」**：mermaid 图标依赖关系与关键路径；显式声明实施顺序，含「多个任务 Modify 同一文件时顺序不可调换」类约束。
- 文首加一行指针：`实现设计见同目录 implementation.md；本文件是唯一执行依据。`

### 3.4 verification.md 改造

- 执行手段章改为**分层自动化策略**：机器可操作步骤（启动、改文件、备份恢复、辅助功能 API 模拟点击）由驱动脚本执行；断言优先用「可观测缝」（环境变量、调试日志、系统状态可查询接口）；真人工只剩：权限弹窗类（一次性授权点击）、不可模拟的拒绝路径、会话级验证（注销重登）——逐条诚实标注，不伪装自动化。
- 新增「可观测缝」清单：为验证而设的环境变量/日志点/状态查询，注明对正常运行零影响的论证。
- 场景出处约定：`§N` 指 design.md，`Task N` / `I-N` 指 plan.md / implementation.md。

**3.4.1 驱动脚本 = 引擎 + 场景数据分离（应对 finish 合并/替换/删除）**

脚本若与具体场景耦合（每 feature 一份脚本代码），并入登记册时会面临代码级合并，替换删除无解、且随 specs 归档冻结成死物。因此：

- **引擎**：项目级通用执行器（如 `scripts/verify-engine`），只认场景 DSL，不含具体场景；一次编写、极少演进，不随 feature 归档。
- **场景数据**：结构化条目活在 verification.md / 登记册，字段含 `id`（登记册合并键，全局唯一）、`schema`（DSL 版本）、`title`、`kind`（auto / semi / human）、`steps`（引擎内置操作原语：backup/launch/quit、file-check、log-grep、ax-click/ax-read/ax-type、run-command、sleep，按需增原语）、`assertions`（机器断言）、`human-observe`（人工观察点，引擎收集后统一呈报）、`cleanup`。
- **生命周期**：finish 阶段并入登记册 = 数据条目合并，引擎不动；场景替换/删除 = 改条目 + decisions.md 记录；specs 归档冻结的是快照，登记册持现行有效数据，引擎只读登记册；regression-sweep 由引擎解释执行登记册并汇总 PASS/FAIL。
- **冲突与漂移**：同 id 不同期望 → finishing 人工环节裁决并记 decisions.md；UI 变更导致 ax 断言失效 → 改场景数据（与维护测试代码同理），回归失败即漂移信号。
- **起步策略**：原语从当前场景所需最小集起步，随新需求扩展；kind=human 的场景引擎只收集观察点、不执行。

## 4. 呈报与确认纪律（硬规则，写入 reporting-rules.md 并在 SKILL.md 引用）

1. **单确认门**：全套规格文档（design.md / implementation.md / plan.md / verification.md）确认一次即闭门进入执行；确认请求对象必须显式写全四件。**确认前不得实施**（不写产品代码、不装依赖、不建工程骨架）。
2. **分离规则**：待裁决项与确认请求不得出现在同一个问题里；确认请求独立成段。
3. **裁决呈报格式**（每项固定三段）：现状 / 建议 / 影响。裁决项可一次列多项，但只回答裁决。
4. **回复模板**（呈报消息末尾给出）：

```
回复格式：
- 裁决：1–N 按建议，或逐项说明你的决定
- 确认：确认 / 不确认（对象 = 全套规格文档）
```

5. **解读规则（写给执行技能的自己）**：需求方对裁决项的任何回应（含「同意」「按建议」）**不得**被解读为对任何文档的确认；确认门只在需求方对显式对象回复确认时关闭。
6. **呈报审查负担缓解**：确认请求段附决策速览表（决策|结论|出处章节）与建议重点抽查点（≤3 处，按审读高危项挑）。
7. **确认后回改**：确认后任何文档需改 → 停止实施 → 修订 → 增量审读 → 重新确认；已实施部分按原 writing-plans 回退规则处理（返工或回滚由需求方决定，已合入 main 的用新提交修正，不改写历史）。
8. **耗时预告**：呈报附下一阶段预计耗时（对话轮数 + 机器时间量级 + 需人工参与点数量）。
9. **轻量修订通道**：纯文字修订（不改行为/范围/决策的引用修正、措辞）允许直接改 + 在 decisions.md 或附录登记，门不重开；影响行为/范围/决策的任何改动必须重走确认。

## 5. 审读纪律改造

### 5.1 影响阈值与条目预算（写进 review-prompt.md）

- 审读只报三类问题：**高** = 改变做成之物 / 导致返工；**中** = 会导致执行歧义或验收不可满足；**低** = 措辞与排版——低危合并为一条清单，作者批量处理。
- 条目预算：单清单 ≤15 条，超出时按影响截断并在末尾注明「已按阈值截断」；这把审读从「巨细无遗」纠偏为「价值密度优先」。

### 5.2 批量修订

- 审读者对每条高/中危问题附**建议替换文本**（不是改稿，是可采纳的建议）；
- 作者批量裁决后**整章重写**（Write 替代几十个零散 Edit），工具调用轮次从数十次降到个位数。

### 5.3 复读收敛规则

- 复读只核对「修订是否忠实落实」，不开放重新发现问题；
- 新发现上限 3 条：超过说明修订质量不达标，退回作者重修而非再开一轮发现。

### 5.4 统一审读提示词要点（review-prompt.md 重写清单）

- 范围：design.md + implementation.md + plan.md + verification.md 四件齐审（+decisions.md 核对标注一致）；
- 新增核对项：跨文件引用一致性（implementation ↔ plan 互引、design 无锚引用禁令）、形态声明裁剪推导、任务依赖图与实施顺序声明、接口六段式完整性；
- 保留：三张清单结构（完备性/方案合理性与实现效果/可读性）、映射表、逐任务可测性推演表、逐行排版清点；
- 形态感知：按形态声明的裁剪结果审章——不苛求纯 API 有界面章，但苛求其错误码契约完整。

### 5.5 自查前置

把 §5.4 的核对项前置为作者成稿自查清单（写作模板内嵌）；自查越严，首轮审读越薄，总时间越短。

## 6. 速度优化清单（预期收益）

| 措施 | 预期节省 | 说明 |
|------|---------|------|
| 审读 3 轮并 1–2 轮（§5.4） | ~20 分钟 | 单一审读者全套产物 + 收敛复读 |
| 影响阈值 + 条目预算（§5.1） | ~15 分钟 | 处置条数从 40+ 降到 ≤15 |
| 批量修订整章重写（§5.2） | ~20 分钟 | 工具调用从数十次降到个位数 |
| 裁决与确认合并一轮呈报（§4） | 一轮对话往返 | 语义不混同的前提下减少轮次 |
| 双确认门并为单确认门（§4） | 一轮审读 + 一轮确认往返 | 门保护实质（确认前不实施）完整保留 |
| 视觉伴侣提前上场（§2.3） | 一轮对话 | 第一次复述 UI 即提议，不等聊完 |
| 自查前置（§5.5） | 间接 | 首轮审读更薄 |
| **合计** | **2.5h → 预计 ≤1.5h** | 不含需求方思考时间 |

## 7. 落地步骤（供你自行改造时照做）

1. **建分支**：superpowers 仓库开改造分支，改完验证后再合入——可回滚。

4. **删旧技能**：确认新技能验证通过后移除 brainstorming / writing-plans 目录（或先保留加 deprecated 标记过渡一个项目周期）。
5. **同步引用**：按 §2.4 修改 using-superpowers、SessionStart hook 文本及其他命中处。
6. **验证**：按 `superpowers:writing-skills` 的验证纪律做——用一个典型触发请求（「我们来构建 X」+「已有设计文档写计划」两种）在全新会话验证技能被正确触发且流程可走通；重点验证合并后 SKILL.md 长度未稀释指令遵循。

**迁移注意**：
- `plan.md` 名字与任务格式保持不动——executing-plans / subagent-driven-development / integration-verification / finishing 全部依赖它；
