# 技能为什么有测试：原理、全景与本次实践

> 回答五个问题：为什么这个仓库的技能有测试而自己写的时候没有？技能为什么需要测试？都应该有哪些？这次 TDD 改造做了哪些？为什么没有全做？
> 依据：`skills/writing-skills/SKILL.md` 原文 + 2026-10-31 TDD 技能改造的实际验证记录。

## 一、为什么你自己建技能时没有测试

因为默认路径把技能当**文档**，而这个仓库把技能当**代码**。

你自己写 skill 的流程大概是：想清楚要教什么 → 写成 SKILL.md → 装上用。有没有用、agent 会不会遵守，靠「读起来写得很清楚」来判断。这个仓库的路径多了一整层——`writing-skills` 技能本身，它的核心主张是一句话：

> **编写技能就是将测试驱动开发应用到流程文档上。**

技能的 description 是触发条件、正文是行为塑形代码、措辞形式决定 agent 是遵守还是讨价还价——这些都是**可以验证的经验问题**，不测就只是猜测。你不是能力问题，是流程问题：你的技能没有经过 RED-GREEN-REFACTOR，所以你只有「写出来了」，没有「有效」。

顺带一个诚实的推论：**不是所有技能都值得同等测试**。纯参考类技能（API 文档）测试很轻；纪律类技能（约束 agent 行为的禁令）不测才真正危险。见第三节。

## 二、技能为什么需要测试

三个理由，每个都来自真实失败模式：

1. **「写了」≠「有效」。** 一个技能的正确性只能通过行为差异证明：没有它时 agent 会失败（RED），有它时遵守（GREEN）。没见过基线失败，你甚至不知道技能教的是不是对的东西——可能 agent 本来就不会犯那个错，技能是空转。
2. **措辞形式有可测量的效果差。** writing-skills 的正面对比测试：在行为塑形问题上，「禁令」（不要 X）的产出质量**明显差于**「配方」（产出是什么形状），甚至比无指导对照更差；追加一条细微让步条款会让稳定一致退化成忽好忽坏。这意味着换一个措辞就是换一次行为结果——猜是猜不出来的。
3. **压力之下会露馅。** agent 聪明且擅长找合理化借口：「就这一次」「太简单不用测」「精神高于字面」。一个纪律技能在平静时被遵守、在时间压力+沉没成本叠加下崩溃，是常见基线。不跑压力场景，你不知道自己的技能是不是这样。

本次 TDD 改造的基线恰好实证了第 1 条：旧技能下三个 agent 的「正确行为」全靠现场自我推理（特征测试为什么可以立即绿、难测接口为什么硬写 mock），技能文本没有给依据——**行为对了，但依据是运气**。没有基线对照，我们就不会知道这一点，改造后也无法证明「锚定在文本上」真的发生了。

## 三、都应该有哪些测试（全景）

### 3.1 按技能类型选测试方法（writing-skills 原表）

| 技能类型 | 例子 | 测试手段 | 成功标准 |
|---|---|---|---|
| **纪律约束类**（规则/禁令） | TDD、verification-before-completion | 学术提问（理解吗）→ 压力场景（遵守吗）→ **多重压力叠加**（时间+沉没成本+疲惫）→ 识别合理化借口并写入反驳 | 最大压力下仍遵守 |
| **技法类**（操作指南） | 解依赖、条件等待 | 应用场景（会用吗）→ 变体场景（边界吗）→ 缺失信息测试（指令有缺口吗） | 正确运用到新场景 |
| **模式类**（心智模型） | 复杂度削减 | 识别场景（知道何时用吗）→ 应用场景 → 反例（知道何时**不**用吗） | 正确识别何时/如何应用 |
| **参考类**（文档/API） | 命令参考 | 检索场景（找得到吗）→ 应用场景（用得对吗）→ 缺口测试（常见用例覆盖吗） | 找到并正确应用 |

### 3.2 形式匹配（写之前先给基线失败分类）

| 基线失败 | 正确形式 | 错误形式 |
|---|---|---|
| 压力下违反规则 | 禁令 + 合理化借口表 + 危险信号 | 软性建议 |
| 遵守但产出形状不对 | 正向配方/契约：直接说明产出是什么 | 禁令清单 |
| 漏掉必需元素 | 模板里设必填（REQUIRED）槽位 | 模板旁的散文提醒 |
| 行为应取决于条件 | 以可观察谓词为键的条件式 | 无条件规则 + 豁免条款 |

### 3.3 微测（措辞层，改行为塑形文字前用）

1. 每次调用一个全新上下文样本（直接 API 调用，或一次性子代理）；系统提示词 = 指导所在的**真实语境**，用户消息 = 一个会诱发失败的任务。
2. **必须含无指导对照组**——对照组没有表现出该失败，就没有东西可修，停下别写。
3. 每个变体重复 ≥5 次——单个样本会撒谎。
4. 人工阅读每一个被标记的命中——自动统计会误判回声式输出。
5. 方差本身是指标：指导起效时各次重复收敛到同一形状；五次五种解读 = 措辞没有约束力，先收紧形式再加字数。

### 3.4 其他层次

- **触发测试**：该触发的场景触发了没有、不该触发的有没有误触发（description 的措辞决定这一切；AGENTS.md 里「brainstorming 必须在验收消息上自动触发」就是这类测试）。
- **部署纪律**：写完任何一个技能必须停下、逐个测试后部署，禁止批量创建不测的技能。
- **上游级 eval**：superpowers-evals 仓库用 Quorum 驱动真实编码 agent 过 Gauntlet QA + 确定性后检查——那是给上游 PR 准备的证据等级，fork 自用一般不跑。

## 四、本次 TDD 改造做了哪些测试

**第一步：判定改动类型。** 本次改动 = 条件分支（双形态铁律、特征测试豁免路径）+ 循环粒度（批量）→ 属**技法类**，按 3.1 表选**应用场景**验证，不适用纪律类的压力叠加。

**第二步：设计可判真伪的成功标准**（设计文档 §6），每条标准对应一个要改变的基线行为。

**第三步：跑基线（RED）——3 个场景 × 旧技能：**

| 场景 | 考察什么 | 基线表现 |
|---|---|---|
| 1：遗留 Python 模块（潜伏 bug + 纠缠代码） | 特征测试会不会被当违例；是否先锁后改 | 行为靠自我推理做对（技能文本无依据）；20 次测试运行（逐行为循环） |
| 2：五条验收标准的绿地任务 | 往返次数；先红纪律；回声测试 | 12 次运行、严格 5 个逐行为循环（设计预测实锤） |
| 3：纠缠遗留 + 不可改的难测接口 | 私自改接口吗；Ruling 留痕还是沉默吞下 | 沉默吞下重型 mock，无任何留痕 |

**第四步：改技能（GREEN），同场景同起点（初始提交克隆）、提示词逐字相同重跑，唯一变量是技能内容。**

**结果：**

| 成功标准 | 结果 |
|---|---|
| 特征测试先于改动且改前跑绿 | 三场景全过；且全部带身份标记（基线无标记） |
| 核心 RED/GREEN 往返 ≤3 | 20→5、12→5、9→6 次运行，循环往返 2 次 |
| 每条新行为测试有先红证据 | 全过；改后 agent 显式引用「错误型失败不算 RED」并放可导入桩保证 RED 合格——**判据条款被当真了** |
| 绿地「先红」纪律无退化 | 场景 2 改后依然全部先红 ✓ |
| 提交保绿 | 零红提交（有一个 agent 用 `git stash` 验证了提交点树上的全绿） |

**第五步：人工读每一份报告**（对应微测第 4 条的精神），不只看数字：期望值来源声明、变异检查、披露读了哪些文件，都是行为改变的证据。

## 五、为什么没有全做（诚实边界）

| 未做的测试 | 为什么不做 | 何时值得补 |
|---|---|---|
| 纪律类压力叠加（时间+沉没成本+疲惫下还遵守吗） | 改动主体是技法类条件分支；但铁律重写确有纪律属性 | 如果你发现 agent 在赶时间时退回逐行为循环或跳过特征测试——那就是该做压力叠加的信号 |
| 措辞微测（对照组 + 每变体 5 次重复） | 成本高；应用场景对照已覆盖主要风险（「先红」退化用场景 2 天然检验） | 引入新的禁令/让步措辞时必做——那是最容易翻车的形式 |
| 每场景多次重复 | 每场景 n=1。writing-skills 自己说「单个样本会撒谎」；三场景方向一致是好信号，无统计强度 | 技能要复用给他人或提上游 PR 前 |
| 「判定不可测 → Ruling/上报」分支 | 场景 3 的 agent 找到了让接口可测的路径，没走到那个岔路口——该分支零样本 | 构造一个任何测试替身都救不了的接口场景（如核心逻辑只在生产环境可观察） |
| 触发层测试 | 本次没改任何 description，触发行为假设不变 | 改动任何 description 时 |
| 上游级 eval（Gauntlet QA） | fork 自用，不准备上游 PR，证据等级按需 | 决定提上游 PR 时——那是 AGENTS.md 的硬门槛 |

一句话版本：**测试的深度跟错误的代价匹配。** 这次改造的错误代价是「agent 在遗留代码上把快照当违例删掉、或往返翻三倍」——场景对照足以验证；如果改的是「TDD 铁律本身能不能扛住 deadline 压力」，那就必须上压力叠加和微测。

## 六、给你自己写技能的最小测试清单

下次自己建 skill 时，按类型取最小集：

1. **先分类**：这个技能是纪律、技法、模式，还是参考？（第三节的表）
2. **纪律类——最少先做两步**：① 无技能基线场景（亲眼看 agent 怎么失败，逐字记下它的合理化借口）；② 写完有技能重跑同一场景，确认遵守。出现新借口 → 写进合理化借口表再测。这是 writing-skills 的 RED-GREEN 最小环。
3. **技法/参考类——一个应用场景**即可：给一个真任务，确认 agent 能照着做对；检索类再加一条「盲找」（不给位置，看它能不能靠 description 找到）。
4. **凡是写了「不要 X」**：停——按形式匹配表换成正配方或条件式，或者拿去微测证明禁令真的有效。
5. **description 只写触发条件**，不概述工作流——否则 agent 会照概述执行而不读正文（触发失效的最常见原因）。
6. **部署前问一句**：我见过它失败的样子吗？没见过 = 没测完。
